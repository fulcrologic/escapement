= Escapement
:toc: left
:toclevels: 3
:source-highlighter: rouge
:icons: font

_Escapement regulates LLM agents the way a watch escapement regulates a mainspring._

A guide to authoring, running, and extending statechart-driven autonomous
agents in this project.

[[introduction]]
== Introduction

Escapement is a Clojure/Babashka library for building coding agents
whose **control flow is a statechart**, not a free-form LLM loop. Workflows are
authored as Fulcrologic Statecharts; an LLM conversation is bound to a
(typically compound) state via the statechart library's invocation mechanism.
While that state is active, a background worker thread holds a live LLM
session, dispatches tool calls, and posts named events back to the chart's
queue. The chart decides what happens next.

Two kinds of tools are exposed to the LLM:

* **Real tools** — actual side-effecting operations (read file, run shell,
  eval Clojure). Calls are dispatched **inside the worker**; results are fed
  back into the conversation. The chart never sees them.
* **Event tools** — one synthetic tool per event the chart-author declares
  `:allowed-events`. When the LLM calls one, the runner validates the
  arguments against a Malli schema and posts the corresponding chart event
  (with the arguments as event data) onto the parent session's queue. The
  tool's "result" returned to the LLM is just an ack so the turn can continue.

The chart only ever sees the high-level domain events its author exposed; it
never sees `tool_use` blocks for real tools. This separation is the project's
key idea:

* Visibility — every LLM request, response, tool call, transition, and event
  is a JSONL transcript entry. Full replay is possible.
* Safety — the chart-author defines the LLM's vocabulary. The LLM can only
  influence chart progression by calling event-tools the author exposed.
* Reproducibility — chart logic is deterministic; only LLM choices are
  non-deterministic, and those choices are tightly scoped.
* Async by construction — the LLM runs on a worker thread, and each parallel
  region has its own worker. Multiple events per turn (fan-out) is natural.
* Resumability — working memory is checkpointed atomically (write-temp →
  rename) after every event-processing pass. Resume reloads the configuration
  and re-spawns invocations; processors are written to be idempotent on
  re-entry.

The runtime is **Babashka** for the agent process, CLI, and test suite
(`bb test`). The statechart library's `simple` and `testing` namespaces
transitively pull `promesa`, which crashes under SCI, so escapement assembles
the env manually and ships its own bb-friendly `escapement.engine.testing`
harness. See <<known-limitations>>.

The dependency stack is small: `com.fulcrologic/statecharts 1.4.0-RC13`,
`metosin/malli`, `cheshire`, `babashka.process`, `org.babashka/http-client`,
and `com.fulcrologic/guardrails`.

[[quickstart]]
== Quickstart

Clone, set an API key, and run the hello chart. The CLI auto-detects an LLM
backend from any one of `ANTHROPIC_API_KEY`, `ZAI_API_KEY`, `OPENAI_API_KEY`,
or `OPENROUTER_API_KEY` (precedence in that order); no `--backend` flag is
required.

[source,bash]
----
git clone <this-repo>
cd escapement

# Any one of these works; z.ai and OpenRouter are cheap for dev.
export ANTHROPIC_API_KEY=...        # claude-sonnet-4-6 by default
export ZAI_API_KEY=...              # glm-4.6 (Anthropic-compat endpoint)
export OPENAI_API_KEY=...           # gpt-4o-mini default; OPENAI_MODEL overrides
export OPENROUTER_API_KEY=...       # openai/gpt-4o-mini default; OPENROUTER_MODEL overrides

escapement run escapement.examples.hello/agent
----

Or, equivalently, before `bbin install`:

[source,bash]
----
bb -m escapement.cli run escapement.examples.hello/agent
----

==== Multi-backend auto-fallback

When more than one credential is configured, Escapement wires a
multi-dispatch backend AND builds a preference-ordered list of model
ids. That order comes from `:llm/preferences` in `.escapement.edn`
(see <<project-config>>) intersected with the reachable credentials,
falling back to a built-in default order when unset. At conversation
time, if a model errors out (HTTP 429, network blip, parse error, etc.)
the InvocationProcessor marks it `:down` for the rest of the process
and tries the next candidate. `:error.llm.backend` is only fired once
every candidate has failed. Each fallback is logged as
`[llm/model-down] <model> — <message>  next=[...]`, and every
`[llm/req]` / `[llm/resp]` line now shows the model in use, so the
TUI/log stream makes the switch visible.

Two ways for a chart to influence the auto-fallback list:

* `:model "..."` or `:models [...]` on the `:llm-conversation` node —
  explicit pick(s). When set, the auto-list is *not* consulted; only
  your strings are tried (with the same `:down`-marking fallback when
  you give a multi-element list).
* `:needs {...}` on the `:llm-conversation` node — a declarative
  **eligibility gate** over the auto-list (see <<params-fn,the
  `params-fn` map>>). A flat `fact → constraint` map over *any* model
  fact — objective (`:vision?`, `:tool-call?`, `:context-tokens`, …)
  or subjective (`:intelligence` plus any opinion key defined via
  `:llm/ratings`). Useful when a state genuinely requires, say, vision
  plus Sonnet-class reasoning. The gate **filters**; it never reorders
  — ranking is the sole job of `:llm/preferences`. If it excludes every
  reachable model the unfiltered list is used as a best-effort fallback
  and an `:llm/model-policy-empty` warning is emitted to the transcript
  (the lib facade can opt into fail-closed instead; see
  <<hosted-config>>). The legacy `:intelligence N` shorthand still
  works and is folded into the gate as `:needs {:intelligence [:>= N]}`.
  The older nested `:model-policy {...}` form is a deprecated alias.

==== Manual configuration

If you need to override the auto-detected backend (e.g. point at a different
endpoint or use a non-default model), pass the flags explicitly:

[source,bash]
----
escapement run escapement.examples.hello/agent \
   --backend api \
   --api-base-url https://api.z.ai/api/anthropic \
   --api-key-env ZAI_API_KEY \
   --model glm-4.6
----

Expected output:

[source]
----
session         <uuid>
transcript      .escapement/<uuid>/transcript.jsonl
checkpoint-dir  .escapement/<uuid>/checkpoints
final-config    [:run :finished]
----

The `.escapement/<session>/` directory contains:

* `transcript.jsonl` — every LLM request, response, tool call, chart
  transition, and checkpoint write, one JSON object per line.
* `checkpoints/<session>.edn` — atomic working-memory snapshot written after
  every event.

To probe the build/runtime:

[source,bash]
----
escapement info
----

To run the M7 iterative-coding smoke against a tmp directory:

[source,bash]
----
bb bb_test/m7_live_iterate.clj
----

[[core-concepts]]
== Core concepts

The vocabulary used throughout this guide:

Chart::
  A Fulcrologic statechart value. Built with
  `com.fulcrologic.statecharts.chart/statechart`. Composed of `state`,
  `parallel`, `final`, `transition`, `script`, `on-entry`, and `invoke`
  elements from `com.fulcrologic.statecharts.elements`. See the `statechart`
  skill or the library docs for the algorithm; this guide assumes familiarity
  with the basics.

LLM-bound state::
  A compound state whose body contains
  `(invoke {:type :llm-conversation :id ... :params <fn>})`. While the state
  is active, the runtime spawns a worker thread that holds a live LLM
  conversation. When the chart leaves the state, the worker is interrupted
  and the conversation dies. The authoring sugar is
  <<llm-conversation-helper,`h/llm-conversation`>>.

Real tool::
  A tool the LLM may call to act on the world (e.g. `:fs/read`,
  `:shell/run`). Implemented by `escapement.tools.protocol/Tool` and looked
  up in a tool registry. Real-tool calls are dispatched inside the worker;
  results loop back into the conversation. The chart never observes them.

Event tool::
  One synthetic tool per entry in the binding's `:allowed-events`. When the
  LLM calls `event__<name>(<args>)`, the worker validates `<args>` against
  the entry's `:data-schema` and posts a chart event named `<name>` with the
  validated input as event data.

Conversation lifecycle::
  Starts on state entry (with `:initial-user-message` if provided).
  Re-entered idempotently if the chart re-enters the bound state (the old
  worker is interrupted and a new one is spawned). Dies on state exit. See
  <<idioms-gotchas>> for what this implies for resume.

Transcript::
  A JSONL file written by `escapement.transcript`. Single-writer (one daemon
  thread); other threads enqueue events through a `LinkedBlockingQueue`.
  Lines are guaranteed intact and FIFO.

Checkpoint::
  EDN serialization of the chart's working memory, written via temp-file +
  atomic rename after every event-processing pass. See
  `src/escapement/engine/store.clj`.

Resume::
  Re-loading the latest checkpoint and continuing. The runner detects
  `:resume?` plus an existing non-empty configuration and skips `start!`. The
  library re-enters the saved configuration on the next event; invocation
  processors re-spawn workers idempotently.

[[authoring]]
== Authoring a chart, step by step

The four demo charts under `src/escapement/examples/` are arranged from
simplest to most complex. Read them in order — together they cover every
substantive pattern this library supports.

[[hello-walkthrough]]
=== Walkthrough: `hello.clj`

Full source: `src/escapement/examples/hello.clj`.

The chart binds an LLM conversation to a state, asks for a single
`event__done` call, and transitions to a final state that assigns the
greeting to the data model.

The namespace pulls in `chart`, `data-model.operations` (for `ops/assign`),
the standard element wrappers, and this project's authoring helpers:

[source,clojure]
----
(:require
 [com.fulcrologic.statecharts.chart :as chart]
 [com.fulcrologic.statecharts.data-model.operations :as ops]
 [com.fulcrologic.statecharts.elements :refer [state transition final script on-entry]]
 [escapement.chart.helpers :as h])
----

The system prompt is just a string. The LLM is told to call `event__done`
once with a `{"greeting": "..."}` payload:

[source,clojure]
----
(def system-prompt
  (str "When asked, call the `event__done` tool exactly once with `{\"greeting\":\"<a short hello "
       "in any language>\"}`. Keep the greeting under 30 characters. After the tool call, end your turn. "
       "Do not call any other tools."))
----

The chart itself:

[source,clojure]
----
(def agent
  (chart/statechart
   {:initial :run}
   (state {:id :run :initial :greeting}
          (state {:id :greeting}
                 (h/llm-conversation
                  {:id        "hello"
                   :params-fn (fn [_env _data]
                                {:system               system-prompt
                                 :real-tools           []
                                 :allowed-events       [{:event       :done
                                                         :data-schema [:map [:greeting :string]]}]
                                 :initial-user-message "Say hello."})})
                 (transition {:event :done :target :finished}
                             (script {:expr (fn [_env data]
                                              [(ops/assign :greeting
                                                           (get-in data [:_event :data :greeting]))])})))
          (final {:id :finished}))))
----

Notes:

* The outer `:run` state is required because a **top-level** `final` would
  empty the configuration set on entry. The convention throughout this project
  is to wrap the final in a compound parent state so callers can observe
  completion.
* `h/llm-conversation` (see <<llm-conversation-helper>>) expands to
  `(invoke {:type :llm-conversation ...})` with `:autoforward? true` set so
  `tell-llm` works.
* `:params-fn` is `(fn [env data] params-map)`. It is called every time the
  binding starts. It is the chart's chance to compute LLM parameters from
  current data-model state.
* `:allowed-events` declares the event vocabulary. Each entry is a map with
  `:event` (chart event keyword) and `:data-schema` (Malli). The runtime
  synthesizes the Anthropic tool definition (`event__done` here) and
  validates the LLM's tool input against the schema before posting the
  event.
* The `:done` transition is **structural** (it leaves the bound state),
  killing the conversation. The `script` action copies the event data into
  the data model. `get-in data [:_event :data ...]` is the standard pattern
  for reading the current event's payload inside a transition action — the
  library exposes the triggering event under the `:_event` key of the
  data-model snapshot passed to script `:expr`.

=== Three shapes of `:llm-conversation`

A single `:llm-conversation` invocation is just a live worker bound to a
chart state. The shape it takes is set entirely by which event-tools the
chart declares and how it reacts to them. Three common shapes, all
first-class and all built from the same machinery:

Concentrated query::
  A short conversation that decides one transition or produces one
  structured payload. Usually one `:initial-user-message`, zero or one
  event-tools, and the chart transitions out on `:llm.idle` (whose data
  carries the final assistant text). Useful for routing, classification,
  summarization, structured-output extraction, or "ask the model which
  of these branches to take." The conversation typically lives for a
  handful of round-trips and then the chart moves on.

Explore / agent state::
  The LLM is given real tools (file read/edit, shell, search, …) and
  runs autonomously for as many `tool_use → tool_result` rounds as the
  task needs — easily into the hundreds for a large refactor or audit.
  The chart declares a small set of *coarse* event-tools for milestones
  it actually branches on (`:patch-applied`, `:report-ready`,
  `:give-up`) and sits on the state until one fires. The chart never
  sees individual tool calls; that is the point.

Long turn with clarifying questions::
  Same shape as the agent state, plus an event-tool such as
  `event__question` that the LLM can call when it needs input it
  doesn't have. The chart routes that question elsewhere — to another
  `:llm-conversation` that decides how to answer, to a human-input
  node, to a stored FAQ — and posts the answer back into the original
  conversation via <<tell-llm-helper,`h/tell-llm`>>. The autonomous
  worker keeps running with its full context intact; from its point of
  view it asked a question and got an answer.

These are blends of one knob — *what event-tools you declare* — not
different invocation types. A chart can have all three shapes in
different states (or in parallel regions) at the same time. See
<<tokens-and-turns>> for the mechanics that make long runs work
(separate catalog-driven output budget per round-trip, prompt caching
across turns) and the `:max-turns` / `:max-conversation-duration-ms` options
below for the worst-case guards.

=== Worked example: `scan.clj` — fan-out with a real tool

Full source: `src/escapement/examples/scan.clj`.

This chart adds one real tool (`:fs/read`) and demonstrates **fan-out**:
the LLM is expected to fire multiple `:found-bug` events and one
`:scan-complete`. Two ideas worth highlighting:

[source,clojure]
----
:real-tools     [:fs/read]
:allowed-events [{:event       :found-bug
                  :data-schema [:map
                                [:file :string]
                                [:line :int]
                                [:summary :string]]}
                 {:event       :scan-complete
                  :data-schema [:map [:total_findings :int]]}]
----

The chart never sees `:fs/read`. The LLM reads files, decides on findings,
calls `event__found_bug` once per finding, then `event__scan_complete`.

The trick is the internal transition for accumulating findings:

[source,clojure]
----
(transition {:event :found-bug :type :internal}
            (script {:expr (fn [_env data]
                             [(ops/assign :findings
                                          (conj (vec (:findings data))
                                                (-> data :_event :data)))])}))
----

`:type :internal` tells the algorithm to **not leave** the source state.
That matters here because leaving and re-entering `:scanning` would kill the
LLM worker. With an internal transition, the binding stays alive across
arbitrarily many `:found-bug` events. Only the terminal `:scan-complete`
uses a normal (external) transition to `:finished`.

=== Worked example: `parallel_demo.clj` — two LLMs at once

Full source: `src/escapement/examples/parallel_demo.clj`.

Two parallel regions, each with its own `:llm-conversation`. Region A is a
translator; region B is a summarizer. The two workers run concurrently on
different threads; tool-name collisions are impossible because event tool
names encode the event keyword (`event__translated` vs `event__summarized`).

[source,clojure]
----
(parallel {:id :work}
  (state {:id :translator :initial :translating} ...)
  (state {:id :summarizer :initial :summarizing} ...))

;; Both regions reach their per-region final → parallel raises done.state.work.
(transition {:event :done.state.work :target :finished})
----

`done.state.<id>` is raised by the library when all children of a
`parallel` element have reached a final substate. The parent then
transitions to its own final.

=== Worked example: `iterate.clj` — multi-state coding loop

Full source: `src/escapement/examples/iterate.clj`.

The most ambitious demo. One long conversation is bound at the top of
`:work`, exposing four event tools:

[source,clojure]
----
:real-tools      [:fs/read :fs/edit :fs/write]
:allowed-events  [{:event :spec-ready    :data-schema [:map [:summary :string]]}
                  {:event :patch-applied :data-schema [:map [:rationale :string]]}
                  {:event :retry         :data-schema [:map [:reasoning :string]]}
                  {:event :give-up       :data-schema [:map [:reason :string]]}]
----

The chart progresses `:read-spec → :propose-patch → :run-tests → :reflect`
with **all internal transitions** so the LLM's accumulated context survives
the whole loop:

[source,clojure]
----
(state {:id :read-spec}
       (transition {:event :spec-ready :target :propose-patch :type :internal}))

(state {:id :propose-patch}
       (on-entry {}
         (h/tell-llm {:expr (fn [_env data] (user-message-for-propose data))}))
       (transition {:event :patch-applied :target :run-tests :type :internal}
                   (script {:expr (fn [_env data]
                                    [(ops/assign :iterations
                                                 (inc (or (:iterations data) 0)))])})))
----

Two new ideas appear here:

* **Test execution is NOT an LLM tool.** It is a chart-controlled `script`
  action on `:run-tests` entry that dispatches `:shell/run` via the tool
  registry directly and posts `:tests-pass` or `:tests-fail` back to itself.
  This keeps test results out of the LLM's tool-loop and out of the
  conversation context unless the chart decides to surface them.
* **`h/tell-llm`** pushes a fresh user message into the live binding from
  inside the chart (see <<tell-llm-helper>>). Used here on
  `:propose-patch` entry to direct the LLM, and on `:reflect` entry to
  surface the test output on failure.

Read all four files together; they exercise every authoring pattern this
project currently supports.

A larger end-to-end demo lives under `demos/unit_test/` (a port of the
pi `unit_test` extension): seven phase prompts on disk, a parallel
REPL-manager region that supplies an nREPL port to the refine state via
shared data + one coordination event, and `:covers`-sealed test output.
See `demos/unit_test/README.md` for run instructions and architecture.

[[prompts]]
== File-based prompts

For non-trivial agents the inline `(str ...)` style of `hello.clj` and
`iterate.clj` rapidly becomes painful — prompts can be many KiB and they
typically need a few interpolated parameters. The
`escapement.prompts` namespace is the project's lightweight answer:

[source,clojure]
----
(require '[escapement.prompts :as p])

(p/render-file "demos/unit_test/prompts/behaviors.md"
               {:FILE     "src/myapp/core.clj"
                :FUNCTION "do-thing"})
----

Rules:

* Tokens are `{{IDENT}}` where `IDENT` matches `[A-Z][A-Z0-9_]*`.
* The substitution map is keyed by keyword, symbol, or string. Values
  are coerced via `str`.
* Any unresolved token in the template throws `ex-info` listing every
  missing name. Prompts must not ship with literal placeholders.
* No dependencies — `slurp` plus `clojure.string`, bb-safe.

The unit-test demo wires this into a small per-phase template registry
(`demos/unit_test/prompts.clj`) so each chart state's `params-fn` just
calls `(prompts/render-phase :write data)`. That keeps phase prompts
authoring-ergonomic on disk while the chart code stays focused on
control flow.

[[invocation]]
== The `:llm-conversation` invocation

This is the core of the project. The processor is defined in
`src/escapement/invocation/llm_conversation.clj`. Authors do not normally
construct it directly; they use the helpers in
`src/escapement/chart/helpers.clj`.

[[llm-conversation-helper]]
=== `h/llm-conversation`

Defined in `src/escapement/chart/helpers.clj:21`. Expands to an `invoke`
element of type `:llm-conversation` with `:autoforward? true` set.

[source,clojure]
----
(h/llm-conversation
 {:id        "scanner"      ; required; becomes the :invokeid
  :params-fn (fn [env data] ; required; returns the params map below
               { ... })
  :autoforward? true})      ; optional; defaults to true
----

`:autoforward?` controls whether the library hands chart events back to the
processor's `forward-event!`. You almost always want this true (it is what
makes `tell-llm` work).

[[params-fn]]
=== The `params-fn` map

`params-fn` returns a map consumed by the processor. The keys it understands:

`:system`::
  Optional string. The system prompt sent to the LLM.

`:real-tools`::
  Optional selector controlling which real tools this conversation sees.
+
  * **Absent / `nil`** — expose EVERY tool currently in the registry. This
    is the recommended default: the CLI's registry already contains the
    eight built-ins plus anything self-registered by a required namespace
    (see <<custom-tool>>).
  * **Vector or set of keywords** — whitelist. Only the named tools are
    exposed to the LLM. Unknown keywords throw at conversation start.
+
  Tools the LLM never sees are still in the registry and still
  dispatchable from chart-side scripts; they are just absent from the
  Anthropic `tools` array.

`:allowed-events`::
  Optional vector of `{:event <kw> :data-schema <malli> :description <str>}`
  maps. Each becomes a synthetic Anthropic tool named `event__<encoded>`
  with `:input-schema` derived from `:data-schema`.

`:chart-tools`::
  Optional vector pulling tools from *service regions* elsewhere in the
  chart. Each entry is `{:owner <state-id> :as <kw-prefix>?}`. Tools
  declared by the named owner state are added to this conversation's
  palette as ordinary Anthropic tools, named `region__<encoded>` (or
  `region__<as>__<encoded>` when aliased). The palette is **snapshotted
  at conversation start** — tools registered after that point are not
  callable. See <<service-regions>> for the full pattern.

`:initial-user-message`::
  Optional string. If present, the worker starts in `:running` and sends
  this as the first user turn. Otherwise it starts in `:awaiting-user` and
  parks until a `:llm.user-message` event arrives via `tell-llm`.

`:initial-messages`::
  Optional vector of pre-built message maps to seed the conversation
  with (e.g. a multi-block first user message carrying an `:image`, or a
  short prior exchange). When non-empty it takes precedence over
  `:initial-user-message` and the worker starts in `:running`. Use it
  when the opening turn is more than a single plain-text string.

`:model`::
  Optional string passed through to the backend. Examples:
  `"claude-opus-4-7"`, `"claude-sonnet-4-6"`, `"claude-haiku-4-5"`,
  `"glm-4.6"` (when targeting the z.ai compat endpoint). When set,
  Escapement uses *exactly this model* — auto-fallback across other
  configured backends is disabled for this state (your explicit pick
  is honored). If absent, the auto-fallback list kicks in (see
  `:models` and `:intelligence` below). Per-state selection is the
  point: one chart state can drive Opus for hard reasoning, the next
  Sonnet for routine edits, the next Haiku for cheap fan-out.

`:models`::
  Optional ordered vector of model id strings. Tried in order; on a
  backend failure (HTTP 429, network error, etc.) the next candidate
  is tried and the failing one is marked `:down` for the rest of the
  process so later turns and later invocations skip it. As with
  `:model`, an explicit list disables the auto-detected default
  fallback list — only the strings you name are tried.

`:needs`::
  Optional **eligibility gate** over the auto-detected fallback list —
  the ergonomic chart-node surface. Only meaningful when neither
  `:model` nor `:models` is set. It is a **flat** `fact → constraint`
  map (one nesting level); each entry states its own rule by shape:
+
[source,clojure]
----
:needs {:tool-call?        true        ; bare value ⇒ exact equality
        :clojure           [:>= 7]     ; [:>= n]    ⇒ inclusive floor
        :context-tokens    [:>= 200000]
        :max-output-tokens [:<= 64000]} ; [:<= n]   ⇒ inclusive ceiling
----
+
  Only the two comparators `:>=` and `:<=` are accepted (there is
  deliberately no `:>` / `:<` / `:=`); a bare value is exact equality.
  All clauses must hold (logical AND). Empty/absent `:needs` admits
  everything. A malformed entry (unknown operator, not a 2-element
  `[op n]` pair, non-numeric bound) throws an `ExceptionInfo` naming
  the offending key. `:needs` is translated at the invocation boundary
  by `escapement.llm.needs/needs->policy` into the canonical
  `{:require {…} :min {…} :max {…}}` policy the catalog consumes.
+
  Keys range over **one uniform keyspace** mixing two sources (the
  invocation layer never names a specific key, so a brand-new dimension
  is filterable with no code change):
+
  * **Documented objective facts** — the stable, enumerated vocabulary
    published as `escapement.llm.catalog/eligibility-facts`:
+
[cols="1,3",options="header"]
|===
| Key | Meaning
| `:vision?` | accepts image input (boolean)
| `:tool-call?` | supports tool/function calling (boolean)
| `:reasoning?` | reasoning / extended-thinking (boolean)
| `:context-tokens` | input context window, in tokens
| `:max-output-tokens` | per-response output cap, in tokens
| `:company` | vendor / maker string
| `:family` | model family string
| `:knowledge` | knowledge-cutoff string
|===
+
  * **Subjective ratings** — any host-defined key from `:llm/ratings`
    (`:intelligence`, `:clojure`, `:ux`, `:tier`, …). These mix into
    the *same* keyspace; they are deliberately not enumerated (free-form,
    host-owned). With no ratings configured, a subjective clause matches
    nothing.
+
  The gate **filters** the preference-ordered candidate list; it
  **never reorders** — *all* ranking comes from the sorted
  `:llm/preferences`. A model rated `:clojure 7` and one rated
  `:clojure 10` are interchangeable under `[:>= 6]`; preference order
  alone decides which survivor runs. If the gate removes every
  candidate the default is **fail-open** (the unfiltered list is used
  as a best-effort fallback and an `:llm/model-policy-empty` warning,
  carrying the resolved `:policy` and the rejected `:default-models`,
  is emitted to the transcript). The lib facade can opt into
  **fail-closed** via `:config :llm/eligibility-strict? true` — see
  <<hosted-config>>.
+
  The legacy `:intelligence N` key is still accepted on the node and is
  equivalent to `:needs {:intelligence [:>= N]}`.

`:model-policy`::
  **Deprecated alias for `:needs`** (still accepted for one cycle so
  existing charts do not break). It is the canonical *nested* shape —
  `{:require {…} :min {…} :max {…}}` — that `:needs` translates into:
  `:require` ⇔ bare value, `:min` ⇔ `[:>= n]`, `:max` ⇔ `[:<= n]`.
  Prefer `:needs` for new charts; `:model-policy` will be removed in a
  later cycle.

`:max-tokens`::
  **Not a chart param.** The per-turn output cap is resolved automatically
  from the model catalog — it is the selected model's
  `catalog/max-output-tokens` (sourced from models-api.json `limit.output`).
  Setting `:max-tokens` in `params-fn` has no effect; remove it from
  charts. Models the catalog does not know fall back to the api backend's
  wire default (**8192**). This caps generation in ONE assistant HTTP
  response — not the whole conversation, not a tool round-trip. See
  <<tokens-and-turns>> for the full mechanics and how `:thinking` interacts
  with it.

`:stream?`::
  Optional boolean. When `true` AND the backend implements streaming (both
  bundled backend families do: the Anthropic/z.ai api backend and the
  OpenAI/OpenRouter backend), the turn is issued over SSE and
  incremental output is published as `:llm/delta` transcript events
  (`{:type :text-delta|:thinking-delta :text "…" :model … :invokeid …}`)
  while the turn is still in flight — relay these to a UI for live output.
  The final Response and all chart semantics are byte-identical to a
  non-streamed turn. No-op (plain buffered turn) on backends without
  streaming support.

`:resilience`::
  Optional map tuning automatic recovery; on by default. Shape:
  `{:max-retries N :backoff-ms MS}` (defaults `{:max-retries 3
  :backoff-ms 500}`).
+
  *Transient backend failures auto-retry.* A backend throw categorized
  `:rate-limited` / `:overloaded` / `:timeout` / `:transport` is retried
  on the same model up to `:max-retries` times with exponential backoff
  off `:backoff-ms` (honoring an explicit `:retry-after-ms` in the
  throwable's ex-data, e.g. a 429 `Retry-After`) *before* any
  `:models` fallback, and only then surfaces as `:error.llm.<category>`.
  Each attempt emits a `:llm/retry` transcript event. Set
  `:max-retries 0` to disable retry and fail fast.
+
  *Terminal failures never retry.* `:auth` / `:invalid-request` /
  `:context-length` fail fast regardless of `:max-retries`, so a bad key
  or oversized prompt cannot burn quota in a loop.
+
  Note: `:max_tokens` truncation is *not* governed by `:resilience` — it
  is always continued (see <<tokens-and-turns>>); there is intentionally
  no continuation knob.

`:temperature`::
  Optional number in `(0, 1]`. Use values near zero for deterministic
  tool-calling work, higher for creative generation. Don't combine with
  `:thinking` — Anthropic ignores temperature when extended thinking is on.

`:top-p` / `:top-k`::
  Optional sampling parameters passed straight through. Most charts won't
  need them; reach for `:temperature` first.

`:stop-sequences`::
  Optional vector of strings. The model halts as soon as any of them
  appears in its output (the matching sequence is excluded from the
  result). Useful for inline output formats.

`:thinking`::
  Optional map enabling Anthropic's extended-thinking mode for THIS
  state's worker:
+
[source,clojure]
----
{:type :enabled :budget-tokens 4096}
----
+
The model emits one or more `:thinking` (and possibly `:redacted_thinking`)
content blocks before its normal text/tool_use blocks. They are recorded
in the message history so the model can build on them across turns; the
chart never sees them — they pass through transparently. Set
`:budget-tokens` low enough to leave room, within the model's
catalog output cap, for the actual answer (select a model with a large
enough output limit when enabling deep thinking).

`:tool-choice`::
  Optional. Forces the model's hand on tool selection:
+
* `:auto` (Anthropic default) — model decides whether to call a tool.
* `:any` — model MUST call some tool this turn.
* `:none` — model is forbidden from calling tools (text-only).
* `{:type :tool :name "fs_read"}` — model MUST call the named tool.
  Optional `:disable-parallel-tool-use true` forbids parallel calls.

`:metadata`::
  Optional `{:user-id "..."}`. Surfaces in Anthropic's audit/abuse
  tracking. Use a stable, non-PII identifier (e.g. a hash).

`:auto-cache?`::
  Boolean, **default `true`**. When true, any absent
  `:system-cache-control` / `:tools-cache-control` key is filled in
  with `{:type :ephemeral}` (Anthropic's 5-minute cache window —
  cheap; the 1-hour `:ttl :1h` variant costs noticeably more). Set
  `:auto-cache? false` to skip defaulting entirely (no cache markers
  emitted at all). See <<prompt-caching>> for the rationale.

`:system-cache-control` and `:tools-cache-control`::
  Optional cache_control markers. Each is one of:
+
* a marker map like `{:type :ephemeral}` (5-minute TTL — the default)
  or `{:type :ephemeral :ttl :1h}` (1-hour TTL, costs more to write)
* `false` — explicit "don't cache this one"
* absent / `nil` — falls through to the `:auto-cache?` default
  (`{:type :ephemeral}` when auto-cache is on)
+
`:system-cache-control` marks the system prompt; `:tools-cache-control`
stamps the LAST tool def so the prefix-through-end of `tools` is
cached. The biggest wins are in tool-heavy single-state loops (refine
in the unit-test demo is the canonical case). See <<prompt-caching>>
for the full explanation and when caching is wasted effort.

`:on-end-turn-event`::
  Optional chart event keyword fired to the parent when the LLM returns
  `:end_turn`. Defaults to `:llm.idle`. The event data carries
  `{:text "<final assistant text>" :from "<invokeid>"}` so chart-authors
  can route the assistant's output to another invocation (see
  <<multi-agent>>) or to a file via `capture-llm-output`.

`:max-turns`::
  Optional positive integer. Caps the number of LLM round-trips for this
  invocation. Size it for the shape of work the state is doing — a
  concentrated-query state may want a small cap (5–10) while an
  autonomous explore/agent state may legitimately want a large value or
  none at all. When exceeded the worker self-cancels with
  `:error.llm.max-turns {:limit N :turns N}` and dies.

`:max-conversation-duration-ms`::
  Optional positive integer. Wall-clock budget from worker start to a clean
  `:end_turn`. Like `:max-turns`, scale it to the state's shape; an
  autonomous refactor / exploration state may want a long ceiling or
  none. When exceeded fires `:error.llm.timeout
  {:elapsed-ms M :limit-ms N}` and dies. Doesn't replace `:http-timeout-ms`
  on the backend (that bounds individual HTTP calls).

`:conversation/id`::
  Optional opaque token used by the `openai-codex` backend as a prompt
  cache key (passed as `conversation_id` + `session_id` headers). The
  `api` backend ignores it.

NOTE: Error reporting now follows SCXML's `:error.x.y` convention. The
processor fires one of:
+
* `:error.llm.backend` — backend threw an **uncategorized** throwable
  (HTTP / parse / unexpected). This is the back-compat fallback: any
  throw that is not a categorized `escapement.llm.protocol` error still
  collapses here with `:reason :backend`, unchanged. Fired only after
  EVERY candidate model has been tried (see `:models` / `:intelligence`).
  The event data carries `:attempts`, a vector of `{:model :error}`
  entries (oldest first) so the chart can see which models were tried and
  what each one failed with.
* `:error.llm.rate-limited` / `:error.llm.overloaded` /
  `:error.llm.auth` / `:error.llm.invalid-request` /
  `:error.llm.context-length` / `:error.llm.timeout` /
  `:error.llm.transport` — a backend threw a **categorized** failure
  (`escapement.llm.protocol/llm-error`); the consumer maps the category
  (∈ `escapement.llm.protocol/error-categories`) to the matching
  `:error.llm.<category>` event so a chart can branch on the failure
  class — e.g. "rate-limited → wait & resume" vs "invalid-request →
  fail". The bundled Anthropic/z.ai api backend categorizes non-2xx HTTP
  by status (429 → `:rate-limited`, 529/overloaded → `:overloaded`,
  401/403 → `:auth`, 400/422 → `:invalid-request` or `:context-length`,
  timeouts → `:timeout`, connection/IO failures → `:transport`) and SSE
  `error` events as `:overloaded`/`:transport`. As with
  `:error.llm.backend`, these fire only after every candidate model has
  been exhausted and carry the same `:attempts` data. (`:error.llm.timeout`
  is shared: it also fires when `:max-conversation-duration-ms` is
  exceeded — see above.)
* `:error.llm.tool-validation` — tool input failed schema after one retry.
* `:error.llm.unexpected-stop` — a `:stop_sequence` / `:pause_turn` /
  `:refusal` stop reason, or a `:max_tokens` truncation that could not be
  continued because the continuation made *no forward progress* (a stuck
  model); that case carries `:detail :no-forward-progress`. A normal
  `:max_tokens` truncation does **not** fire this — it is continued
  transparently (see <<tokens-and-turns>>).
* `:error.llm.max-turns` — `:max-turns` budget exceeded.
* `:error.llm.worker-exception` — uncaught throwable in the worker.
+
Every `:error.llm.*` event (and the `:llm/error` / `:llm/model-down`
transcript events) carries an additive `:category` key: the matched
category keyword for a categorized failure, or `nil` when uncategorized
(so existing `:error.llm.backend` consumers are unaffected). Chart-authors
catch the whole family with `(transition {:event :error.llm.* :target
:recover})` or pin to a specific cause/category. The old
`:on-error-event` option has been removed; the canonical event is always
fired.
+
Recovery happens *before* these fire. A transient category
(`:rate-limited` / `:overloaded` / `:timeout` / `:transport`) is
auto-retried with backoff per the `:resilience` param (see
<<params-fn>>), so `:error.llm.rate-limited` and friends now fire
only after retries are exhausted; terminal categories (`:auth` /
`:invalid-request` / `:context-length`) still fire immediately.

[[tell-llm-helper]]
=== `h/tell-llm`

Defined in `src/escapement/chart/helpers.clj:39`. Emits a `script` that
posts a `:llm.user-message` event to the current session:

[source,clojure]
----
(on-entry {}
  (h/tell-llm {:expr (fn [env data] (str "Tests failed. Output:\n" (:last-test-output data)))}))
----

With `:autoforward? true` on the binding (the default), the library hands
the event to the processor's `forward-event!`, which converts it into a new
user message in the live conversation. The worker wakes up, appends the
message, and runs another turn.

IMPORTANT: `tell-llm` only works from **inside** the state that owns the
binding (or a descendant). Outside, there is no live invocation to forward
to, and the event is silently dropped.

When multiple `:llm-conversation` invocations are live concurrently (typical
in parallel regions / multi-agent charts), `tell-llm` broadcasts to ALL of
them. Use `h/tell-other-llm` (see <<multi-agent>>) when you want to target a
specific conversation by its `invokeid`.

=== Internal vs external transitions

If a transition's `:target` leaves the state that owns the binding (or
omits `:type :internal` and the target is the same state), the library
exits and re-enters the state, killing and re-spawning the worker. This is
sometimes what you want (each iteration is a fresh conversation) and
sometimes not (you want to keep the LLM's accumulated context).

* `scan.clj` uses `:type :internal` on `:found-bug` so the binding survives
  multiple findings.
* `iterate.clj` uses `:type :internal` throughout `:work` so one
  conversation drives the whole loop.

=== Bad tool-use

The processor validates every real-tool and event-tool input against its
schema. On failure, the LLM gets a corrective `tool_result` with
`is_error: true` and one retry. A second failure for the same tool-use id
fires `:error.llm.tool-validation` to the parent and the worker exits. See
`handle-tool-use-block` in
`src/escapement/invocation/llm_conversation.clj`.

=== Event-tool name encoding

The LLM-facing name for event `:foo-bar` is `event__foo_bar`. Qualified
keywords are flattened: `:my.ns/foo-bar` becomes `event__my_ns_foo_bar`.
Anthropic enforces alphanum/underscore in tool names, so any other character
in the keyword is replaced by `_`. See `kw->anthropic-name` in
`src/escapement/invocation/llm_conversation.clj:41`.

[[prompt-caching]]
=== Prompt caching and the conversation lifecycle

This is one of the more impactful knobs in the `params-fn` map and it is
not obvious. Read the lifecycle paragraph first, then the caching
recipe.

==== Conversation lifecycle is state lifecycle

Every `:llm-conversation` invocation owns a worker thread, a
`messages-atom`, and a `user-msg-queue`. They are all created when the
chart enters the state that hosts the invocation and torn down when the
chart leaves it. **A fresh state means a fresh conversation, starting
from the system prompt with an empty message history.** This is the
"escapement" principle: the chart drives lifecycle; the model never
chooses when to forget.

Practical consequences:

* The accumulated message history inside one state grows monotonically.
  An assistant `tool_use` response, the dispatched `tool_result`, the
  next assistant turn, etc. all stack up on `messages-atom`. The
  state's `:on-end-turn-event` parks the worker; another
  `tell-llm`/`:llm.user-message` resumes it with the history intact.
* Crossing a state boundary discards that history. The next state's
  worker starts cold.
* Parallel regions get independent conversations — no shared history.

==== Where Anthropic caching helps (and where it doesn't)

Anthropic prompt-caching reuses the *prefix* of a request when its
content matches a recent prior request. Cache hits return the cached
tokens at 0.1× the normal input price; cache writes cost 1.25×. The
prefix is everything UP TO the last `cache_control` marker — typically
the system prompt and the tool definitions.

* **Within a state**: a tool-heavy loop (refine in the unit-test demo
  is ~25 round-trips against a 13 KB system prompt and 8 tools) is the
  prime caching target. The system + tools prefix is identical on every
  HTTP call; only the growing tail of tool_result/text differs. Marking
  `system` and the tail-end of `tools` with `cache_control` makes every
  call after the first read those prefix tokens at 10% price.
* **Across states**: the cache window is 5 minutes (`{:type :ephemeral}`
  default) or 1 hour with the Anthropic extended-cache-ttl beta. So
  cache CAN technically survive a state transition if the next state's
  conversation happens to share a long prefix. In practice
  Escapement's phases use *different* system prompts on purpose, so
  cross-state hits are rare.

==== Defaults

**Caching is on by default.** An `:llm-conversation` state with no
cache keys set behaves as if you had written

[source,clojure]
----
{:system-cache-control {:type :ephemeral}
 :tools-cache-control  {:type :ephemeral}}
----

i.e. ephemeral (5-minute TTL) markers on both the system prompt and the
tail of the tool defs. The reasoning: Anthropic silently ignores
`cache_control` on prompts below the minimum cacheable size (1024
tokens for Sonnet/Opus, 2048 for Haiku), so the default is free for
small prompts and a clear win for any multi-turn state with a
substantial prefix. We default to the 5-minute TTL because the 1-hour
TTL (`:ttl :1h`) costs noticeably more to *write* — only worth it for
prefixes that the next state is likely to reuse.

To opt out:

* `:auto-cache? false` — skip defaulting entirely; no cache markers
  emitted (use this for guaranteed single-turn states with a 1K+ prompt
  you truly never reuse).
* `:system-cache-control false` or `:tools-cache-control false` —
  disable just one marker while letting the other auto-default.
* An explicit map for either key always wins (e.g.
  `:system-cache-control {:type :ephemeral :ttl :1h}` when you know
  the next state will reuse this same system prompt within the hour).

==== Overriding for the 1-hour TTL

Set the explicit map:

[source,clojure]
----
{:system               (slurp "prompts/refine.md")        ; ~13 KB
 :system-cache-control {:type :ephemeral :ttl :1h}        ; longer-lived
 :tools-cache-control  {:type :ephemeral :ttl :1h}
 :real-tools           [:fs/read :fs/edit :shell/run]
 :allowed-events       [...]
 :initial-user-message "..."}
----

`tools-cache-control` stamps the *last* tool def because Anthropic
caches everything up through the marker — stamping the tail therefore
covers every tool. You normally want either both flags set to the same
value or neither: caching system but not tools means the tools section
ends the cache prefix, so the system prefix is the only thing reused.

==== When the cache wins are real

* Long system prompts (4 KB+).
* Many tool round-trips inside one state.
* Stable tool defs.
* Long-running refine loops, iterative coding agents, RAG-prompt agents.

==== When caching is wasted effort

* States that fire one turn and exit — the cache-write surcharge runs
  but no second turn ever uses the cached prefix.
* Charts whose system prompt is templated with per-turn data (the
  prefix differs every time, so cache always misses).

==== Verifying the cache

The Anthropic response includes `cache_creation_input_tokens` and
`cache_read_input_tokens` in `usage`. Our `Response.usage` schema
already carries both. Look at them in the transcript:

[source,bash]
----
jq -r 'select(.event == "llm/response") |
       (.data.usage // {}) | [.cache_creation_input_tokens,
                              .cache_read_input_tokens] | @tsv' transcript.jsonl
----

First request shows a creation count, subsequent ones show reads.

[[context-tracking]]
=== Context-window tracking

Anthropic never returns the context-window size on a response. We
resolve it from the model catalog (`escapement.llm.catalog`) and use it
to enrich the transcript so chart authors and reviewers can see, at any
point in a run, how much of the model's context the running
conversation has consumed.

==== `escapement.llm.catalog`

The catalog assembles model facts from three layers: objective facts
from a bundled models.dev data dump (loaded via
`escapement.llm.catalog-source`), a tiny local fact overlay for ids the
dump doesn't carry yet, and a subjective `:llm/ratings` overlay from
`.escapement.edn` (see <<project-config>>).

[source,clojure]
----
(require '[escapement.llm.catalog :as cat])

(cat/info "claude-opus-4-7")
;; => {:context-tokens 200000 :max-output-tokens 64000 :vision? true
;;     :tool-call? true ...}  ; OBJECTIVE only — no ratings, no config

(cat/context-window "claude-sonnet-4-6")          ; => 200000
(cat/max-output-tokens "claude-haiku-4-5")        ; => 32000
(cat/vision? "claude-opus-4-7")                   ; => true
(cat/pricing :anthropic "claude-opus-4-7")        ; => {:input .. :output ..}
(cat/pricing "claude-opus-4-7")                   ; cheapest metered list price
(cat/satisfies-policy? "claude-opus-4-7"
                       {:min {:intelligence 8}}
                       {"claude-opus-4-7" {:intelligence 9}}) ; => true
----

`cat/info` and the objective accessors are **opinion-free**: the
subjective ratings overlay is no longer merged into `info` and the
catalog carries no process-global ratings cache. Intelligence is just
one key in that overlay, filtered like any other fact via
`satisfies-policy?` — whose 3-arity takes the ratings table as an
explicit argument (an empty `{}` ⇒ a subjective clause matches
nothing). The 2-arity is a backward-compatible CLI seam that resolves
ratings from `.escapement.edn` per call. `cat/eligibility-facts` is
the stable, published vocabulary of objective gate keys (`:vision?`,
`:tool-call?`, `:reasoning?`, `:context-tokens`, `:max-output-tokens`,
`:company`, `:family`, `:knowledge`); this backs the `:needs` node
option (the deprecated `:model-policy` is its canonical nested alias).
Subscription providers (`:z-ai-plan`, `:ollama`, `:openai-codex`)
report zero marginal per-token cost.

Resolution is exact-match-first, then longest-prefix. Dated ids like
`claude-opus-4-7-20260101` resolve to the `claude-opus-4-7` family
entry. Objective facts update by regenerating the models.dev dump;
ids the dump lacks go in the small `local-models`/`local-providers`
overlay in `escapement.llm.catalog`.

==== Transcript enrichment

The worker stamps every `:llm/response` event with:

* `:usage`  — the Anthropic `usage` block (`:input-tokens`,
  `:output-tokens`, `:cache-creation-input-tokens`,
  `:cache-read-input-tokens` when present)
* `:model` — the model id reported by the API (or our request model)
* `:context-window` — the lookup-table value for that model, when
  known
* `:context-used-frac` — `:input-tokens` / `:context-window`, rounded
  to three decimals; absent when we can't look up the model

Additionally, whenever `:context-used-frac` ≥ 0.8 a separate
`:llm/context-warning` event is emitted into the transcript with the
same data. Charts can ignore it (the worker keeps running) or chain a
transition on it via the parent session's autoforward path if they
want to do something proactive (compact history, swap to a smaller
model for the next state, etc.).

==== Plotting usage from a transcript

[source,bash]
----
# Per-response: input tokens, output tokens, fraction of context used.
jq -r 'select(.event == "llm/response") |
       [(.data.usage["input-tokens"]   // 0),
        (.data.usage["output-tokens"]  // 0),
        (.data["context-used-frac"]    // 0)] | @tsv' transcript.jsonl
----

Pipe through `column -t` for tidy display, or into any plotting tool
for a per-turn growth curve.

==== Pre-flight token counting

Anthropic ships a separate Messages `count_tokens` endpoint for
predicting an input size before sending. Escapement does not call it
today; if you need a hard pre-flight gate, the simplest approach is to
add a chart-side script that calls `count_tokens` via `:shell/run` and
either transitions to a compaction state or trims `messages-atom`
before the request goes out.

[[tokens-and-turns]]
=== Tokens and turns — what the output cap actually limits

This trips people up the first time. The short version:

* The per-turn output cap (the `max_tokens` sent on the wire) is
  **catalog-driven**: it is the selected model's
  `catalog/max-output-tokens`, resolved by the invocation layer — charts
  do not set it. It caps generation in **one HTTP response** from the
  model. It is not a session budget, not a per-tool budget, not a
  per-chart budget. It only constrains "how long can the assistant's
  single message be."
* A tool round-trip is a **separate HTTP call** with a **separate fresh
  budget**. The worker emits one request, the model returns
  `stop_reason=tool_use` with some text + tool_use blocks (≤ `:max-tokens`
  for that response), the worker dispatches tools, appends `tool_result`
  to the message history, and POSTs the next request. The next response
  gets its own clean `:max-tokens` allocation.
* So a long, tool-heavy conversation can produce far more total tokens
  than the per-turn cap over many turns. The only failure mode the cap
  actually causes is **truncation inside a single response** — for
  example, when a model's catalog output ceiling is small relative to a
  whole-file write the chart asks for in one shot. The fix is to select a
  model with a larger output limit, not to tweak a param.

==== Stop reasons

When a response completes, Anthropic returns `stop_reason`:

* `:end_turn` — the model is done with this turn. The worker fires
  `:on-end-turn-event` (default `:llm.idle`) and parks in
  `:awaiting-user`. The chart can transition on the event if it cares
  about turn boundaries.
* `:tool_use` — the response contains at least one tool_use block. The
  worker dispatches the tools, appends results, and immediately POSTs
  the next request. Chart-side scripts don't see this.
* `:max_tokens` — the API truncated the response at the model's catalog
  output cap mid-message. This is **not** an error and the chart never
  sees it: the worker keeps the partial content as prefill and continues
  the turn (emitting a `:llm/continuation` transcript event per segment)
  until a genuine terminal stop, then stitches the segments into one
  coherent Response. No tool runs and no chart event fires until the
  message is actually complete. Continuation is unbounded by design; the
  only guard is forward progress — a continuation that adds nothing (a
  stuck model) aborts with `:error.llm.unexpected-stop` carrying
  `:detail :no-forward-progress`. See <<continuation>> below.
* `:stop_sequence`, `:pause_turn`, `:refusal` — fired as
  `:error.llm.unexpected-stop` with `:stop-reason` set to the specific
  cause. Charts that opt into `:stop-sequences` (or care about refusals)
  wire a transition on `:error.llm.unexpected-stop` and inspect
  `:_event :data :stop-reason`.

==== Where the cap comes from

The cap is the selected model's `catalog/max-output-tokens`
(models-api.json `limit.output`), resolved per turn by the invocation
layer — see `escapement.llm.catalog`. Modern Claude 4 models expose a
large ceiling (64K+), so most agent turns (short reasoning + a tool call
+ a short summary) never truncate. Models the catalog does not know fall
back to the api backend's wire default of **8192**.

To give a state more output room, **select a model with a larger output
limit** (via `:model`, `:needs`, or `:llm/preferences`) — there is
no per-state cap param to raise. If a state needs whole-file authoring or
long markdown analysis, pick a high-output model for it. With extended
thinking enabled, the resolved cap must accommodate BOTH the thinking
blocks and the visible answer; choose a model whose output limit
comfortably exceeds `:thinking`'s `:budget-tokens`.

==== Cost note

Anthropic bills per token actually generated, not per output-cap
ceiling. A large catalog cap doesn't cost more on its own — it just gives
the model permission to produce more. Real cost driver is the number of
tokens in the request (your accumulated message history and system
prompt). Use `cache_control` markers on `system` and stable message
prefixes to drive that down; see `escapement.llm.cache` and the
`:system-cache-control` / `:cache-control` keys in the type schemas.

[[continuation]]
==== Continuation is automatic

`stop_reason="max_tokens"` is handled by the worker, not the chart: the
partial assistant content becomes prefill for an immediate continuation
request, repeated until a real terminal stop, then the segments are
stitched (text merged across the truncation boundary, usage summed) into
a single Response that the rest of the pipeline — tool dispatch, event
firing, `:on-end-turn-event` — sees as one ordinary turn. Nothing acts on
a half-finished message.

This is intentionally **unbounded** — it is just "finish reading the
message" — and there is no continuation knob (it is not part of
`:resilience`). The sole stop condition besides a terminal
`stop_reason` is *no forward progress*: if a continuation segment adds no
new content, the worker stops and fires `:error.llm.unexpected-stop`
(`:detail :no-forward-progress`) rather than loop and drain quota. Each
continuation emits a `:llm/continuation` transcript event
(`{:segment N :blocks K :usage {…}}`) for observability.

[[web-tools]]
== Web tools: `:web/search` and `:web/fetch`

Two built-in tools give the LLM first-class web access without dragging full
HTML into the context window. `:web/fetch` is always registered in
`default-registry`; `:web/search` is registered **only when `GEMINI_API_KEY`
is set in the environment at namespace-load time**, so a chart running
without a key never advertises a search tool the LLM would only discover by
calling it and failing. Opt in explicitly via `:real-tools [:web/search
:web/fetch]` when you whitelist.

NOTE: The `:web/search` record still defends itself with a
`"GEMINI_API_KEY not set"` error result if someone constructs and registers
it manually after the namespace has loaded — but the recommended path is to
set the env var before the bb process starts.

=== `:web/search`

Google Search grounding via the Gemini API. Returns up to `max-results`
(default 5, max 10) results as an EDN vector of `{:title :url :snippet}`.

Input schema::
+
[source,clojure]
----
{:query       "string, required"
 :max-results "int 1..10, optional, default 5"}
----

Configuration::
* `GEMINI_API_KEY` — required. Get one at https://aistudio.google.com/apikey.
  If missing, the tool returns `{:is-error true :result "GEMINI_API_KEY not set"}`
  — it never throws.
* `GEMINI_SEARCH_MODEL` — optional model override. Default `gemini-2.5-flash`
  (grounding-eligible, free tier).

Result shape (example)::
+
[source,clojure]
----
[{:title "Clojure Guides"
  :url   "https://clojure.org/guides"
  :snippet "Clojure is great for data."}
 ...]
----

=== `:web/fetch`

HTTP `GET` a URL, streaming the body to a temp file at
`${java.io.tmpdir}/escapement-fetch/<uuid><ext>`. The result is small EDN
metadata plus a short raw preview — the **full body lives on disk**, not in
the LLM's context.

Input schema::
+
[source,clojure]
----
{:url        "string, required"
 :max-bytes  "int 1024..50_000_000, optional, default 5_000_000"
 :timeout-ms "int 100..120_000, optional, default 30_000"}
----

Result map::
+
[source,clojure]
----
{:url          "https://..."
 :final-url    "https://..."         ; after redirects
 :status       200
 :content-type "text/html; charset=utf-8"
 :bytes        412334
 :saved-to     "/tmp/escapement-fetch/abc.html"
 :title        "..."                 ; nil unless HTML
 :preview      "first ~500 chars of body, raw"
 :truncated    false}
----

`:is-error` is true only for network failure, timeout, or non-2xx status. A
body that exceeds `:max-bytes` is **not** an error — it is truncated on
disk and `:truncated true` is set in the result.

=== Recipe: search → fetch → read slices off disk

The intended flow keeps context small:

. `:web/search` returns a few snippets + URLs. Most questions are answered here.
. When a snippet isn't enough, `:web/fetch` saves the chosen URL to disk and
  returns metadata + a tiny preview.
. The LLM then composes existing tools to read only what it needs:
+
[source,clojure]
----
;; grep for the section you care about
{:tool :fs/grep   :pattern "deprecation"   :path "/tmp/escapement-fetch/abc.html"
                  :output-mode "content"   :context 3}

;; read a numbered window of the file
{:tool :fs/read   :path "/tmp/escapement-fetch/abc.html"
                  :offset 1200 :limit 80}

;; convert HTML to clean text via shell if pandoc/html2text is available
{:tool :shell/run :command "pandoc -f html -t plain /tmp/escapement-fetch/abc.html | head -200"}
----

Sandboxing the fetch (Docker, sandbox-exec, firejail) is an operator concern
— the tool itself does no isolation.

[[human-interaction]]
== Human interaction and the TUI

A chart can ask the human for input via the `:human-input` invocation. The
chart-author declares what to ask (free text, single-select pick, etc.); a
pluggable `HumanRenderer` decides how. Production wiring uses the
persistent TUI; tests inject a `StubRenderer` that returns scripted
answers.

=== The `:human-input` invocation

Defined in `src/escapement/invocation/human_input.clj`. Spawned on state
entry; posts `:human.answer {:answer <value>}` to the parent session when
the user responds, then dies.

Authoring sugar lives in `escapement.chart.helpers`:

[source,clojure]
----
(state {:id :ask-name}
  (h/human-input
    {:id "ask"
     :params-fn (fn [_env _data]
                  {:kind          :text
                   :prompt        "What's your name?"
                   :answer-schema [:string {:min 1}]})})
  (transition {:event :human.answer :target :greet}
              (script {:expr (fn [_ d]
                               [(ops/assign :name
                                            (get-in d [:_event :data :answer]))])})))
----

Supported `:kind` values:

* `:text` — free-text line. Returns a string.
* `:select` — single pick from `:options [{:label … :value …}]`. Returns
  the chosen `:value`.
* `:multi-select` — same shape, returns a vector of `:value`s.
* `:confirm` — y/n with `:default`. Returns boolean.
* `:progress` — non-blocking progress indicator (driven by forwarded
  `:human.progress` events; v1 just no-ops to `:answer :done`).
* `:custom` — call `(:render params)` with `[env data]` and return its value.

Events the chart receives:

* `:human.answer {:answer <value>}` on success.
* `:human.cancelled {}` on user-cancel (Esc on a modal).
* `:error.human.invalid-answer {:errors … :answer …}` when an
  `:answer-schema` rejects the user's input.
* `:error.human.worker-exception {:message …}` on a renderer throwable.

Catch error families with `(transition {:event :error.human.* :target
:recover})`.

=== `with-llm-questions` — LLM-asks-human pattern

For the common case where you want an LLM to be able to consult the human
mid-conversation (e.g. design decisions, free-text clarifications), the
`(h/with-llm-questions {...})` helper produces a compound state bundling:

* an `llm-conversation` invocation on the bubble's parent state (so the
  conversation survives the human-input detour);
* a `:converse` child state where the user's `:exit-transitions` fire;
* two ask states (`:ask-choice`, `:ask-text`) that pop the corresponding
  `human-input` modal;
* automatic `tell-llm` of the human's answer back to the live LLM,
  prefixed with `"User chose: "` or `"User said: "`.

Two event-tools are injected into the LLM's `:allowed-events`:

* `event__question_ask_choice {:question :string :options [...]}` —
  prompts a `:select` modal.
* `event__question_ask_text {:question :string}` — prompts a `:text` modal.

[source,clojure]
----
(state {:id :run :initial :work}
  (h/with-llm-questions
    {:id        :work
     :params-fn (fn [_ _]
                  {:system "..."
                   :real-tools [:fs/read :fs/write]
                   :initial-user-message "go"})
     :exit-transitions
     [(transition {:event :done :target :finished})]})
  (final {:id :finished}))
----

Requires an interactive chart (see <<interactive-marker>>) — without a
`HumanRenderer` the ask states stall.

[[interactive-marker]]
=== Interactive chart marker

Chart authors declare a chart as interactive via Clojure var metadata:

[source,clojure]
----
(def ^{:interactive? true} agent (chart/statechart …))
----

The CLI reads this on `load-chart-with-meta` and:

* Refuses to start an interactive chart without a TTY, unless `--no-tui`
  was passed (in which case the stdin fallback renderer is used).
* Enables the persistent TUI by default when a TTY is available.
* Wires up `escapement.tui/->renderer` as the `HumanRenderer`, so modals
  pop in the TUI's bottom region.

Non-interactive charts still get a stdin renderer for any `:human-input`
states they happen to invoke (fail-soft default), but the TUI itself stays
off unless `--debug` is passed (which forces it on).

=== The TUI

`src/escapement/tui.clj`. JLine-backed persistent display, on a single
input thread, with a modal-state machine and an in-memory line buffer.
Layout:

----
┌──────────────────────────────────────────────────────────────┐
│ escapement · <chart-sym> · <session-short>                  │
├──────────────────────────────────────────────────────────────┤
│ states: [:run :ask-name]                                     │  ← live config
│ [runner] started …                                           │
│ [llm/req] n-messages=3                                       │
│ [llm/resp] stop=tool_use tokens=in:100/out:17                │
│ [tool] name=event__done input={greeting "Hola!"}             │
│ [chart] event=:done config=[:run :finished]                  │
├──────────────────────────────────────────────────────────────┤
│ ▸ What's your name? alice                                    │  ← modal
└──────────────────────────────────────────────────────────────┘
 Esc=interrupt   Ctrl-C=quit   PgUp/PgDn=scroll
----

Wiring:

* Status line shows the current chart configuration. Driven by
  `:runner/start-config` and `:runner/event-processed` transcript events.
* Scrollback buffer holds the last ~2000 transcript lines (PgUp/PgDn to
  navigate, Home/End to jump). Consecutive duplicate lines collapse into
  `… (xN)`. `:runner/tick`, `:runner/quiescent`, and `:checkpoint/written`
  are suppressed from scrollback (still in JSONL).
* `Esc` (when no modal is open) posts `:ui.interrupt` to the chart's
  session — the chart decides what to do with it (e.g. transition to a
  `:cancelled` state). With a modal open, `Esc` cancels just the modal.
* `Ctrl-C` posts `:ui.quit` and tears down the TUI.

Atomic frames are used when the terminal advertises Mode 2026
(Synchronized Output) — detected at startup via DECRQM. iTerm2 (recent),
kitty, wezterm, foot, ghostty, and contour qualify; Apple Terminal does
not and falls back to per-frame writes (still flicker-light, just not
guaranteed atomic). On exit the alt-screen buffer is left, restoring your
shell scrollback exactly as it was before.

[[viz]]
=== Live chart visualization (`v`)

Press `v` in the TUI (works in both normal and `--debug` runs) to start
a tiny embedded HTTP server that renders the chart to SVG **once** via
the `d2` binary, then streams every configuration change to your browser
over Server-Sent Events. The browser only rewrites a single `<style>`
block keyed on CSS classes — the SVG layout never re-runs, so transitions
recolor states and the most-recently-fired edge **without** shuffling the
diagram.

* Each shape carries `class="state-<id>"` and each transition carries
  `class="edge-<id>"`. The page targets them via
  `[class~="state-..."]` attribute selectors, so any state-id encoding
  works (dots, slashes, namespaced keywords).
* First `v` press: the server binds on `127.0.0.1:0`, writes
  `<session-dir>/chart.d2` and `chart.svg`, logs the live URL to the
  scrollback, and (optionally — see `:viewers "url"` below) launches your
  configured browser. Subsequent `v` presses just re-log the URL.
* In `--debug` mode the active state lights up exactly when you step
  (`s`) or continue (`c`); the just-fired transition flashes red on
  every step. No special config is needed — debug-paced transitions
  flow through the same path normal-mode transitions do.
* The page header has zoom controls (`−` / `100%` / `+` / `Fit`),
  responds to `⌘+` / `⌘−` / `⌘0` (or `Ctrl` on non-Mac), and `⌘-scroll`
  zooms around the cursor. Plain scroll-wheel pans.
* The server shuts down with the TUI; SSE clients reconnect
  automatically on browser reload while the run is live.

Requires the `d2` binary on `$PATH` (or pinned via `:d2 :command`); on
failure, the scrollback explains and the `chart.d2` source is left on
disk so you can render it manually.

[[multi-agent]]
== Multi-agent / team patterns

Multiple `:llm-conversation` invocations can run concurrently (typically
under parallel regions, or as siblings of one parent state). The library
provides three primitives for routing between them.

=== `:target` routing on `:llm.user-message`

`tell-llm` posts a `:llm.user-message` to the chart's session; with
autoforward enabled, EVERY live `:llm-conversation` invocation's
`forward-event!` receives it. With a `:target <invokeid>` in the event
data, only the matching invocation accepts. Comparison normalizes
keyword and string invokeids transparently via
`escapement.invocation.llm-conversation/->id-str`, so `:id :researcher`
and `:id "researcher"` are interchangeable.

=== `h/tell-other-llm`

Sugar for the targeted case:

[source,clojure]
----
(h/tell-other-llm
  {:target "advisor"                  ; or a fn (fn [env data] invokeid)
   :expr   (fn [env data]
             (str "Lead's plan:\n" (:plan data) "\n\nDoes this hold up?"))})
----

Use this when the chart-author knows statically which conversation
receives the message. Plain `tell-llm` continues to broadcast.

=== `:on-end-turn-event` payload

Every `:end_turn` now fires the configured `:on-end-turn-event` (default
`:llm.idle`) with `{:text "<final assistant text>" :from "<invokeid>"}`
in the data. That's the wire for routing one LLM's output to another:
catch the event, inspect `:from`, format `:text` into a follow-up prompt,
`tell-other-llm` it elsewhere.

=== File-backed artifact helpers

For agent pipelines that produce text artifacts to be embedded in later
prompts, three helpers in `escapement.chart.helpers` write to and read
from `<session-dir>/artifacts/<name>`:

`(h/capture-llm-output)` / `(h/capture-llm-output {:as "x.md"})`::
  Returns a script. Used in a transition reacting to `:llm.idle`. Writes
  `:_event :data :text` to `<session-dir>/artifacts/<name>` atomically
  (temp + rename). Default `:as` is the producing invokeid (`:from`).
  Logs `:artifact/captured {:name N :bytes B}` to the transcript.

`(h/render-template tmpl env)` / `(h/render-template tmpl env extras)`::
  Pure-ish substitution. Mustache-light `{{name}}` tokens are resolved
  against `<session-dir>/artifacts/<name>`. `{{output}}` is reserved for
  in-flight text passed via `extras` (used by `forward-llm-output`).
  **Throws** `ex-info {:reason :missing-artifact ...}` on any unresolved
  token — fail-fast so a typoed prompt doesn't ship malformed text to the
  LLM.

`(h/forward-llm-output {:to :template :as :capture?})`::
  Capture + format + targeted `tell-other-llm` in one step. Writes a file
  (unless `:capture? false`), renders the template with `{{output}}`
  bound to the just-arrived text, then sends a `:llm.user-message`
  targeted at `:to`.

[source,clojure]
----
;; Five-state agent pipeline (researcher → writer → editor)
(state {:id :researching}
  (h/llm-conversation
    {:id "researcher"
     :params-fn (fn [_ _] {:initial-user-message "Research X"})})
  (transition {:event :llm.idle :target :writing}
    (h/capture-llm-output)))                ; → artifacts/researcher

(state {:id :writing}
  (h/llm-conversation
    {:id "writer"
     :params-fn (fn [env _]
                  {:initial-user-message
                   (h/render-template
                    "Research:\n\n{{researcher}}\n\nWrite a draft."
                    env)})})
  (transition {:event :llm.idle :target :editing}
    (h/capture-llm-output)))                ; → artifacts/writer

(state {:id :editing}
  (h/llm-conversation
    {:id "editor"
     :params-fn (fn [env _]
                  {:initial-user-message
                   (h/render-template
                    "Draft:\n\n{{writer}}\n\nPolish for clarity."
                    env)})})
  (transition {:event :llm.idle :target :done}
    (h/capture-llm-output)))                ; → artifacts/editor
----

Latest write wins. Keep history by picking versioned filenames
(`(str "draft-" iteration ".md")`).

[[service-regions]]
== Service regions: subcharts as tools

The multi-agent patterns above route _messages_ between LLM conversations.
Sometimes you want the opposite: one conversation calls into another part
of the chart as if it were an ordinary tool, gets a synchronous-looking
reply, and continues. The callee is a **service region** — a chart region
that owns stateful resources (a REPL, a cached connection, an indexer) and
declares which of its states handle which tool keywords.

The chart's event bus is the wire. The framework is a thin layer over it:
`escapement.chart.service` (≈3 public fns) plus one new
`:llm-conversation` param (`:chart-tools`).

=== The whole pattern in one chart

[source,clojure]
----
(require '[escapement.chart.service :as service]
         '[escapement.chart.helpers :as h])

(state {:id :run :initial :work}
  (parallel {:id :work}

    ;; --- the service region -----------------------------------------------
    (state {:id :repl-A :initial :idle}
      (on-entry {} (service/register-tool!
                     {:tool         :repl/eval
                      :description  "Evaluate a Clojure form."
                      :input-schema [:map [:expr :string]]}))
      (on-exit  {} (service/unregister-tool! :repl/eval))

      (state {:id :idle}
        ;; A handler that runs while we're in :idle.
        (h/handle-tool :repl/eval
          (fn [_env _req] {:result "not running" :is-error true}))))

    ;; --- the consumer conversation ----------------------------------------
    (state {:id :consumer :initial :running}
      (state {:id :running}
        (h/llm-conversation
          {:id        "coder"
           :params-fn (fn [_ _]
                        {:initial-user-message "evaluate (+ 1 2)"
                         :chart-tools          [{:owner :repl-A}]})})
        (transition {:event :llm.idle :target :done}))
      (final {:id :done})))

  (transition {:event :done.state.work :target :finished})
  (final {:id :finished}))
----

What happens when the LLM in `coder` decides to call `region__repl_eval`:

. The worker fires `:repl/eval` on the chart's event queue, carrying a
  correlation id and the routing payload.
. The engine routes the event to `:repl-A`'s `:idle` substate, where
  `handle-tool` has installed a transition.
. The handler returns `{:result "not running" :is-error true}`. The helper
  fires an `:escapement.tool/reply` event back.
. The worker, parked in a poll loop, drains the reply and emits the
  matching `tool_result` block on its next assistant turn.

The LLM sees a normal `tool_use → tool_result` exchange. No `:end_turn`
back-and-forth in the consumer's transcript for the service's work.

=== `service/register-tool!`

Returns a `script` element. Place it on the service region's `on-entry`:

[source,clojure]
----
(on-entry {} (service/register-tool!
               {:tool         :repl/eval
                :description  "Evaluate a Clojure form. Input :expr (string)."
                :input-schema [:map [:expr :string]]}))
----

* `:tool` — the chart event the LLM call fires.
* `:description` — exposed to the LLM verbatim.
* `:input-schema` — a Malli schema. Must be _open_ (no `{:closed true}`)
  so the framework can merge an implicit optional `:timeout-ms` field;
  closed schemas error at registration time.

The `:owner` is read from the enclosing state (`::sc/context-element-id`)
at runtime — you never pass it. Two sibling regions MAY register the same
tool keyword; consumers disambiguate with `:as`. A single owner
re-registering the same keyword with a _different_ declaration is a hard
error.

=== `service/unregister-tool!`

Returns a `script` element. Place it on `on-exit` if you want to scrub the
entry when the region leaves:

[source,clojure]
----
(on-exit {} (service/unregister-tool! :repl/eval))
----

The chart-level registry is scoped to one engine run, so stale entries
only matter if a later sibling conversation might mistake an exited
region's tools for available ones.

=== `service/handle` / `h/handle-tool`

Produces a `transition` element bound to the tool event, with the
handler-fn wired as the transition's action:

[source,clojure]
----
(state {:id :running}
  (h/handle-tool :repl/eval
    (fn [env {:keys [data reply-id reply-to timeout-ms]}]
      {:result (str (eval-form (:expr data)))
       :is-error false})))
----

The handler receives `[env request]`. The `request` map carries:

* `:data` — the LLM-supplied input, with framework-injected keys stripped.
* `:reply-id` — correlation id (you only need this for the slow-work
  pattern below).
* `:reply-to` — caller invokeid string (ditto).
* `:timeout-ms` — the deadline the caller is enforcing.

Return value:

* `{:result <string> :is-error <bool>}` — replies synchronously.
* `nil` — promises a deferred reply via `service/post-reply` (see below).
* a throw — surfaced as `{:result "handler threw: <msg>" :is-error true}`.

The owner is derived from chart structure at call time — the transition is
tagged at build time with a synthetic id, and the cond walks
`::sc/elements-by-id [tid :parent]` to find the enclosing service-region
state, comparing it against the request's `:escapement.tool/owner`. So
`(h/handle-tool ...)` is identical in single-owner and multi-owner charts;
the author never names the state-id twice.

The helper `h/handle-tool` is a thin alias for `service/handle`. Use
either; the codebase prefers `h/handle-tool` for symmetry with other
`h/*` helpers.

=== Consumer side: `:chart-tools`

The consumer conversation opts in via its `params-fn`:

[source,clojure]
----
{:chart-tools [{:owner :repl-A}]                         ;; pull from one region
 ;; or, with aliasing for multi-region scenarios:
 :chart-tools [{:owner :repl-A :as :py}
               {:owner :repl-B :as :clj}]}
----

The palette is built by walking the registry at conversation start. Each
tool becomes an Anthropic tool named `region__<encoded>`. With `:as
:py`, `:repl/eval` becomes `region__py__repl_eval` on the LLM side and
the consumer can call both `:py` and `:clj` variants in the same turn
without collision.

The LLM may include `:timeout-ms` in any region-tool call to override the
default (30s). The framework merges that field into every region-tool's
JSON schema automatically.

[CAUTION]
====
The palette is a **snapshot** taken at conversation start. Tools
registered _after_ that point are NOT in the consumer's palette and will
fall through to the worker's "Unknown tool" branch. If a service region
needs to add tools dynamically, the consumer must be started after the
registration completes (the existing readiness-barrier pattern: have the
service fire an `:x/ready` event the consumer's parent state waits for).
====

=== Substate routing (`:idle` / `:running` / `:busy`)

The handler installed by `h/handle-tool` is a transition on the
*enclosing* state. SCXML transition precedence means a substate's handler
overrides the parent's — the framework rides this for free.

[source,clojure]
----
(state {:id :repl-A :initial :idle}
  (on-entry {} (service/register-tool!
                 {:tool         :repl/eval
                  :description  "Evaluate."
                  :input-schema [:map [:expr :string]]}))

  (state {:id :idle}
    (h/handle-tool :repl/eval
      (fn [_ _] {:result "not started; call :repl/start first"
                 :is-error true})))

  (state {:id :running}
    (h/handle-tool :repl/eval real-eval-fn)))
----

A call to `:repl/eval` while in `:idle` gets the "not started" reply; the
same call after a transition into `:running` runs the real handler. No
framework dispatch table — the chart's state machine IS the dispatch
table.

[WARNING]
====
**Use `:type :internal` for transitions between substates of a service
region.** Per SCXML §3.13, `findLCCA` excludes the source state itself,
so an _external_ transition `:source :repl-A → :target <child-of-:repl-A>`
has LCCA = `:repl-A`'s parent. If `:repl-A` is one branch of a
`<parallel>`, the external transition will exit and re-enter the entire
parallel — including sibling branches running the consumer LLM
conversation, which restart from scratch.

The fix is one keyword: `(transition {:event :repl/start
:target :running :type :internal})`. Place it on the compound
service-region state; the parallel sibling is undisturbed.
====

=== Slow / async work — `service/post-reply`

A synchronous handler that needs to do slow work blocks the chart's
microstep, which serializes other event processing. The pattern is to
return `nil`, kick off the work on another thread, and call
`service/post-reply` from that thread when the result is ready:

[source,clojure]
----
(state {:id :running}
  (h/handle-tool :repl/eval
    (fn [env {:keys [reply-id reply-to data]}]
      (future
        (let [result (slow-eval (:expr data))]
          (service/post-reply env
                              {:reply-id reply-id
                               :reply-to reply-to
                               :result   (str result)
                               :is-error false})))
      ;; nil = "the reply is in the mail"
      nil)))
----

The consumer's worker is parked in a poll loop with the caller's
`:timeout-ms`. As long as `post-reply` fires inside that window, the
worker receives it like any synchronous reply. If the deadline passes
first, the worker emits an is-error `tool_result` with "timed out after
Xms" and continues; a `post-reply` that arrives later is logged on the
transcript as `:llm/region-tool-late-reply` and dropped.

For "busy, retry shortly" behavior under concurrent calls to the same
slow tool, model it as a substate the region transitions into for the
duration of the work, with its own handler returning `{:result "busy,
retry shortly" :is-error true}`. The chart's state IS the policy.

=== `escapement.chart.repl-service` — a worked drop-in

`escapement.chart.repl-service/repl-service-region` packages the
pattern for a Clojure REPL service:

[source,clojure]
----
(require '[escapement.chart.repl-service :as repl-svc])

(state {:id :run :initial :work}
  (parallel {:id :work}
    (repl-svc/repl-service-region
      {:id          :repl-mgr
       :project-dir "/path/to/project"})         ;; optional auto-discovery
    (state {:id :consumer :initial :running}
      (state {:id :running}
        (h/llm-conversation
          {:id        "coder"
           :params-fn (fn [_ _]
                        {:initial-user-message "Refactor foo.clj"
                         :chart-tools          [{:owner :repl-mgr}]})})))))
----

Defaults to in-process SCI eval via the `:repl/eval` builtin tool. Pass
`:eval-fn` to talk to a real external nREPL; pass `:status-fn` to
register `:repl/status` (the helper has no honest default for status —
omit if you don't have one).

=== The wire (for debugging)

Region-tool calls travel as two chart events. You'll see them on the
transcript when something goes wrong:

Request, posted by the consumer worker on a `tool_use`::
+
[source,clojure]
----
{:event :repl/eval
 :data  {:expr "(+ 1 2)"
         :escapement.tool/reply-id   "tr_abc"     ;; correlation
         :escapement.tool/reply-to   "coder"      ;; caller invokeid
         :escapement.tool/owner      :repl-A      ;; chosen owner
         :escapement.tool/timeout-ms 30000}}
----

Reply, fired by the handler helper::
+
[source,clojure]
----
{:event :escapement.tool/reply
 :data  {:escapement.tool/reply-id "tr_abc"
         :escapement.tool/reply-to "coder"
         :result   "3"
         :is-error false}}
----

Replies are hard-routed by `:reply-to`, not broadcast: the conversation
processor's `forward-event!` only delivers when the calling invocation's
own invokeid equals `:reply-to`.

[[backends]]
== LLM backends

The core `LLMBackend` protocol is one method, `send-turn`. Defined in
`src/escapement/llm/protocol.clj`, which also defines an optional
`StreamingLLMBackend` (`stream-turn`) and the `send-turn*` capability
dispatcher (see the SSE token streaming subsections below). Four
implementations ship.

=== `escapement.llm.api` — Anthropic-compatible HTTP

Defined in `src/escapement/llm/api.clj`. Near-passthrough to the Anthropic
Messages API. Works against any service that speaks that wire format.

[source,clojure]
----
(require '[escapement.llm.api :as api])

;; Anthropic
(api/new-backend {:base-url      "https://api.anthropic.com"
                  :api-key       (System/getenv "ANTHROPIC_API_KEY")
                  :default-model "claude-sonnet-4-5"})

;; z.ai (Anthropic-compatible endpoint, cheap dev option)
(api/new-backend {:base-url      "https://api.z.ai/api/anthropic"
                  :api-key       (System/getenv "ZAI_API_KEY")
                  :default-model "glm-4.6"})
----

The auth mode is auto-sniffed from the base URL: `z.ai` → `Authorization:
Bearer <key>`; anything else → `x-api-key: <key>` plus `anthropic-version:
2023-06-01`. Override with `:auth-mode :bearer` or `:auth-mode :x-api-key`.

`cache_control` markers are passed through verbatim — both Anthropic and
z.ai consume them natively.

NOTE: z.ai does not currently return `cache_creation_input_tokens` and does
not require the `anthropic-version` header. Both differences are tolerated
silently by the request builder and the usage parser.

z.ai's published GLM family (`glm-5.1`, `glm-5`, `glm-5-turbo`,
`glm-4.7`, `glm-4.7-flashx`, `glm-4.7-flash`, `glm-4.6` at 200K
context, the `glm-4.5*` / `glm-4-32b-0414-128k` family at 128K, …) is
tracked in the model catalog (`escapement.llm.catalog`). Pass any of
them as `:default-model` or per-state `:model`.

==== Image (vision) content blocks

The request protocol accepts an `:image` content block on `:user`
messages, alongside `:text` / `:tool_result`. Its `:source` is either
inline base64 or a URL the provider fetches server-side:

[source,clojure]
----
;; inline bytes
{:role :user
 :content [{:type :image
            :source {:type :base64
                     :media-type "image/png"   ; jpeg|png|gif|webp
                     :data b64-string}}
           {:type :text :text "Describe this screenshot."}]}

;; remote URL (Anthropic fetches it)
{:type :image :source {:type :url :url "https://…/ref.png"}}
----

The api (Anthropic) backend serializes this to the Messages API
`image`/`source` wire shape and parses it back symmetrically; it
survives a streamed turn identically. The OpenAI/OpenRouter backend
serializes the same `:image` block to the Chat Completions multimodal
`image_url` content shape (a `:url` source passes through verbatim; a
`:base64` source is encoded as a `data:` URI), so vision works on either
backend family without invocation-code changes. This is a
**protocol-level capability** — it is consumed by any code constructing
a `Request`/`Message` (e.g. a custom invocation or a chart that builds
user content directly). Backends without vision support should reject or
drop the block explicitly rather than silently.
Use it for reference-image → description pipelines without changing
invocation code.

==== SSE token streaming

The api backend also implements the optional
`escapement.llm.protocol/StreamingLLMBackend` (`stream-turn`). Callers
go through `proto/send-turn*`, which streams when the backend supports it
and a delta callback is supplied, and otherwise issues a plain buffered
`send-turn` — the final Response is byte-identical either way. With
`"stream": true` the backend reads the SSE `data:` events and rebuilds
the Response from `content_block_*` events; `proto/streaming?`
feature-detects support. Charts opt in per state with the `:stream?`
`llm-conversation` param (see <<params-fn>>), which surfaces deltas as
`:llm/delta` transcript events; nothing else about chart semantics
changes.

=== `escapement.llm.openai` — OpenAI Chat Completions / OpenRouter

Defined in `src/escapement/llm/openai.clj`. Sibling of the Anthropic
backend. Accepts the same internal `Request` map and translates to the
OpenAI Chat Completions wire format. Works against any OpenAI-compatible
endpoint: OpenAI itself, OpenRouter (multi-provider broker), local
llama.cpp / vLLM servers, Codex-style coding models served via OpenAI
shape, etc.

[source,clojure]
----
(require '[escapement.llm.openai :as openai])

;; OpenAI
(openai/new-backend {:base-url      "https://api.openai.com/v1"
                     :api-key       (System/getenv "OPENAI_API_KEY")
                     :default-model "gpt-4o-mini"})

;; OpenRouter (set Referer/Title headers when publishing usage)
(openai/new-backend {:base-url      "https://openrouter.ai/api/v1"
                     :api-key       (System/getenv "OPENROUTER_API_KEY")
                     :default-model "openai/gpt-4o-mini"
                     :extra-headers {"HTTP-Referer" "https://example.com"
                                     "X-Title"      "my-app"}})
----

Translation rules:

* Our `:system` becomes the leading `role: "system"` message.
* Assistant `:tool_use` blocks fold into `tool_calls`; assistant text and
  tool-calls live on a single OpenAI message.
* Each `:tool_result` user-block fans out into its own
  `role: "tool"` message (OpenAI does not batch tool results like Anthropic
  does). `:is-error` is surfaced inline as a `[error]` prefix (OpenAI has no
  native flag for it).
* `:thinking`, `:redacted_thinking`, and all `cache_control` markers are
  silently dropped (OpenAI's prefix cache is implicit and not addressable).
* `:max-tokens` flips to `max_completion_tokens` for newer models
  (`gpt-5*`, `gpt-4.1*`, `o*`) and stays as `max_tokens` for legacy
  (`gpt-3.5*`, `gpt-4-*`, `gpt-4o*`).
* OpenAI's `usage.prompt_tokens_details.cached_tokens` is surfaced as
  `:cache-read-input-tokens` for transcript parity with the Anthropic
  backend.

CLI auto-detect: `OPENAI_API_KEY` routes to the OpenAI base URL,
`OPENROUTER_API_KEY` routes through the OpenAI backend at OpenRouter's
endpoint. `OPENAI_MODEL` / `OPENROUTER_MODEL` env vars override the default
model strings.

==== SSE token streaming

Like the Anthropic `api` backend, the OpenAI backend also implements the
optional `escapement.llm.protocol/StreamingLLMBackend` (`stream-turn`).
It uses the Chat Completions SSE wire (`"stream": true` with
`stream_options.include_usage`), accumulates the `choices[].delta`
content/`tool_calls` fragments and the trailing usage chunk, then
finalizes through the *same* `openai-json->response` translator the
buffered path uses — so a streamed turn yields a `Response` structurally
identical (blocks + usage) to a buffered one. Charts opt in per state
with `:stream?` (see <<params-fn>>); incremental content surfaces as
`:llm/delta` transcript events. Each delta may carry an optional
cumulative `:usage` key for live UX — OpenAI only emits usage on the
final chunk, so most deltas carry none; the finalized `Response` usage
remains the billing source of truth.

=== `escapement.llm.openai-codex` — ChatGPT subscription via OAuth

Defined in `src/escapement/llm/openai_codex.clj` (entry point) and the
`openai_codex/` sub-package. Routes to
`https://chatgpt.com/backend-api/codex/responses` using an OAuth 2.0 +
PKCE token bound to a ChatGPT Plus, Pro, Business, or Enterprise account.
No OpenAI API key is required; billing is against your subscription's
per-tier message limits.

==== Constructor

[source,clojure]
----
(require '[escapement.llm.openai-codex :as codex])
(codex/new-backend {:default-model "gpt-5.1-codex"})
----

==== Authentication

[source,bash]
----
escapement login codex   # one-time, opens browser for ChatGPT OAuth
escapement logout codex  # remove cached credentials
----

Credentials are saved to `~/.escapement/openai-auth.json` (mode 0600).
The backend refreshes the token automatically when it is within 60 seconds
of expiry.

==== Available models

* `gpt-5.2-codex` — latest flagship Codex model (supports `xhigh` reasoning)
* `gpt-5.2` — GPT-5.2 general purpose
* `gpt-5.1-codex` — standard Codex model *(default)*
* `gpt-5.1-codex-max` — extended context Codex variant
* `gpt-5.1-codex-mini` — lighter Codex variant (lower quota cost)
* `codex-mini-latest` — legacy mini alias
* `gpt-5.1` — GPT-5.1 general purpose

Anthropic-style model names (`claude-opus-4-7`, `claude-sonnet-4-6`) are
silently mapped to `gpt-5.2-codex`; `claude-haiku-4-5` maps to
`gpt-5.1-codex-mini`.

==== Reasoning effort

Pass a `:reasoning` key in the params map (value overrides the default):

[source,clojure]
----
{:reasoning {:effort "high" :summary "auto"}}
----

Valid effort values: `none` (gpt-5.1/gpt-5.2 general only), `low`,
`medium` (default), `high`, `xhigh` (gpt-5.2/codex-max only).

==== Subscription billing

IMPORTANT: This backend authenticates against `chatgpt.com/backend-api`
using an OAuth token bound to your ChatGPT Plus, Pro, Business, or
Enterprise subscription. Usage counts against your subscription's per-tier
message limits (Plus is approximately 30-150 messages per 5-hour window as
of May 2026; see your ChatGPT plan for current quotas). It does NOT bill
the OpenAI API meter.

**This path is for personal development use with your own subscription.**
It is not sanctioned by OpenAI for redistribution or multi-user services.
If you need multi-user or production deployment, use a pay-per-token
backend (the `api` backend above for Anthropic, or a future OpenAI
Platform API backend).

==== Limitations vs `api` backend

* `:max-tokens` is silently ignored (not accepted by the ChatGPT backend).
* `:temperature`, `:top-p`, `:top-k`, `:stop-sequences`, `:tool-choice`
  are silently ignored (reasoning models do not accept them).
* Extended-thinking is replaced by the reasoning effort knob (`:reasoning`
  key described above).
* `cache_control` markers are no-ops; a debug log line is emitted when
  they are present.
* Only GPT-5.x reasoning models are available; there is no cheap
  Haiku-equivalent.
* Stateless: `store: false`. The full conversation is re-sent on every
  turn (no server-side caching across turns beyond reasoning summaries).

=== `escapement.llm.multi` — multi-backend dispatcher

Routes each request to a sub-backend based on the requested `:model`. A
chart that asks for `claude-sonnet-4-6` in one state and `gpt-5.2-codex`
in the next will reach Anthropic and the codex subscription endpoint
respectively, with no caller changes.

[source,clojure]
----
(require '[escapement.llm.api          :as anthropic]
         '[escapement.llm.openai-codex :as codex]
         '[escapement.llm.multi        :as multi])

(def backend
  (multi/new-backend
    {:routes          [[#"^claude-" (anthropic/new-backend {...})]
                       [#"^gpt-5"   (codex/new-backend {})]]
     :default-backend (anthropic/new-backend {...})}))
----

Matchers may be a regex, a set of exact-match strings, or a predicate
`(fn [model-string] boolean)`. Routes are tried in order; first match
wins. If no route matches, `:default-backend` handles the request, or an
`ex-info` is thrown when no default is configured.

`new-backend` returns a dispatcher that **also implements
`StreamingLLMBackend`** iff every selectable sub-backend (all routed
backends plus any `:default-backend`) supports streaming, so the
request-less `protocol/streaming?` faithfully reflects the sub-backend
that would be picked. When it streams, `stream-turn` selects the
sub-backend via the *same* routing logic as `send-turn` (no duplicate
selection, no re-counting) and forwards deltas + the final Response
through. If a mixed route set has any non-streaming sub-backend the
dispatcher is non-streaming and callers transparently get buffered
turns.

The CLI assembles this dispatcher automatically when more than one
credential is available — see <<cli>> for the default route table.

=== Ollama Cloud and OpenCode Go

Two further provider wirings are selectable without a new protocol
implementation — both reuse the `api`/`openai` backends above against
provider-specific endpoints:

* **Ollama Cloud** — `escapement run --backend ollama`, served via the
  OpenAI-compatible backend at `https://ollama.com/v1`. Credential:
  `OLLAMA_API_KEY`.
* **OpenCode Go** — `escapement run --backend opencode-go`, served at
  `https://opencode.ai/zen/go`. The wire shape is chosen per model:
  Anthropic-shaped for `minimax-*` models, OpenAI-shaped for
  `glm-*`/`kimi-*`/`mimo-*`. Credential: `OPENCODE_GO_API_KEY`.
  `--api-base-url` overrides the endpoint.

Both are auto-detected from their env vars for the default
multi-backend and reported by `escapement info`. A blank/empty
credential env var is treated as unset (it no longer registers a dead
route).

=== `escapement.llm.cache` — content-addressed disk cache

Defined in `src/escapement/llm/cache.clj`. Wraps any `LLMBackend` and
caches by SHA-256 over `(model, system, messages, tools)`. Opt-in via
`ESCAPEMENT_LLM_CACHE=1` or by explicit construction. Useful for
deterministic dev runs against expensive backends.

[[tools]]
== Tools

The `Tool` protocol (`src/escapement/tools/protocol.clj:18`):

[source,clojure]
----
(defprotocol Tool
  (tool-name    [t])  ; keyword, e.g. :fs/read
  (description  [t])  ; short string for the LLM
  (input-schema [t])  ; Malli schema
  (invoke       [t input]))  ; returns {:result <string> :is-error <bool>}
----

A registry is just an atom of `{tool-name → tool}`. Construct with
`tp/new-registry` or seed all five builtins with
`builtin/new-builtin-registry`. `tp/dispatch` validates the input against
the tool's schema before invoking; validation failures are returned as
`{:result <pretty error> :is-error true}` so the LLM gets a corrective
`tool_result` rather than a thrown exception.

`tp/tool->anthropic-tool-def` produces the JSON Schema that the LLM sees,
using `malli.json-schema/transform`. Qualified keywords are flattened
(`:fs/read` → `"fs_read"`).

=== Built-in tools

Defined in `src/escapement/tools/builtin.clj`. The filesystem and search
tools are designed to sit at Claude-Code-parity ergonomics for the LLM.

`:fs/read`::
  Read a UTF-8 text file. Input: `{:path :string
  :offset (? pos-int?) :limit (? pos-int?)}`. Output is `cat -n` style:
  6-digit right-padded 1-based line numbers, a tab, then content. Default
  read window is 2000 lines from the top; `offset`/`limit` page through
  larger files. When more lines remain past the window the result ends
  with a `... [N more lines; read with :offset M]` notice telling the
  model exactly how to fetch the next chunk. Files larger than 200 KiB
  are byte-truncated up front before line-numbering.

`:fs/write`::
  Atomic UTF-8 write. Input: `{:path :string :content :string}`. Writes
  via temp-file + `ATOMIC_MOVE`. Creates parent directories.

`:fs/edit`::
  String-replacement edit. Input: `{:path :string :old-string :string
  :new-string :string :replace-all (? :boolean)}`. By default
  `old-string` must occur exactly once — the LLM is forced to supply
  enough context for an unambiguous edit. Pass `replace-all true` to
  replace every occurrence (the response then reports the count).
  Indentation in `old-string` must match the file byte-for-byte. The
  result reports replacement count; identical `old-string`/`new-string`
  is rejected rather than written as a no-op.

`:fs/multi-edit`::
  Atomic sequence of string-replacement edits to one file. Input:
  `{:path :string :edits [{:old-string :string :new-string :string
  :replace-all (? :boolean)} ...]}`. Edits are applied in order to the
  in-memory content; the file is written only if ALL edits succeed.
  Later edits can operate on the output of earlier ones. On failure
  the response identifies the failing edit index (`edit #N of M`) and
  the file is unchanged.

`:fs/glob`::
  Find files matching a glob pattern (e.g. `**/*.cljc`). Input:
  `{:pattern :string :cwd (? :string) :limit (? pos-int?) :by-mtime?
  (? :boolean)}`. Walks `cwd` (default `.`) recursively using
  `java.nio.file.PathMatcher`. Matches `**/*.foo` against both root and
  nested files (Java's stock `**` only matches nested — we also try the
  suffix without the leading `**/` so behavior matches
  ripgrep/fd/minimatch). Sorted most-recently-modified first by default;
  pass `by-mtime?` false for lexicographic. Capped at `limit` (default
  200) with an overflow notice. Returns absolute paths, one per line.

`:fs/grep`::
  Regex search across files. Input: `{:pattern :string :path (? :string)
  :glob (? :string) :output-mode (? :enum) :ignore-case (? :boolean)
  :context (? :int) :limit (? pos-int?)}`. Prefers `rg` (ripgrep) when
  available on PATH; falls back to `grep -rE`. `output-mode` is one of
  `"files-with-matches"` (default), `"content"` (numbered match lines
  with optional `:context` lines around each hit), or `"count"`. `glob`
  filters file names (`*.clj`). 20-second timeout; non-match returns
  the `[no matches]` sentinel; rg/grep exit 2 surfaces as `is-error`
  with stderr trimmed.

`:shell/run`::
  Run a shell command via `bash -lc`. Input: `{:command :string
  :timeout-ms (? :int)}`. Default timeout 30s. Returns combined
  stdout+stderr and the exit code; `is-error` is true on non-zero exit
  or timeout.

[[custom-tool]]
=== Registering a custom tool

There are two registries in play:

`escapement.tools.builtin/default-registry`::
  A `defonce` singleton atom, seeded on namespace load with the eight
  built-ins. The CLI uses this. Top-level `register!` calls in any
  namespace that gets required before `runner/run!` are visible to the
  chart — the standard Clojure side-effect-on-require pattern.

`escapement.tools.builtin/new-builtin-registry`::
  Returns a FRESH atom each call, pre-seeded with the eight built-ins.
  Use this when you want isolation — tests, or a host process driving
  multiple chart runs with disjoint tool sets.

The natural way to expose a custom tool to a CLI-driven chart is to
require its namespace from the chart and let that namespace self-register
at load time:

[source,clojure]
----
(ns my.app.tools
  (:require
   [babashka.http-client :as http]
   [escapement.tools.builtin :as builtin]
   [escapement.tools.protocol :as tp]))

(defrecord HttpGetTool []
  tp/Tool
  (tool-name    [_] :http/get)
  (description  [_] "GET a URL and return the body as a string.")
  (input-schema [_] [:map {:closed true} [:url :string]])
  (invoke [_ {:keys [url]}]
    (let [{:keys [status body]} (http/get url)]
      {:result body :is-error (not (and (>= status 200) (< status 300)))})))

;; Top-level: registers on namespace load. Idempotent because the
;; registry is keyed by tool-name — re-loading the ns just rewrites the
;; entry under :http/get.
(tp/register! builtin/default-registry (->HttpGetTool))
----

Then have your chart namespace require it:

[source,clojure]
----
(ns my.chart
  (:require
   [com.fulcrologic.statecharts.chart :as chart]
   [escapement.chart.helpers :as h]
   [my.app.tools]))   ;; <-- require triggers registration
----

Now the chart's `params-fn` can name the tool in `:real-tools`:

[source,clojure]
----
{:real-tools [:http/get :fs/read]
 :allowed-events [{:event :done :data-schema [:map [:summary :string]]}]
 ...}
----

The CLI just runs:

[source,bash]
----
escapement run my.chart/agent
----

It loads the chart (`runner/load-chart` does `require` on its namespace),
which transitively requires `my.app.tools`, which registers `:http/get`
into the singleton. The CLI then hands that singleton to `runner/run!`.

=== Explicit registration: the `--tools-ns` flag

If you would rather wire tools at the entry point — for example because
the chart cannot transitively require its tools, or you want an explicit
manifest visible at the call site — define a single-arg function and pass
its symbol with `--tools-ns`:

[source,clojure]
----
(defn register-tools!
  "Called by the CLI with the registry atom. Register everything; the
   builtins are already in there."
  [reg]
  (tp/register! reg (->HttpGetTool))
  ;; (other-ns/register! reg) ...
  reg)
----

[source,bash]
----
escapement run my.chart/agent --tools-ns my.app.tools/register-tools!
----

=== Driving the chart yourself

If you are NOT using the CLI — your own bb script — choose your registry
deliberately:

[source,clojure]
----
(require '[escapement.tools.builtin :as builtin]
         '[escapement.tools.protocol :as tp]
         '[escapement.runner :as runner])

;; Option A: share the global singleton (matches CLI behavior).
(tp/register! builtin/default-registry (->HttpGetTool))

;; Option B: isolated fresh registry (better for tests / parallel runs).
(let [reg (builtin/new-builtin-registry)]
  (tp/register! reg (->HttpGetTool))
  (runner/run! {:chart           (runner/load-chart 'my.chart/agent)
                :tool-registry   reg
                :backend         my-backend
                :session-id      :session/one
                :transcript-path "out/transcript.jsonl"
                :checkpoint-dir  "out/checkpoints"}))
----

[[transcript-runner-cli]]
== Transcript, runner, CLI

=== Transcript event vocabulary

`src/escapement/transcript.clj` is the JSONL sink. Every transcript row
has `:event`, `:ts`, `:seq`, plus event-specific `:data`. The events
emitted across the codebase:

* `:runner/started`, `:runner/start-config`, `:runner/resumed`,
  `:runner/quiescent`, `:runner/tick`, `:runner/done`, `:runner/error`,
  `:runner/aborted`, `:runner/event-processed`
* `:checkpoint/written`
* `:llm/start`, `:llm/request`, `:llm/response`, `:llm/error`,
  `:llm/user-message`, `:llm/worker-exit`, `:llm/context-warning`
* `:llm/delta` — incremental output during a `:stream?` turn. `:data` is
  `{:type :text-delta|:thinking-delta :text "…" :model … :invokeid …}`.
  Only emitted when the state set `:stream?` and the backend supports
  streaming; consumers MUST ignore unknown `:type` values (more may be
  added). Relay these off the transcript tap for live UI output; the
  final `:llm/response` is unchanged.
* `:llm/retry` — a transient backend failure is being retried per
  `:resilience`. `:data` is `{:model … :category … :attempt N
  :max-retries M :invokeid …}`. Fired before each backoff sleep.
* `:llm/continuation` — a `:max_tokens`-truncated turn is being
  continued. `:data` is `{:segment N :blocks K :usage {…} :invokeid …}`.
  The final stitched turn still arrives as one ordinary `:llm/response`.
* `:human-input/start`, `:human-input/answer`, `:human-input/cancelled`,
  `:human-input/error`, `:human-input/interrupted`,
  `:human-input/validation-failed`
* `:artifact/captured` (with `:name` and `:bytes`)
* `:cli/config-loaded` (`:path`, `:keys`), `:cli/deps-added` (`:coords`) —
  emitted as a prelude before `:runner/started` when an `.escapement.edn`
  is discovered or runtime deps are resolved.
* `:transcript/serialize-error`

The `api` backend emits its own `:llm/request` and `:llm/response` rows
with the full Anthropic body / parsed response (so you can replay the wire
exchange exactly).

=== Runner

`src/escapement/runner.clj` exposes `run!`. Required keys:
`:chart`, `:session-id`, `:transcript-path`, `:checkpoint-dir`. Optional:
`:backend`, `:tool-registry`, `:initial-data`, `:resume?`, `:trace?`,
`:max-iterations` (default 100000), `:quiescent-sleep-ms` (default 50),
plus these additive keys (all default to prior behavior when omitted):

* `:store` — working-memory store override, threaded to
  `engine.env/new-env`; `nil` ⇒ the default file-backed store
  (CLI behavior unchanged).
* `:session-dir` — artifact/session directory threaded to
  `engine.env/new-env` as `:escapement/session-dir` (backs
  `<session-dir>/artifacts/<name>`); omitted ⇒ the engine default.
* `:run-id` — opaque correlation id; when supplied it is echoed
  (stringified) on the `:runner/started` transcript event.
* `:cancel` — a host-supplied cancel handle: an atom (or any `IDeref`)
  whose truthy current value, or a promise/future/delay whose
  *delivered* value is truthy, requests a prompt abort. An undelivered
  promise never blocks the pump.

`run!` returns a summary map that now also carries `:status` —
`:done` on normal quiescence, `:aborted` if `:cancel` fired or
`:max-iterations` was hit. The same `:status` is included on the
`:runner/done` transcript event.

The pump loop:

1. **At the top of each iteration (a safe boundary between events,
   never mid-transcript- or mid-checkpoint-write), check `:cancel`.**
   If it is requesting abort, emit `:runner/aborted`
   `{:reason :cancelled}` and stop with `:status :aborted`. (The
   pre-existing max-iterations bound emits the same `:runner/aborted`
   event with `{:reason :max-iterations}`.)
2. Drain currently-deliverable events through the processor.
3. After each event, save working memory to the checkpoint store.
4. When the queue is empty, ask each `InvocationProcessor` how many live
   workers it has. If zero, terminate with `:status :done`. Otherwise
   sleep `:quiescent-sleep-ms` and try again. This is what lets the
   chart park while the LLM is thinking.

=== CLI

`src/escapement/cli.clj`. Subcommands:

* `run <chart-sym>` — execute a chart (the everyday command).

* `--no-tui` forces the TUI off (useful in CI, or to fall back to stdin

|===

[[project-config]]
=== Project configuration (`.escapement.edn`)

A project can pin its layout once in a single `.escapement.edn` file at
its root. Escapement walks up from the current working directory (git
style) looking for the file; the directory containing it becomes the
**config root**, and all relative paths in the file resolve against
that root — so `escapement run …` works the same from any subdirectory.

Schema (validated with Malli on load; unknown keys are rejected):

[source,clojure]
----
{:source-paths  ["ai/agents"]                 ;; classpath roots, prepended
 :deps          {hiccup/hiccup
                 {:mvn/version "2.0.0-RC3"}}  ;; runtime deps via add-deps
 :tools-ns      [my.app/register-tools]       ;; symbol or vector of symbols
 :work-dir      "ai/agents/transcripts"       ;; default --work-dir
 :default-chart my.app.examples.hello/agent   ;; used when no chart given
 :viewers       {"svg"     "open -a 'Google Chrome' {{path}}"
                 "url"     "open -a 'Google Chrome' {{path}}"
                 "default" "open {{path}}"}   ;; see Viewers below
 :d2            {:command "d2" :layout "elk"} ;; chart rendering (see Viz)
 :debug         {:auto-pause? true}           ;; --debug pause-on-start
 :llm/preferences [{:provider :anthropic :model "claude-opus-4-7"}
                   {:provider :z-ai      :model "glm-4.6"}]
 ;; ^ priority-ordered {:provider :model} pairs; validated against the
 ;;   catalog (unreachable entries are dropped). Sets the default
 ;;   backend and the auto-fallback model order. Built-in default order
 ;;   is used when unset.
 :llm/ratings   {"claude-opus-4-7" {:intelligence 10 :clojure 10}}}
 ;; ^ subjective opinion overlay; there is no built-in opinion, so the
 ;;   table comes entirely from config. Any key here becomes filterable
 ;;   via a node's :needs gate. Dated ids resolve to the family entry.
 ;; :llm/eligibility-strict? false}
 ;; ^ honored by the hermetic lib facade only (see Hosted library):
 ;;   true ⇒ fail-closed when a :needs gate empties; default fail-open.
----

==== Viewers — opening artifacts and the live chart URL

The `:viewers` map controls how Escapement opens artifact files
(`chart.svg`, transcripts, request/response captures, …) and the live
visualization URL. Keys are matched in this order:

* For an **artifact file**: lower-cased file extension (e.g. `"svg"`,
  `"jsonl"`, `"md"`) → `"default"` → `:internal` (the built-in pager).
* For the **live chart URL** (`v` in the TUI): the special key `"url"` →
  `:internal` (no auto-open; the URL still appears in the scrollback so
  you can click/paste it).

Values are shell-command templates. `{{path}}` is replaced with a
shell-quoted path (or URL); a template with no `{{path}}` placeholder
gets the path appended, so naked entries like `"open"` work too.
Templates are executed via `sh -c`.

==== d2 rendering

`:d2 :command` is the path to the `d2` binary (default `"d2"`, looked up
on `$PATH`). `:d2 :layout` selects the layout engine (`elk` by default;
`dagre` and `tala` are common alternatives). Used both by `v` in the TUI
and by any chart that calls `escapement.debug.d2/render-and-open!`.

Startup order (matters because each step may require what the previous
one made visible):

. Discover and validate `.escapement.edn`.
. Layer CLI flags over config over defaults.
. `add-deps` for `:deps` (Maven/git coords).
. `add-classpath` for `:source-paths`.
. `require` every `:tools-ns` and, if the symbol resolves to a function,
  invoke it with the builtin tool registry atom.
. Resolve the chart symbol — CLI argument wins, else `:default-chart`.

Precedence is `CLI flag > .escapement.edn > built-in default`. CLI
`:deps` is merged on top of config `:deps` (CLI wins per coordinate);
CLI `:source-paths` is prepended to config `:source-paths`; CLI
`:tools-ns` entries are appended to config entries. CLI-supplied paths
resolve against `cwd`; config-supplied paths resolve against the config
root. There is no environment-variable layer.

When a config file is found, the transcript opens with a
`:cli/config-loaded` event recording the file path and the keys present.
If runtime deps were resolved, a `:cli/deps-added` event follows.

A missing `.escapement.edn` is silent; defaults apply. A malformed file
fails fast with a humanized Malli error pointing at the offending key.

See also: <<add-chart,Adding a new chart>>.

[[idioms-gotchas]]
== Idioms and gotchas

* **`:type :internal` to keep the LLM alive.** Any transition out of (or
  back into) a bound state kills and re-spawns the worker. If you want
  the conversation to survive a hop, use `:type :internal`. Both
  `scan.clj` and `iterate.clj` lean on this.

* **`h/tell-llm` only works inside the bound state.** Outside, there is
  no live invocation to forward to. The event is silently dropped.

* **Parallel regions get their own workers.** No tool-name collision is
  possible because event-tool names encode the chart event keyword. See
  `parallel_demo.clj`.

* **Top-level `final` empties the configuration.** Wrap finals in a
  compound parent state (every demo chart does this).

* **Resume restarts in-flight conversations from scratch.** When the chart
  re-enters a bound state on resume, a fresh worker is spawned with a fresh
  message history; the previous conversation does not survive a process
  restart. This is idempotent for read tools like `:fs/read` but
  **at-most-once cannot be guaranteed for side-effecting tools** like
  `:fs/edit` or `:shell/run`. Charts that need durable side-effect tracking
  must drive it themselves via the data model (e.g. `iterate.clj`
  increments `:iterations` so retries respect the cap).

* **The library passes the triggering event as `:_event`.** Inside a
  transition `script`, `(get-in data [:_event :data ...])` is the standard
  way to read the event payload.

* **Daemon threads only.** All worker threads (`llm-conv-...`) and the
  transcript writer are daemon threads. They do not prevent bb exit.

[[testing]]
== Testing

Tests run under bb with `bb test`. The library's
`com.fulcrologic.statecharts.testing` is unusable because it transitively
requires `promesa`, which crashes under SCI; escapement ships its own
harness, `escapement.engine.testing`, that replaces the library's testing
helpers with a synchronous pump:

[source,clojure]
----
(require '[escapement.engine.testing :as dct])

(def t (-> (dct/new-testing-env {:statechart my-chart
                                 :tool-registry my-registry}
                                my-processor1 my-processor2)
           (dct/start! initial-data)))

(dct/drain! t)             ; pump until quiescent
(dct/configuration t)      ; #{:run :finished}
(dct/in? t :finished)
(dct/data t)               ; current data-model contents
(dct/run-events! t :foo {:name :bar :data {...}})
----

=== Mocking the LLM backend

Implement `LLMBackend` with a script-driven queue of canned responses. The
M7 iterate test
(`test/escapement/examples/iterate_test.clj`) is a complete example:

[source,clojure]
----
(defrecord MockBackend [responses call-log]
  llm/LLMBackend
  (send-turn [_ request]
    (swap! call-log conj request)
    (or (ts/pop-first! responses)
        (throw (ex-info "mock out of canned responses" {})))))

(defn- tool-use [tool-uses]
  {:stop-reason :tool_use
   :content     (mapv (fn [{:keys [id name input]}]
                        {:type :tool_use :id id :name name :input input})
                      tool-uses)
   :usage {} :model "mock"})

(defn- end-turn []
  {:stop-reason :end_turn :content [{:type :text :text "ok"}] :usage {} :model "mock"})
----

A test then queues up `(tool-use [...])` and `(end-turn)` responses in the
order the chart should drive them, and asserts the chart reaches
`:finished` with the expected data-model contents.

=== Stubbing a tool

Implement `Tool` with a queue of canned `{:result :is-error}` maps and
register it over the builtin (the iterate test stubs `:shell/run` so tests
do not actually run a shell):

[source,clojure]
----
(defrecord StubShellTool [responses calls]
  tp/Tool
  (tool-name    [_] :shell/run)
  (description  [_] "stub shell")
  (input-schema [_] [:map [:command :string]])
  (invoke [_ input]
    (swap! calls conj input)
    (or (ts/pop-first! responses)
        {:result "no canned response" :is-error true})))

(let [reg (builtin/new-builtin-registry)]
  (tp/register! reg (stub-shell [{:result "ok" :is-error false}]))
  ...)
----

[[chart-segment-testing]]
=== Testing segments of a large chart

Every chart node — `state`, `parallel`, `transition`, `script`,
`on-entry`, `invoke` — is a plain Clojure map produced by the element
constructors in `com.fulcrologic.statecharts.elements`. `chart/statechart`
just rolls them up into a registered chart value. So nothing prevents
extracting one (or several) states into top-level `def`s, dropping them
into the production chart unchanged, AND reusing the same vars inside
minimal *shim* charts whose only job is to drive that segment through
the testing harness.

This is how you write integration tests for a large chart without
booting the whole thing. The shim chart wraps the segment with the
minimum parent state + finals required for its transition targets to
resolve; the mocked `LLMBackend` scripts only the turns that segment
issues; the real engine, real invocation processor, real `params-fn`,
and real tool dispatch all run.

The pattern, distilled:

. In the production chart's namespace, lift the state into a `def`. The
  assembled chart references the var; behavior is unchanged.
+
[source,clojure]
----
(def refine-state               ; isolatable segment
  (state {:id :refine}
    (h/llm-conversation {:id "refine" :params-fn ...})
    (transition {:event :refine/sealed :target :pipeline-done} ...)
    (transition {:event :refine/give-up :target :pipeline-done} ...)))

(def agent
  (chart/statechart {:initial :run}
    ...
    refine-state                ; same var, in place
    ...))
----

. In the test, build a shim chart that wraps just that segment with the
  smallest possible parent state + finals so the segment's
  `:target` ids resolve.
+
[source,clojure]
----
(def shim
  (chart/statechart {:initial :run}
    (state {:id :run :initial :refine}
      refine-state
      (final {:id :pipeline-done}))))
----

. Run the shim through `escapement.engine.testing` with a mocked backend
  and (optionally) stubbed tools. The harness is unaware that it is
  driving an extracted sub-chart — everything else (the
  `:llm-conversation` invocation processor, the worker thread, event
  validation, transition algorithm, data-model ops) is the real
  production code path.
+
A complete example: `demos/unit_test/test/unit_test/refine_segment_test.clj`
extracts `refine-state` from `demos/unit_test/chart.clj` (a parallel,
two-region, seven-LLM-state pipeline) and exercises it in isolation.
Run it via:
+
[source,bash]
----
bb test-demo-unit-test
----

When to reach for this pattern:

* The full chart is expensive to set up — multiple parallel regions,
  long initialization chains, complex initial-data requirements.
* You want focused failure messages: a broken refine transition should
  surface as a refine-segment test failure, not as a chart-level
  "didn't reach :finished" timeout 30 states downstream.
* You want to characterize one state's contract — what inputs it
  requires, what events it emits, what data-model deltas it produces —
  without coupling the test to the surrounding chart.

When NOT to:

* If two segments are coupled (shared data, parallel coordination
  events), test them together — the shim chart can wrap both. The
  pattern works at any granularity: one state, one region, one
  compound substate.

=== Live smoke scripts

The `bb_test/` directory contains scripts that exercise the system against
real backends. `m6_live_smoke.clj` runs `hello`, `scan`, and
`parallel_demo`; `m7_live_iterate.clj` runs the iterate chart against a
tmp directory and reports pass/fail. These are not unit tests — they

==== `bb test:e2e` — live provider matrix

`bb test:e2e` (suite under `e2e/escapement/e2e/`, **not** run by
`bb test`) sweeps every provider whose credential is present in the
environment — the same matrix as the CLI's auto-detection, via the shared
`escapement.llm.providers`. For each it checks the real wire: a basic
turn, streaming, vision, and `:max_tokens` truncation detection; plus the
credential-independent `:transport` / `:timeout` / `:auth` error
categories and catalog freshness (these always run, even with no keys).
Providers without a credential are reported `SKIP` — never a failure —
and a capability×provider matrix is printed at the end. Only a reachable
provider actually misbehaving fails the run. Secrets are never printed.
Prompts and token caps are deliberately tiny.

[[project-layout]]
== Project layout

`src/escapement/engine/`::
  Custom engine pieces — `queue` (in-process FIFO event queue), `store`
  (atomic file-backed working-memory checkpoint), `exec` (lambda
  `ExecutionModel`), `env` (assembles the `::sc/env` map), and `testing`
  (bb-friendly synchronous test harness). These replace
  `com.fulcrologic.statecharts.simple`, which crashes under Babashka
  because of a transitive `promesa`/SCI conflict.

`src/escapement/llm/`::
  `protocol` (the one-method `LLMBackend`), `types` (Malli schemas for
  requests/responses/content-blocks/tool-defs), `api` (Anthropic-compatible
  HTTP backend, sniffing z.ai vs Anthropic auth modes), `openai` /
  `openai_codex` (OpenAI Chat Completions and the ChatGPT Plus/Pro
  subscription backend via OAuth 2.0 + PKCE), `multi` (model-routed
  dispatcher), `providers` (the public env→provider→backend matrix shared
  by the CLI auto-detection and `bb test:e2e`), `cache`
  (content-addressed disk cache), and the model
  catalog trio — `catalog_source` (loads the bundled
  `models-api.json` models.dev dump), `catalog` (the three-layer
  objective+local model facts and `satisfies-policy?` filtering with
  the published `eligibility-facts` vocabulary), `needs` (the flat
  `:needs` → canonical-policy translation), `preferences`
  (`:llm/preferences` ordering), and `ratings` (`:llm/ratings`
  subjective overlay, threaded explicitly — no process global).

[[hosted-library]]
== Hosted library

Escapement supports three usage modes:

CLI::
  `escapement run …` — see <<quickstart>>. Unchanged by this slice.

Hosted library::
  `escapement.lib/run` — embed Escapement in your own JVM/bb process.
  This section.

Future daemon direction::
  A long-lived, multi-session HTTP/socket service is an intended
  *future* direction (process-resident run registry, remote cancel,
  streamed events over the wire). It is **deferred — not in this
  slice**. No daemon namespace, endpoint, or API exists yet; the shape
  above is described only so the facade design does not foreclose it.
  Do not depend on a daemon API; there is none.

=== `escapement.lib/run`

`escapement.lib/run` is a thin, additive facade over the runner. It
validates its single option map against a **closed Malli schema**
(unknown keys are rejected — invalid options throw `ExceptionInfo`
with `ex-data` `{:errors <humanized> :provided-keys [...]}` and the
chart is never run), generates a stable `:run-id`, defaults the
transcript + checkpoint to a fresh temp dir when omitted, threads an
optional `:store` through to the engine env, and raises log min-level
to `:warn` for the run (quiet by default). It is **hermetic**: it
reads no `.escapement.edn` and no credential env var — providers and
config are injected as explicit data via `:credentials` / `:config`
(see <<hosted-config>>).

Companion vars/fns in the same namespace:

* `escapement.lib/Options` — the closed Malli schema value.
* `(escapement.lib/validate-options opts)` — returns `nil` when valid,
  a humanized error map otherwise. No side effects, never runs a chart.

==== Closed option schema (`escapement.lib/Options`)

`[:map {:closed true} …]`. Only these keys are accepted:

[cols="1,1,1,2",options="header"]
|===
| Key | Optional? | Default | Notes
| `:chart` | **required** | — | statechart value (from `chart/statechart`)
| `:session-id` | **required** | — | session id (keyword / string / uuid)
| `:credentials` | **required** | — | ordered vector of provider descriptor maps; the backend is assembled from these hermetically (no env/disk). See <<hosted-config>>
| `:config` | optional | `{}` ⇒ empty ratings + default preferences | `.escapement.edn`-shaped map (`:llm/preferences`, `:llm/ratings`, `:llm/eligibility-strict?`); never a disk fallback. See <<hosted-config>>
| `:backend` | optional | none | an `LLMBackend`; an escape hatch that wins verbatim over `:credentials` assembly
| `:tool-registry` | optional | none | tool registry atom. **Required in practice for any chart containing an `:llm-conversation`**: the facade registers the LLM invocation processor only when *both* a backend (from `:credentials`) and a `:tool-registry` are present — omit it and the invocation cannot start (`No processor for :llm-conversation`, chart quiesces early). Pass `(escapement.tools.protocol/new-registry)` for an empty registry or `(escapement.tools.builtin/new-builtin-registry)` for one with the fs/shell/repl built-ins.
| `:initial-data` | optional | none | data-model seed (`[:maybe :map]`)
| `:transcript-tap` | optional | none | `(fn [event])` — receives every transcript row in-process
| `:on-env-ready` | optional | none | `(fn [env])` — called once env is built, before chart start
| `:transcript-path` | optional | `<tmp>/transcript.jsonl` | when omitted, a fresh temp dir is created
| `:checkpoint-dir` | optional | `<tmp>/checkpoints` | when omitted, a fresh temp dir is created
| `:session-dir` | optional | `<tmp>` | artifact/session dir (`<session-dir>/artifacts/<name>`); defaults to the same temp dir
| `:store` | optional | engine default file store | threaded to `engine.env/new-env`
| `:quiet?` | optional | `true` | suppress statecharts-impl DEBUG/INFO stderr (restored after the run)
| `:cancel` | optional | none | atom/volatile/ref/agent (truthy current value) **or** delivered promise/future/delay; truthy ⇒ abort
| `:chart-id` | optional | runner default | passthrough
| `:resume?` | optional | `false` | passthrough
| `:trace?` | optional | `false` | passthrough
| `:max-iterations` | optional | runner default (100000) | passthrough
| `:quiescent-sleep-ms` | optional | runner default (50) | passthrough
|===

A single temp dir (`escapement-run-…`) is created **only if**
`:transcript-path` *or* `:checkpoint-dir` is missing; the missing
one(s) are placed inside it. Supplying both explicitly creates no
temp dir.

==== Result map

`run` returns the runner summary map with these keys:

[cols="1,1,3",options="header"]
|===
| Key | Type | Value
| `:run-id` | string | generated 36-char UUID string, stable within the run, unique across runs
| `:status` | keyword | `:done` (normal quiescence) or `:aborted` (cancel fired, or max-iterations hit)
| `:transcript` | string | transcript path actually used (temp or explicit)
| `:checkpoint-dir` | string | checkpoint dir actually used (temp or explicit)
| `:session-dir` | string | session/artifact dir actually used (temp or explicit)
| `:session-id` | any | echoed session id
| `:final-config` | vector | final statechart configuration
| `:env` | map | the live `::sc/env`
|===

`:run-id` is also emitted (stringified) on the `:runner/started`
transcript event, so a host can correlate logs by it. Hosts read
`(:status result)`; `(= :aborted (:status result))` means the run was
cancelled or hit the iteration bound. Omitting `:cancel` always yields
`:status :done` for a normal run.

==== Cancellation

Pass `:cancel` an atom/volatile/ref/agent (cancels when its current
value is truthy) **or** a promise/future/delay (cancels only when
delivered *and* truthy — an un-delivered promise never aborts and
never blocks the pump). When fired, the run terminates at a safe
pump-loop boundary *between* events (never mid-transcript- or
mid-checkpoint-write, so no torn row), emits a `:runner/aborted`
`{:reason :cancelled}` lifecycle row, then still falls through to a
clean `:runner/done` `{:status :aborted}`. The pre-existing
max-iterations abort is the same `:runner/aborted` event with
`{:reason :max-iterations}`.

[[hosted-config]]
=== Hermetic configuration and credentials

The CLI sniffs credential env vars and walks up the filesystem for
`.escapement.edn`. The hosted facade does **neither**: `escapement.lib/run`
never reads disk and never reads env. A host (e.g. a webapp) configures
providers, preference order, and ratings **once** at startup and injects
them as explicit data on **every** invocation — like passing a DB pool,
not like sourcing a dotfile. This makes a run fully reproducible per
request, with no ambient state and no cross-thread global: two `run`
calls in one process with different `:config` ratings resolve the
`:needs` gate independently.

==== `:credentials` — required provider descriptors

`:credentials` is a **required** key (a closed-schema violation if
omitted): an ordered vector of provider descriptor maps. Each names a
`:provider` keyword (matching `escapement.llm.providers`) plus the
env-free secrets/overrides that provider needs:

[source,clojure]
----
;; app-lifetime, built once at startup
(def llm-credentials
  [{:provider :z-ai-plan :subscription true}
   {:provider :anthropic :api-key (System/getenv "ANTHROPIC_API_KEY")}
   {:provider :openai    :api-key (System/getenv "OPENAI_API_KEY")}])
----

Per-descriptor keys: `:provider` (required keyword), and any of
`:api-key`, `:base-url`, `:model`, `:default-model`, `:auth-mode`,
`:subscription`. The backend is assembled from this vector via
`escapement.llm.providers/build-injected-credentials-backend` (zero env,
zero disk), ordered by the resolved preference list. An explicit
`:backend` is an escape hatch that wins verbatim over `:credentials`
assembly.

==== `:config` — the `.escapement.edn`-shaped map

`:config` is **optional** and mirrors the `.escapement.edn` shape
(see <<project-config>>) — but read from the host, never disk:

[source,clojure]
----
(def llm-config
  {:llm/preferences                       ; THE ranking — sorted, priority-first
   [{:provider :z-ai-plan :model "glm-5.1"}
    {:provider :anthropic :model "claude-opus-4-7"}
    {:provider :openai    :model "gpt-5"}]

   :llm/ratings                           ; subjective opinion — host-owned scale
   {"glm-5.1"         {:clojure 7 :ux 5}
    "claude-opus-4-7" {:clojure 9 :ux 4}
    "gpt-5"           {:clojure 5 :ux 8}}

   :llm/eligibility-strict? true})        ; webapp: error a node, never run wrong model
----

Absent `:config` ⇒ an empty ratings table (`{}`) and the built-in
`escapement.llm.preferences/default-preferences` order — never a disk
fallback.

==== Three orthogonal pieces, each with one job

`:llm/preferences` — **the only ranking.** A sorted vector of
`{:provider P :model M}` pairs, highest priority first. Nothing else
reorders. Absent ⇒ `default-preferences`.

The `:needs` gate (a chart-node `params-fn` key; see
<<params-fn,`:needs`>>) — **filters, never ranks.** It removes
ineligible models from the preference-ordered list; the survivors stay
in preference order. A model rated `:clojure 7` and one rated
`:clojure 10` are interchangeable under `[:>= 6]` — preference order
alone decides which survivor runs. Do **not** expect "higher rating
wins."

`:llm/ratings` — **subjective, optional.** A host-owned `id → opinion`
table whose keys (`:clojure`, `:ux`, `:tier`, …) mix into the same
keyspace as the objective `eligibility-facts`. With nothing configured,
a subjective `:needs` clause matches nothing.

==== `:needs` syntax and the fact vocabulary

At a chart node the `:needs` key holds a **flat** `fact → constraint`
map (one nesting level). Each entry states its own rule by shape:

* bare value `v` ⇒ exact equality
* `[:>= n]` ⇒ inclusive numeric floor
* `[:<= n]` ⇒ inclusive numeric ceiling

Only `:>=` and `:<=` are accepted — there is deliberately no `:>` /
`:<` / `:=`. All clauses must hold (logical AND); empty/absent `:needs`
admits everything; a malformed entry throws an `ExceptionInfo` naming
the offending key. The keyspace mixes two sources uniformly:

* **Documented objective facts** — the stable vocabulary published as
  `escapement.llm.catalog/eligibility-facts`: `:vision?`,
  `:tool-call?`, `:reasoning?` (booleans), `:context-tokens`,
  `:max-output-tokens` (token counts), `:company`, `:family`,
  `:knowledge` (strings). "Min context window 20000" is just
  `:context-tokens [:>= 20000]` — the fact keys *are* the vocabulary,
  no special syntax.
* **Subjective rating keys** — any key the host invents in
  `:llm/ratings`. These mix into the *same* keyspace; the invocation
  layer never special-cases a key.

`:needs` is the ergonomic surface; `:model-policy` is its deprecated
canonical-nested alias (still accepted for one cycle). See
<<params-fn,the `params-fn` map>> for the full reference.

==== Fail-open vs fail-closed

When the `:needs` gate filters out *every* candidate, the default is
**fail-open**: the run proceeds on the unfiltered preference list and a
`:llm/model-policy-empty` transcript event records the gap (the CLI
bias — keep running). A webapp usually wants the opposite: setting
`:config :llm/eligibility-strict? true` makes the lib path
**fail-closed** — the node errors rather than silently run a model the
gate rejected.

==== Reference example

A host configures `llm-credentials` / `llm-config` (above) once at
startup. A two-node chart expresses a different `:needs` gate per node,
mixing an objective fact with a subjective rating:

[source,clojure]
----
(ns escapement.examples.skill-routed
  (:require
   [com.fulcrologic.statecharts.chart :as chart]
   [com.fulcrologic.statecharts.elements :refer [state transition final]]
   [escapement.chart.helpers :as h]))

(def agent
  (chart/statechart
   {:initial :refactor}

   ;; NODE 1 — Clojure refactor. :needs mixes an OBJECTIVE fact
   ;; (:tool-call?, from models-api.json) with a SUBJECTIVE rating
   ;; (:clojure, from :llm/ratings). Filter, not rank.
   (state {:id :refactor}
          (h/llm-conversation
           {:id        "refactor"
            :params-fn (fn [_env _data]
                         {:system "You are a Clojure refactoring agent."
                          :needs  {:tool-call? true
                                   :clojure    [:>= 7]}
                          :real-tools []
                          :allowed-events [{:event :refactor-done}]
                          :initial-user-message
                          "Rename `foo` to `bar` across src/, then emit :refactor-done."})})
          (transition {:event :refactor-done :target :design-review}))

   ;; NODE 2 — Design review. :needs mixes the OBJECTIVE fact :vision?
   ;; with the SUBJECTIVE rating :ux. Same chart, different gate.
   (state {:id :design-review}
          (h/llm-conversation
           {:id        "design-review"
            :params-fn (fn [_env _data]
                         {:system "You are a UX/design reviewer."
                          :needs  {:vision? true
                                   :ux      [:>= 6]}
                          :real-tools []
                          :allowed-events [{:event :review-done}]
                          :initial-user-message
                          "Critique the attached mockups, then emit :review-done."})})
          (transition {:event :review-done :target :finished}))

   (final {:id :finished})))
----

Resolution against the config above:

[cols="1,2,3,2,1",options="header"]
|===
| Node | `:needs` | Clears gate | Preferences pick | Provider
| `:refactor`
| `:tool-call? true` + `:clojure [:>= 7]`
| `glm-5.1` (clj 7 ✓), `claude-opus-4-7` (clj 9 ✓) — `gpt-5` dropped (clj 5)
| **`glm-5.1`** (first in preferences)
| `:z-ai-plan`
| `:design-review`
| `:vision? true` + `:ux [:>= 6]`
| only `gpt-5` (ux 8 ✓, vision ✓) — `glm-5.1`/`opus` dropped (ux 5 / 4)
| **`gpt-5`** (only survivor)
| `:openai`
|===

The gate **never reordered** anything — it removed ineligible models;
the sorted `:llm/preferences` chose among survivors. Node 2 shows the
gate overriding preference *priority*: `gpt-5` is last in preferences
yet selected because it is the only model clearing its gate.

The host invokes it with everything injected as data:

[source,clojure]
----
(require '[escapement.lib :as escapement])

(escapement/run
  {:chart       escapement.examples.skill-routed/agent
   :session-id  :req-42
   :credentials llm-credentials
   :config      llm-config})
;; zero disk reads, zero env sniffing — fully reproducible per request
----

=== Normalized public events: `escapement.lib.event-sink`

The raw transcript is internal and unstable. `escapement.lib.event-sink`
is a **pure normalization adapter** over `:transcript-tap` that maps
raw rows to a closed, stable public Malli event union and drops
internal/unmapped rows. Attach it via the host closure:

[source,clojure]
----
(let [adapter (escapement.lib.event-sink/make-adapter)]
  (escapement.lib/run
    {:chart c :session-id sid
     :transcript-tap (fn [row]
                       (doseq [e (escapement.lib.event-sink/feed! adapter row)]
                         (handle-public-event e)))}))
----

Streaming assistant text to a UI is the `:text-delta` variant — this
is the **supported** way; do not match raw `:llm/delta` transcript rows
by hand. Filter by `:invokeid` to stream one conversation:

[source,clojure]
----
:transcript-tap
(fn [row]
  (doseq [e (escapement.lib.event-sink/feed! adapter row)]
    (when (and (= :text-delta (:type e))
               (= "pitch" (some-> (:invokeid e) name)))
      (print (get-in e [:delta :text])) (flush))))
----

A complete runnable host example — two LLM phases authored with
`escapement.chart.helpers`, artifact-shared context, injected
`:credentials`/`:config`/`:initial-data`/`:session-dir`, and this
`:text-delta` streaming tap — is in `demos/lib/` (`bb -m
lib.embed-example`; see `demos/lib/README.md`). For vision input, gate
the node with `:needs {:vision? true}` and pass the base64 image
content block documented in *The `:llm-conversation` invocation*.

Entry points:

* `(escapement.lib.event-sink/make-adapter)` ⇒
  `{:feed (fn [row] -> [event …]) :ctx (fn [] -> ctx-map)}`. Stateful
  but instance-local — no globals, no producer mutation.
* `(escapement.lib.event-sink/feed! adapter row)` ⇒ `[event …]`
  (0, 1, or 2 events).
* `(escapement.lib.event-sink/normalize ctx row)` ⇒ `[event …]` —
  the pure transform (does not capture state).
* `(escapement.lib.event-sink/valid-event? event)` ⇒ boolean.
* `escapement.lib.event-sink/PublicEvent` — the closed Malli schema
  value (`[:multi {:dispatch :type}]`).

Every public event is a closed map with `:type` plus the correlation
triple `:session-id`, `:run-id` (captured from `:runner/started`),
and `:invokeid` (present only on LLM/tool events). Variants include
`:run-started`, `:chart-config`, `:run-done`, `:run-aborted`,
`:run-error`, `:chart-event`, `:chart-checkpoint`, `:llm-request`,
`:text-delta`, `:llm-response`, `:llm-retry`, `:llm-fallback`,
`:llm-error`, `:llm-continuation`, `:tool-call`, `:tool-result`, and
`:tool-validation-failure`. There is no native tool-call transcript
row, so the tool call/result/validation split is **synthesized** from
`:llm/tool-result` plus tool-attributed `:llm/error`/`:llm/retry`
rows; a categorized `:llm/error` with both `:category` and `:attempts`
yields a `:llm-fallback` then an `:llm-error`. Internal rows
(`:runner/tick`, `:llm/start`, …) normalize to `[]`.

=== Locked design decisions

These decisions are locked for the slice (the option schema passed a
human-approval checkpoint and is the public API contract):

. **Facade with a closed Malli schema.** `escapement.lib/run` is the
  single hosted entry point; `Options` is `{:closed true}`; unknown
  keys are rejected before any chart runs.
. **Pure-adapter event sink over `:transcript-tap`.**
  `escapement.lib.event-sink` is a normalization adapter only — no
  processor/runner/producer is modified; raw transcript-internal keys
  are normalized, not leaked.
. **OpenAI via Chat Completions SSE.** OpenAI/OpenRouter streaming
  uses the Chat Completions API with `stream:true`, accumulated then
  finalized so the buffered and streamed `Response` are equivalent.
. **Correlation in the host closure.** No host domain identifier is
  put into facade or event payloads. The host captures
  `:run-id`/`:session-id` in its own closure and correlates there.
. **Optional cumulative-usage delta field.** Streamed deltas may carry
  an optional running cumulative-usage field for live UX only. It is
  **not** a billing source — the final `Response` usage is
  authoritative.
. **`:run-id` and `:store` formalized now.** `:run-id` is generated by
  the facade, returned, and emitted on `:runner/started`; `:store` is
  an optional passthrough to `engine.env/new-env`.
. **Hermetic config + credentials are explicit data.** The facade
  reads no disk and no env. `:credentials` is a required closed-schema
  key (app-lifetime injection, like a DB pool); `:config` is optional
  and mirrors `.escapement.edn` but is host-supplied, never a disk
  fallback. Ratings/preferences flow as plain values threaded through
  the invocation context — no dynamic var, no process global — so
  concurrent runs with different `:config` resolve independently.
. **`:needs` is an eligibility *gate*, not a ranker.** It filters the
  preference-ordered candidate list; *all* ordering comes from the
  sorted `:llm/preferences`. Only `=` / `[:>= n]` / `[:<= n]` are
  supported. `:model-policy` is a deprecated alias for one cycle.
  Fail-open by default; `:llm/eligibility-strict? true` opts the lib
  path into fail-closed.
. **Explicitly deferred:** a `TranscriptSink` protocol, DB-backed
  stores beyond the `:store` passthrough, a broader lifecycle-hook
  taxonomy, and the daemon API. These are *not* available; do not
  depend on them.

=== Migration notes

This slice is **purely additive** — no caller changes are required:

* A new namespace (`escapement.lib`) and a new adapter namespace
  (`escapement.lib.event-sink`); no existing namespace's public
  signature changed.
* `escapement.runner/run!` still takes a single opts map
  (`:map => :map`); it gained only *optional* `:store`, `:run-id`, and
  `:cancel` destructuring and additive `:status` keys on
  `:runner/done` / the summary map. Existing consumers that ignore the
  new keys are unaffected; the CLI path is byte-for-byte unchanged
  (omitted `:run-id`/`:store`/`:cancel` ⇒ prior behavior).
* No `Options` schema change was needed for cancellation — `:cancel`
  was reserved in the locked schema up front.
* **Out of slice scope, flagged for the release step:** the embed
  smoke alias uses a `:local/root` dependency coordinate; a published
  release will need a `:git/url` + `:sha` (or Maven) coordinate
  instead. This is a packaging concern only, not a code change.

[[known-limitations]]
== Known limitations and roadmap

* **OpenAI Codex backend is reverse-engineered against the ChatGPT CLI
  auth flow.** OpenAI may change the protocol or revoke this path without
  notice. Use the `api` backend for production work.

* **Checkpoint-resume restarts in-flight conversations.** Re-entering a
  bound state on resume spawns a fresh worker with an empty message
  history. At-most-once cannot be guaranteed for side-effecting tools.

* **Sandboxing of third-party charts is deferred.** A chart can reference
  arbitrary tools and arbitrary side-effects through `:script` and
  `:on-entry`. There is currently no policy layer.

* **LLM token budgets are per-turn, not per-session.** Long iterative
  runs accumulate context. The per-turn output cap is catalog-driven (not
  a param); prompt for brevity, pick an appropriately-sized model, and
  watch the `:context-used-frac` field on `:llm/response` transcript
  events (see <<context-tracking>>).

* **Billing on successful turns only.** Token usage is authoritative
  only from the **final** `Response` of a completed turn. Usage from a
  partial, failed, or cancelled streamed turn is **discarded** — out
  of slice scope. The optional cumulative-usage delta field on
  streamed deltas is for live UX only and is **not** a billing
  source. Bill on successful turns only.

[[contributing]]
== Contributing and running tests

Tests run under bb with `bb test`. The task lives in `bb.edn` and
auto-discovers `test/**/*_test.clj`, requires each namespace, and runs
`clojure.test/run-tests`. The runner is `escapement.test.runner` (under
`bb_test/`).

[[add-chart]]
=== Adding a new chart

1. Create `src/escapement/examples/my_thing.clj`. Pattern after the demos.
2. Use `h/llm-conversation` for any LLM-bound state; wrap finals in a
   compound parent.
3. Add a unit test under `test/escapement/examples/my_thing_test.clj`
   using a `MockBackend` and (where applicable) stub tools.
4. Run via `escapement run escapement.examples.my-thing/agent`.

For host projects that want to keep charts and chart utility namespaces
outside the Escapement source tree, add an `.escapement.edn` at the
project root with `:source-paths` (and optionally `:default-chart`) —
see <<project-config>>.

=== Adding a new tool

1. `defrecord` implementing `escapement.tools.protocol/Tool`.
2. Provide a Malli `input-schema`; the runtime validates before `invoke`.
3. Return `{:result <string> :is-error <bool>}`. Strings only — the LLM
   sees a string.
4. Register in the chart's tool registry via `tp/register!` (or seed a
   custom registry).
5. Add a unit test under `test/escapement/tools/`.

=== Adding a new backend

1. Implement `escapement.llm.protocol/LLMBackend`.
2. Validate request and response with `escapement.llm.types` so chart
   authors see consistent shapes regardless of backend.
3. Add a `new-backend` constructor.
4. Wire into the CLI's `make-backend` if it should be selectable via
   `--backend`.
