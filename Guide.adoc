= Escapement
:toc: left
:toclevels: 3
:source-highlighter: rouge
:icons: font

_Escapement regulates LLM agents the way a watch escapement regulates a mainspring._

A guide to authoring, running, and extending statechart-driven autonomous
agents in this project.

[[introduction]]
== Introduction

Escapement is a Clojure/Babashka library for building coding agents
whose **control flow is a statechart**, not a free-form LLM loop. Workflows are
authored as Fulcrologic Statecharts; an LLM conversation is bound to a
(typically compound) state via the statechart library's invocation mechanism.
While that state is active, a background worker thread holds a live LLM
session, dispatches tool calls, and posts named events back to the chart's
queue. The chart decides what happens next.

Two kinds of tools are exposed to the LLM:

* **Real tools** — actual side-effecting operations (read file, run shell,
  eval Clojure). Calls are dispatched **inside the worker**; results are fed
  back into the conversation. The chart never sees them.
* **Event tools** — one synthetic tool per event the chart-author declares
  `:allowed-events`. When the LLM calls one, the runner validates the
  arguments against a Malli schema and posts the corresponding chart event
  (with the arguments as event data) onto the parent session's queue. The
  tool's "result" returned to the LLM is just an ack so the turn can continue.

The chart only ever sees the high-level domain events its author exposed; it
never sees `tool_use` blocks for real tools. This separation is the project's
key idea:

* Visibility — every LLM request, response, tool call, transition, and event
  is a JSONL transcript entry. Full replay is possible.
* Safety — the chart-author defines the LLM's vocabulary. The LLM can only
  influence chart progression by calling event-tools the author exposed.
* Reproducibility — chart logic is deterministic; only LLM choices are
  non-deterministic, and those choices are tightly scoped.
* Async by construction — the LLM runs on a worker thread, and each parallel
  region has its own worker. Multiple events per turn (fan-out) is natural.
* Resumability — working memory is checkpointed atomically (write-temp →
  rename) after every event-processing pass. Resume reloads the configuration
  and re-spawns invocations; processors are written to be idempotent on
  re-entry.

The runtime is **Babashka** for the agent process and CLI. Tests run on the
JVM (kaocha) because the statechart library's `simple` and `testing`
namespaces transitively pull `promesa`, which crashes under SCI. See
<<known-limitations>> and `SPIKE_FINDINGS.md`.

The dependency stack is small: `com.fulcrologic/statecharts 1.4.0-RC13`,
`metosin/malli`, `cheshire`, `babashka.process`, `org.babashka/http-client`,
and `com.fulcrologic/guardrails`.

[[quickstart]]
== Quickstart

Clone, set an API key, and run the hello chart. The CLI auto-detects an LLM
backend from any one of `ANTHROPIC_API_KEY`, `ZAI_API_KEY`, `OPENAI_API_KEY`,
or `OPENROUTER_API_KEY` (precedence in that order); no `--backend` flag is
required.

[source,bash]
----
git clone <this-repo>
cd escapement

# Any one of these works; z.ai and OpenRouter are cheap for dev.
export ANTHROPIC_API_KEY=...        # claude-sonnet-4-6 by default
export ZAI_API_KEY=...              # glm-4.6 (Anthropic-compat endpoint)
export OPENAI_API_KEY=...           # gpt-4o-mini default; OPENAI_MODEL overrides
export OPENROUTER_API_KEY=...       # openai/gpt-4o-mini default; OPENROUTER_MODEL overrides

escapement run escapement.charts.hello/agent
----

Or, equivalently, before `bbin install`:

[source,bash]
----
bb -m escapement.cli run escapement.charts.hello/agent
----

==== Multi-backend auto-fallback

When more than one credential is configured, Escapement wires a
multi-dispatch backend AND builds a preference-ordered list of model
ids (one per credential, in the precedence order above). At conversation
time, if a model errors out (HTTP 429, network blip, parse error, etc.)
the InvocationProcessor marks it `:down` for the rest of the process
and tries the next candidate. `:error.llm.backend` is only fired once
every candidate has failed. Each fallback is logged as
`[llm/model-down] <model> — <message>  next=[...]`, and every
`[llm/req]` / `[llm/resp]` line now shows the model in use, so the
TUI/log stream makes the switch visible.

Two ways for a chart to influence the auto-fallback list:

* `:model "..."` or `:models [...]` on the `:llm-conversation` node —
  explicit pick(s). When set, the auto-list is *not* consulted; only
  your strings are tried (with the same `:down`-marking fallback when
  you give a multi-element list).
* `:intelligence N` (1–10) on the `:llm-conversation` node —
  filters the auto-list to models whose rating (see
  `escapement.llm.models/intelligence`) is `>= N`. Useful when a
  state genuinely requires a strong model. If your configured
  credentials only provide weaker models the filter is dropped and an
  `:llm/intelligence-filter-empty` warning is emitted to the
  transcript.

==== Manual configuration

If you need to override the auto-detected backend (e.g. point at a different
endpoint or use a non-default model), pass the flags explicitly:

[source,bash]
----
escapement run escapement.charts.hello/agent \
   --backend api \
   --api-base-url https://api.z.ai/api/anthropic \
   --api-key-env ZAI_API_KEY \
   --model glm-4.6
----

Expected output:

[source]
----
session         <uuid>
transcript      .escapement/<uuid>/transcript.jsonl
checkpoint-dir  .escapement/<uuid>/checkpoints
final-config    [:run :finished]
----

The `.escapement/<session>/` directory contains:

* `transcript.jsonl` — every LLM request, response, tool call, chart
  transition, and checkpoint write, one JSON object per line.
* `checkpoints/<session>.edn` — atomic working-memory snapshot written after
  every event.

To probe the build/runtime:

[source,bash]
----
escapement info
----

To run the M7 iterative-coding smoke against a tmp directory:

[source,bash]
----
bb bb_test/m7_live_iterate.clj
----

[[core-concepts]]
== Core concepts

The vocabulary used throughout this guide:

Chart::
  A Fulcrologic statechart value. Built with
  `com.fulcrologic.statecharts.chart/statechart`. Composed of `state`,
  `parallel`, `final`, `transition`, `script`, `on-entry`, and `invoke`
  elements from `com.fulcrologic.statecharts.elements`. See the `statechart`
  skill or the library docs for the algorithm; this guide assumes familiarity
  with the basics.

LLM-bound state::
  A compound state whose body contains
  `(invoke {:type :llm-conversation :id ... :params <fn>})`. While the state
  is active, the runtime spawns a worker thread that holds a live LLM
  conversation. When the chart leaves the state, the worker is interrupted
  and the conversation dies. The authoring sugar is
  <<llm-conversation-helper,`h/llm-conversation`>>.

Real tool::
  A tool the LLM may call to act on the world (e.g. `:fs/read`,
  `:shell/run`). Implemented by `escapement.tools.protocol/Tool` and looked
  up in a tool registry. Real-tool calls are dispatched inside the worker;
  results loop back into the conversation. The chart never observes them.

Event tool::
  One synthetic tool per entry in the binding's `:allowed-events`. When the
  LLM calls `event__<name>(<args>)`, the worker validates `<args>` against
  the entry's `:data-schema` and posts a chart event named `<name>` with the
  validated input as event data.

Conversation lifecycle::
  Starts on state entry (with `:initial-user-message` if provided).
  Re-entered idempotently if the chart re-enters the bound state (the old
  worker is interrupted and a new one is spawned). Dies on state exit. See
  <<idioms-gotchas>> for what this implies for resume.

Transcript::
  A JSONL file written by `escapement.transcript`. Single-writer (one daemon
  thread); other threads enqueue events through a `LinkedBlockingQueue`.
  Lines are guaranteed intact and FIFO.

Checkpoint::
  EDN serialization of the chart's working memory, written via temp-file +
  atomic rename after every event-processing pass. See
  `src/escapement/engine/store.clj`.

Resume::
  Re-loading the latest checkpoint and continuing. The runner detects
  `:resume?` plus an existing non-empty configuration and skips `start!`. The
  library re-enters the saved configuration on the next event; invocation
  processors re-spawn workers idempotently.

[[authoring]]
== Authoring a chart, step by step

The four demo charts under `src/escapement/charts/` are arranged from
simplest to most complex. Read them in order — together they cover every
substantive pattern this library supports.

[[hello-walkthrough]]
=== Walkthrough: `hello.clj`

Full source: `src/escapement/charts/hello.clj`.

The chart binds an LLM conversation to a state, asks for a single
`event__done` call, and transitions to a final state that assigns the
greeting to the data model.

The namespace pulls in `chart`, `data-model.operations` (for `ops/assign`),
the standard element wrappers, and this project's authoring helpers:

[source,clojure]
----
(:require
 [com.fulcrologic.statecharts.chart :as chart]
 [com.fulcrologic.statecharts.data-model.operations :as ops]
 [com.fulcrologic.statecharts.elements :refer [state transition final script on-entry]]
 [escapement.chart.helpers :as h])
----

The system prompt is just a string. The LLM is told to call `event__done`
once with a `{"greeting": "..."}` payload:

[source,clojure]
----
(def system-prompt
  (str "When asked, call the `event__done` tool exactly once with `{\"greeting\":\"<a short hello "
       "in any language>\"}`. Keep the greeting under 30 characters. After the tool call, end your turn. "
       "Do not call any other tools."))
----

The chart itself:

[source,clojure]
----
(def agent
  (chart/statechart
   {:initial :run}
   (state {:id :run :initial :greeting}
          (state {:id :greeting}
                 (h/llm-conversation
                  {:id        "hello"
                   :params-fn (fn [_env _data]
                                {:system               system-prompt
                                 :real-tools           []
                                 :allowed-events       [{:event       :done
                                                         :data-schema [:map [:greeting :string]]}]
                                 :initial-user-message "Say hello."
                                 :max-tokens           120})})
                 (transition {:event :done :target :finished}
                             (script {:expr (fn [_env data]
                                              [(ops/assign :greeting
                                                           (get-in data [:_event :data :greeting]))])})))
          (final {:id :finished}))))
----

Notes:

* The outer `:run` state is required because a **top-level** `final` would
  empty the configuration set on entry (see `SPIKE_FINDINGS.md`). The
  convention throughout this project is to wrap the final in a compound
  parent state so callers can observe completion.
* `h/llm-conversation` (see <<llm-conversation-helper>>) expands to
  `(invoke {:type :llm-conversation ...})` with `:autoforward? true` set so
  `tell-llm` works.
* `:params-fn` is `(fn [env data] params-map)`. It is called every time the
  binding starts. It is the chart's chance to compute LLM parameters from
  current data-model state.
* `:allowed-events` declares the event vocabulary. Each entry is a map with
  `:event` (chart event keyword) and `:data-schema` (Malli). The runtime
  synthesizes the Anthropic tool definition (`event__done` here) and
  validates the LLM's tool input against the schema before posting the
  event.
* The `:done` transition is **structural** (it leaves the bound state),
  killing the conversation. The `script` action copies the event data into
  the data model. `get-in data [:_event :data ...]` is the standard pattern
  for reading the current event's payload inside a transition action — the
  library exposes the triggering event under the `:_event` key of the
  data-model snapshot passed to script `:expr`.

=== Three shapes of `:llm-conversation`

A single `:llm-conversation` invocation is just a live worker bound to a
chart state. The shape it takes is set entirely by which event-tools the
chart declares and how it reacts to them. Three common shapes, all
first-class and all built from the same machinery:

Concentrated query::
  A short conversation that decides one transition or produces one
  structured payload. Usually one `:initial-user-message`, zero or one
  event-tools, and the chart transitions out on `:llm.idle` (whose data
  carries the final assistant text). Useful for routing, classification,
  summarization, structured-output extraction, or "ask the model which
  of these branches to take." The conversation typically lives for a
  handful of round-trips and then the chart moves on.

Explore / agent state::
  The LLM is given real tools (file read/edit, shell, search, …) and
  runs autonomously for as many `tool_use → tool_result` rounds as the
  task needs — easily into the hundreds for a large refactor or audit.
  The chart declares a small set of *coarse* event-tools for milestones
  it actually branches on (`:patch-applied`, `:report-ready`,
  `:give-up`) and sits on the state until one fires. The chart never
  sees individual tool calls; that is the point.

Long turn with clarifying questions::
  Same shape as the agent state, plus an event-tool such as
  `event__question` that the LLM can call when it needs input it
  doesn't have. The chart routes that question elsewhere — to another
  `:llm-conversation` that decides how to answer, to a human-input
  node, to a stored FAQ — and posts the answer back into the original
  conversation via <<tell-llm-helper,`h/tell-llm`>>. The autonomous
  worker keeps running with its full context intact; from its point of
  view it asked a question and got an answer.

These are blends of one knob — *what event-tools you declare* — not
different invocation types. A chart can have all three shapes in
different states (or in parallel regions) at the same time. See
<<tokens-and-turns>> for the mechanics that make long runs work
(separate `:max-tokens` budget per round-trip, prompt caching across
turns) and the `:max-turns` / `:max-conversation-duration-ms` options
below for the worst-case guards.

=== Worked example: `scan.clj` — fan-out with a real tool

Full source: `src/escapement/charts/scan.clj`.

This chart adds one real tool (`:fs/read`) and demonstrates **fan-out**:
the LLM is expected to fire multiple `:found-bug` events and one
`:scan-complete`. Two ideas worth highlighting:

[source,clojure]
----
:real-tools     [:fs/read]
:allowed-events [{:event       :found-bug
                  :data-schema [:map
                                [:file :string]
                                [:line :int]
                                [:summary :string]]}
                 {:event       :scan-complete
                  :data-schema [:map [:total_findings :int]]}]
----

The chart never sees `:fs/read`. The LLM reads files, decides on findings,
calls `event__found_bug` once per finding, then `event__scan_complete`.

The trick is the internal transition for accumulating findings:

[source,clojure]
----
(transition {:event :found-bug :type :internal}
            (script {:expr (fn [_env data]
                             [(ops/assign :findings
                                          (conj (vec (:findings data))
                                                (-> data :_event :data)))])}))
----

`:type :internal` tells the algorithm to **not leave** the source state.
That matters here because leaving and re-entering `:scanning` would kill the
LLM worker. With an internal transition, the binding stays alive across
arbitrarily many `:found-bug` events. Only the terminal `:scan-complete`
uses a normal (external) transition to `:finished`.

=== Worked example: `parallel_demo.clj` — two LLMs at once

Full source: `src/escapement/charts/parallel_demo.clj`.

Two parallel regions, each with its own `:llm-conversation`. Region A is a
translator; region B is a summarizer. The two workers run concurrently on
different threads; tool-name collisions are impossible because event tool
names encode the event keyword (`event__translated` vs `event__summarized`).

[source,clojure]
----
(parallel {:id :work}
  (state {:id :translator :initial :translating} ...)
  (state {:id :summarizer :initial :summarizing} ...))

;; Both regions reach their per-region final → parallel raises done.state.work.
(transition {:event :done.state.work :target :finished})
----

`done.state.<id>` is raised by the library when all children of a
`parallel` element have reached a final substate. The parent then
transitions to its own final.

=== Worked example: `iterate.clj` — multi-state coding loop

Full source: `src/escapement/charts/iterate.clj`.

The most ambitious demo. One long conversation is bound at the top of
`:work`, exposing four event tools:

[source,clojure]
----
:real-tools      [:fs/read :fs/edit :fs/write]
:allowed-events  [{:event :spec-ready    :data-schema [:map [:summary :string]]}
                  {:event :patch-applied :data-schema [:map [:rationale :string]]}
                  {:event :retry         :data-schema [:map [:reasoning :string]]}
                  {:event :give-up       :data-schema [:map [:reason :string]]}]
----

The chart progresses `:read-spec → :propose-patch → :run-tests → :reflect`
with **all internal transitions** so the LLM's accumulated context survives
the whole loop:

[source,clojure]
----
(state {:id :read-spec}
       (transition {:event :spec-ready :target :propose-patch :type :internal}))

(state {:id :propose-patch}
       (on-entry {}
         (h/tell-llm {:expr (fn [_env data] (user-message-for-propose data))}))
       (transition {:event :patch-applied :target :run-tests :type :internal}
                   (script {:expr (fn [_env data]
                                    [(ops/assign :iterations
                                                 (inc (or (:iterations data) 0)))])})))
----

Two new ideas appear here:

* **Test execution is NOT an LLM tool.** It is a chart-controlled `script`
  action on `:run-tests` entry that dispatches `:shell/run` via the tool
  registry directly and posts `:tests-pass` or `:tests-fail` back to itself.
  This keeps test results out of the LLM's tool-loop and out of the
  conversation context unless the chart decides to surface them.
* **`h/tell-llm`** pushes a fresh user message into the live binding from
  inside the chart (see <<tell-llm-helper>>). Used here on
  `:propose-patch` entry to direct the LLM, and on `:reflect` entry to
  surface the test output on failure.

Read all four files together; they exercise every authoring pattern this
project currently supports.

A larger end-to-end demo lives under `demos/unit_test/` (a port of the
pi `unit_test` extension): seven phase prompts on disk, a parallel
REPL-manager region that supplies an nREPL port to the refine state via
shared data + one coordination event, and `:covers`-sealed test output.
See `demos/unit_test/README.md` for run instructions and architecture.

[[prompts]]
== File-based prompts

For non-trivial agents the inline `(str ...)` style of `hello.clj` and
`iterate.clj` rapidly becomes painful — prompts can be many KiB and they
typically need a few interpolated parameters. The
`escapement.prompts` namespace is the project's lightweight answer:

[source,clojure]
----
(require '[escapement.prompts :as p])

(p/render-file "demos/unit_test/prompts/behaviors.md"
               {:FILE     "src/myapp/core.clj"
                :FUNCTION "do-thing"})
----

Rules:

* Tokens are `{{IDENT}}` where `IDENT` matches `[A-Z][A-Z0-9_]*`.
* The substitution map is keyed by keyword, symbol, or string. Values
  are coerced via `str`.
* Any unresolved token in the template throws `ex-info` listing every
  missing name. Prompts must not ship with literal placeholders.
* No dependencies — `slurp` plus `clojure.string`, bb-safe.

The unit-test demo wires this into a small per-phase template registry
(`demos/unit_test/prompts.clj`) so each chart state's `params-fn` just
calls `(prompts/render-phase :write data)`. That keeps phase prompts
authoring-ergonomic on disk while the chart code stays focused on
control flow.

[[invocation]]
== The `:llm-conversation` invocation

This is the core of the project. The processor is defined in
`src/escapement/invocation/llm_conversation.clj`. Authors do not normally
construct it directly; they use the helpers in
`src/escapement/chart/helpers.clj`.

[[llm-conversation-helper]]
=== `h/llm-conversation`

Defined in `src/escapement/chart/helpers.clj:21`. Expands to an `invoke`
element of type `:llm-conversation` with `:autoforward? true` set.

[source,clojure]
----
(h/llm-conversation
 {:id        "scanner"      ; required; becomes the :invokeid
  :params-fn (fn [env data] ; required; returns the params map below
               { ... })
  :autoforward? true})      ; optional; defaults to true
----

`:autoforward?` controls whether the library hands chart events back to the
processor's `forward-event!`. You almost always want this true (it is what
makes `tell-llm` work).

=== The `params-fn` map

`params-fn` returns a map consumed by the processor. The keys it understands:

`:system`::
  Optional string. The system prompt sent to the LLM.

`:real-tools`::
  Optional selector controlling which real tools this conversation sees.
+
  * **Absent / `nil`** — expose EVERY tool currently in the registry. This
    is the recommended default: the CLI's registry already contains the
    eight built-ins plus anything self-registered by a required namespace
    (see <<custom-tool>>).
  * **Vector or set of keywords** — whitelist. Only the named tools are
    exposed to the LLM. Unknown keywords throw at conversation start.
+
  Tools the LLM never sees are still in the registry and still
  dispatchable from chart-side scripts; they are just absent from the
  Anthropic `tools` array.

`:allowed-events`::
  Optional vector of `{:event <kw> :data-schema <malli> :description <str>}`
  maps. Each becomes a synthetic Anthropic tool named `event__<encoded>`
  with `:input-schema` derived from `:data-schema`.

`:initial-user-message`::
  Optional string. If present, the worker starts in `:running` and sends
  this as the first user turn. Otherwise it starts in `:awaiting-user` and
  parks until a `:llm.user-message` event arrives via `tell-llm`.

`:model`::
  Optional string passed through to the backend. Examples:
  `"claude-opus-4-7"`, `"claude-sonnet-4-6"`, `"claude-haiku-4-5"`,
  `"glm-4.6"` (when targeting the z.ai compat endpoint). When set,
  Escapement uses *exactly this model* — auto-fallback across other
  configured backends is disabled for this state (your explicit pick
  is honored). If absent, the auto-fallback list kicks in (see
  `:models` and `:intelligence` below). Per-state selection is the
  point: one chart state can drive Opus for hard reasoning, the next
  Sonnet for routine edits, the next Haiku for cheap fan-out.

`:models`::
  Optional ordered vector of model id strings. Tried in order; on a
  backend failure (HTTP 429, network error, etc.) the next candidate
  is tried and the failing one is marked `:down` for the rest of the
  process so later turns and later invocations skip it. As with
  `:model`, an explicit list disables the auto-detected default
  fallback list — only the strings you name are tried.

`:intelligence`::
  Optional integer (1–10). Only meaningful when neither `:model` nor
  `:models` is set, i.e. when the conversation is using the
  auto-detected fallback list. With `:intelligence N` the auto-list is
  filtered to models whose intelligence rating (see
  `escapement.llm.models`) is `>= N`. Use this to say "this state
  needs at least Sonnet-class reasoning; if you only have a cheap
  model wired up, complain rather than silently downgrade." If the
  filter removes every candidate, the unfiltered list is used as a
  best-effort fallback and an `:llm/intelligence-filter-empty`
  warning is emitted to the transcript so you can spot the gap.

`:max-tokens`::
  Optional int; defaults to **8192** in the api backend's request builder.
  This caps generation in ONE assistant HTTP response — not the whole
  conversation, not a tool round-trip. See <<tokens-and-turns>> for the
  full mechanics, when to raise it, and how `:thinking` interacts with it.
  Required to be strictly greater than `:thinking`'s `:budget-tokens`
  when extended thinking is enabled.

`:temperature`::
  Optional number in `(0, 1]`. Use values near zero for deterministic
  tool-calling work, higher for creative generation. Don't combine with
  `:thinking` — Anthropic ignores temperature when extended thinking is on.

`:top-p` / `:top-k`::
  Optional sampling parameters passed straight through. Most charts won't
  need them; reach for `:temperature` first.

`:stop-sequences`::
  Optional vector of strings. The model halts as soon as any of them
  appears in its output (the matching sequence is excluded from the
  result). Useful for inline output formats.

`:thinking`::
  Optional map enabling Anthropic's extended-thinking mode for THIS
  state's worker:
+
[source,clojure]
----
{:type :enabled :budget-tokens 4096}
----
+
The model emits one or more `:thinking` (and possibly `:redacted_thinking`)
content blocks before its normal text/tool_use blocks. They are recorded
in the message history so the model can build on them across turns; the
chart never sees them — they pass through transparently. Set
`:budget-tokens` low enough to leave room within `:max-tokens` for the
actual answer.

`:tool-choice`::
  Optional. Forces the model's hand on tool selection:
+
* `:auto` (Anthropic default) — model decides whether to call a tool.
* `:any` — model MUST call some tool this turn.
* `:none` — model is forbidden from calling tools (text-only).
* `{:type :tool :name "fs_read"}` — model MUST call the named tool.
  Optional `:disable-parallel-tool-use true` forbids parallel calls.

`:metadata`::
  Optional `{:user-id "..."}`. Surfaces in Anthropic's audit/abuse
  tracking. Use a stable, non-PII identifier (e.g. a hash).

`:auto-cache?`::
  Boolean, **default `true`**. When true, any absent
  `:system-cache-control` / `:tools-cache-control` key is filled in
  with `{:type :ephemeral}` (Anthropic's 5-minute cache window —
  cheap; the 1-hour `:ttl :1h` variant costs noticeably more). Set
  `:auto-cache? false` to skip defaulting entirely (no cache markers
  emitted at all). See <<prompt-caching>> for the rationale.

`:system-cache-control` and `:tools-cache-control`::
  Optional cache_control markers. Each is one of:
+
* a marker map like `{:type :ephemeral}` (5-minute TTL — the default)
  or `{:type :ephemeral :ttl :1h}` (1-hour TTL, costs more to write)
* `false` — explicit "don't cache this one"
* absent / `nil` — falls through to the `:auto-cache?` default
  (`{:type :ephemeral}` when auto-cache is on)
+
`:system-cache-control` marks the system prompt; `:tools-cache-control`
stamps the LAST tool def so the prefix-through-end of `tools` is
cached. The biggest wins are in tool-heavy single-state loops (refine
in the unit-test demo is the canonical case). See <<prompt-caching>>
for the full explanation and when caching is wasted effort.

`:on-end-turn-event`::
  Optional chart event keyword fired to the parent when the LLM returns
  `:end_turn`. Defaults to `:llm.idle`. The event data carries
  `{:text "<final assistant text>" :from "<invokeid>"}` so chart-authors
  can route the assistant's output to another invocation (see
  <<multi-agent>>) or to a file via `capture-llm-output`.

`:max-turns`::
  Optional positive integer. Caps the number of LLM round-trips for this
  invocation. Size it for the shape of work the state is doing — a
  concentrated-query state may want a small cap (5–10) while an
  autonomous explore/agent state may legitimately want a large value or
  none at all. When exceeded the worker self-cancels with
  `:error.llm.max-turns {:limit N :turns N}` and dies.

`:max-conversation-duration-ms`::
  Optional positive integer. Wall-clock budget from worker start to a clean
  `:end_turn`. Like `:max-turns`, scale it to the state's shape; an
  autonomous refactor / exploration state may want a long ceiling or
  none. When exceeded fires `:error.llm.timeout
  {:elapsed-ms M :limit-ms N}` and dies. Doesn't replace `:http-timeout-ms`
  on the backend (that bounds individual HTTP calls).

`:conversation/id`::
  Optional opaque token used by the `openai-codex` backend as a prompt
  cache key (passed as `conversation_id` + `session_id` headers). The
  `api` backend ignores it.

NOTE: Error reporting now follows SCXML's `:error.x.y` convention. The
processor fires one of:
+
* `:error.llm.backend` — HTTP / parse / unexpected backend throw. Fired
  only after EVERY candidate model has been tried (see `:models` /
  `:intelligence`). The event data carries `:attempts`, a vector of
  `{:model :error}` entries (oldest first) so the chart can see which
  models were tried and what each one failed with.
* `:error.llm.tool-validation` — tool input failed schema after one retry.
* `:error.llm.unexpected-stop` — `:max_tokens` / `:stop_sequence` /
  `:refusal` stop reason.
* `:error.llm.max-turns` — `:max-turns` budget exceeded.
* `:error.llm.timeout` — `:max-conversation-duration-ms` exceeded.
* `:error.llm.worker-exception` — uncaught throwable in the worker.
+
Chart-authors catch the family with `(transition {:event :error.llm.*
:target :recover})` or pin to a specific cause. The old
`:on-error-event` option has been removed; the canonical event is always
fired.

[[tell-llm-helper]]
=== `h/tell-llm`

Defined in `src/escapement/chart/helpers.clj:39`. Emits a `script` that
posts a `:llm.user-message` event to the current session:

[source,clojure]
----
(on-entry {}
  (h/tell-llm {:expr (fn [env data] (str "Tests failed. Output:\n" (:last-test-output data)))}))
----

With `:autoforward? true` on the binding (the default), the library hands
the event to the processor's `forward-event!`, which converts it into a new
user message in the live conversation. The worker wakes up, appends the
message, and runs another turn.

IMPORTANT: `tell-llm` only works from **inside** the state that owns the
binding (or a descendant). Outside, there is no live invocation to forward
to, and the event is silently dropped.

When multiple `:llm-conversation` invocations are live concurrently (typical
in parallel regions / multi-agent charts), `tell-llm` broadcasts to ALL of
them. Use `h/tell-other-llm` (see <<multi-agent>>) when you want to target a
specific conversation by its `invokeid`.

=== Internal vs external transitions

If a transition's `:target` leaves the state that owns the binding (or
omits `:type :internal` and the target is the same state), the library
exits and re-enters the state, killing and re-spawning the worker. This is
sometimes what you want (each iteration is a fresh conversation) and
sometimes not (you want to keep the LLM's accumulated context).

* `scan.clj` uses `:type :internal` on `:found-bug` so the binding survives
  multiple findings.
* `iterate.clj` uses `:type :internal` throughout `:work` so one
  conversation drives the whole loop.

=== Bad tool-use

The processor validates every real-tool and event-tool input against its
schema. On failure, the LLM gets a corrective `tool_result` with
`is_error: true` and one retry. A second failure for the same tool-use id
fires `:error.llm.tool-validation` to the parent and the worker exits. See
`handle-tool-use-block` in
`src/escapement/invocation/llm_conversation.clj`.

=== Event-tool name encoding

The LLM-facing name for event `:foo-bar` is `event__foo_bar`. Qualified
keywords are flattened: `:my.ns/foo-bar` becomes `event__my_ns_foo_bar`.
Anthropic enforces alphanum/underscore in tool names, so any other character
in the keyword is replaced by `_`. See `kw->anthropic-name` in
`src/escapement/invocation/llm_conversation.clj:41`.

[[prompt-caching]]
=== Prompt caching and the conversation lifecycle

This is one of the more impactful knobs in the `params-fn` map and it is
not obvious. Read the lifecycle paragraph first, then the caching
recipe.

==== Conversation lifecycle is state lifecycle

Every `:llm-conversation` invocation owns a worker thread, a
`messages-atom`, and a `user-msg-queue`. They are all created when the
chart enters the state that hosts the invocation and torn down when the
chart leaves it. **A fresh state means a fresh conversation, starting
from the system prompt with an empty message history.** This is the
"escapement" principle: the chart drives lifecycle; the model never
chooses when to forget.

Practical consequences:

* The accumulated message history inside one state grows monotonically.
  An assistant `tool_use` response, the dispatched `tool_result`, the
  next assistant turn, etc. all stack up on `messages-atom`. The
  state's `:on-end-turn-event` parks the worker; another
  `tell-llm`/`:llm.user-message` resumes it with the history intact.
* Crossing a state boundary discards that history. The next state's
  worker starts cold.
* Parallel regions get independent conversations — no shared history.

==== Where Anthropic caching helps (and where it doesn't)

Anthropic prompt-caching reuses the *prefix* of a request when its
content matches a recent prior request. Cache hits return the cached
tokens at 0.1× the normal input price; cache writes cost 1.25×. The
prefix is everything UP TO the last `cache_control` marker — typically
the system prompt and the tool definitions.

* **Within a state**: a tool-heavy loop (refine in the unit-test demo
  is ~25 round-trips against a 13 KB system prompt and 8 tools) is the
  prime caching target. The system + tools prefix is identical on every
  HTTP call; only the growing tail of tool_result/text differs. Marking
  `system` and the tail-end of `tools` with `cache_control` makes every
  call after the first read those prefix tokens at 10% price.
* **Across states**: the cache window is 5 minutes (`{:type :ephemeral}`
  default) or 1 hour with the Anthropic extended-cache-ttl beta. So
  cache CAN technically survive a state transition if the next state's
  conversation happens to share a long prefix. In practice
  Escapement's phases use *different* system prompts on purpose, so
  cross-state hits are rare.

==== Defaults

**Caching is on by default.** An `:llm-conversation` state with no
cache keys set behaves as if you had written

[source,clojure]
----
{:system-cache-control {:type :ephemeral}
 :tools-cache-control  {:type :ephemeral}}
----

i.e. ephemeral (5-minute TTL) markers on both the system prompt and the
tail of the tool defs. The reasoning: Anthropic silently ignores
`cache_control` on prompts below the minimum cacheable size (1024
tokens for Sonnet/Opus, 2048 for Haiku), so the default is free for
small prompts and a clear win for any multi-turn state with a
substantial prefix. We default to the 5-minute TTL because the 1-hour
TTL (`:ttl :1h`) costs noticeably more to *write* — only worth it for
prefixes that the next state is likely to reuse.

To opt out:

* `:auto-cache? false` — skip defaulting entirely; no cache markers
  emitted (use this for guaranteed single-turn states with a 1K+ prompt
  you truly never reuse).
* `:system-cache-control false` or `:tools-cache-control false` —
  disable just one marker while letting the other auto-default.
* An explicit map for either key always wins (e.g.
  `:system-cache-control {:type :ephemeral :ttl :1h}` when you know
  the next state will reuse this same system prompt within the hour).

==== Overriding for the 1-hour TTL

Set the explicit map:

[source,clojure]
----
{:system               (slurp "prompts/refine.md")        ; ~13 KB
 :system-cache-control {:type :ephemeral :ttl :1h}        ; longer-lived
 :tools-cache-control  {:type :ephemeral :ttl :1h}
 :real-tools           [:fs/read :fs/edit :shell/run]
 :max-tokens           16384
 :allowed-events       [...]
 :initial-user-message "..."}
----

`tools-cache-control` stamps the *last* tool def because Anthropic
caches everything up through the marker — stamping the tail therefore
covers every tool. You normally want either both flags set to the same
value or neither: caching system but not tools means the tools section
ends the cache prefix, so the system prefix is the only thing reused.

==== When the cache wins are real

* Long system prompts (4 KB+).
* Many tool round-trips inside one state.
* Stable tool defs.
* Long-running refine loops, iterative coding agents, RAG-prompt agents.

==== When caching is wasted effort

* States that fire one turn and exit — the cache-write surcharge runs
  but no second turn ever uses the cached prefix.
* Charts whose system prompt is templated with per-turn data (the
  prefix differs every time, so cache always misses).

==== Verifying the cache

The Anthropic response includes `cache_creation_input_tokens` and
`cache_read_input_tokens` in `usage`. Our `Response.usage` schema
already carries both. Look at them in the transcript:

[source,bash]
----
jq -r 'select(.event == "llm/response") |
       (.data.usage // {}) | [.cache_creation_input_tokens,
                              .cache_read_input_tokens] | @tsv' transcript.jsonl
----

First request shows a creation count, subsequent ones show reads.

[[context-tracking]]
=== Context-window tracking

Anthropic never returns the context-window size on a response. We keep
a small lookup table at `src/escapement/llm/models.clj` and use it to
enrich the transcript so chart authors and reviewers can see, at any
point in a run, how much of the model's context the running
conversation has consumed.

==== `escapement.llm.models`

[source,clojure]
----
(require '[escapement.llm.models :as m])

(m/info "claude-opus-4-7")
;; => {:context-tokens 200000 :max-output-tokens 64000 :provider :anthropic}

(m/context-window "claude-sonnet-4-6")           ; => 200000
(m/max-output-tokens "claude-haiku-4-5")         ; => 32000
(m/approaching-limit? "claude-opus-4-7" 180000)  ; => true (≥ 80% of cap)
----

Resolution is exact-match-first, then longest-prefix. Dated ids like
`claude-opus-4-7-20260101` resolve to the `claude-opus-4-7` family
entry. Add new model rows to the `known-models` map at the top of
the namespace as Anthropic ships them.

==== Transcript enrichment

The worker stamps every `:llm/response` event with:

* `:usage`  — the Anthropic `usage` block (`:input-tokens`,
  `:output-tokens`, `:cache-creation-input-tokens`,
  `:cache-read-input-tokens` when present)
* `:model` — the model id reported by the API (or our request model)
* `:context-window` — the lookup-table value for that model, when
  known
* `:context-used-frac` — `:input-tokens` / `:context-window`, rounded
  to three decimals; absent when we can't look up the model

Additionally, whenever `:context-used-frac` ≥ 0.8 a separate
`:llm/context-warning` event is emitted into the transcript with the
same data. Charts can ignore it (the worker keeps running) or chain a
transition on it via the parent session's autoforward path if they
want to do something proactive (compact history, swap to a smaller
model for the next state, etc.).

==== Plotting usage from a transcript

[source,bash]
----
# Per-response: input tokens, output tokens, fraction of context used.
jq -r 'select(.event == "llm/response") |
       [(.data.usage["input-tokens"]   // 0),
        (.data.usage["output-tokens"]  // 0),
        (.data["context-used-frac"]    // 0)] | @tsv' transcript.jsonl
----

Pipe through `column -t` for tidy display, or into any plotting tool
for a per-turn growth curve.

==== Pre-flight token counting

Anthropic ships a separate Messages `count_tokens` endpoint for
predicting an input size before sending. Escapement does not call it
today; if you need a hard pre-flight gate, the simplest approach is to
add a chart-side script that calls `count_tokens` via `:shell/run` and
either transitions to a compaction state or trims `messages-atom`
before the request goes out.

[[tokens-and-turns]]
=== Tokens and turns — what `:max-tokens` actually limits

This trips people up the first time. The short version:

* `:max-tokens` caps generation in **one HTTP response** from the model.
  It is not a session budget, not a per-tool budget, not a per-chart
  budget. It only constrains "how long can the assistant's single
  message be."
* A tool round-trip is a **separate HTTP call** with a **separate fresh
  budget**. The worker emits one request, the model returns
  `stop_reason=tool_use` with some text + tool_use blocks (≤ `:max-tokens`
  for that response), the worker dispatches tools, appends `tool_result`
  to the message history, and POSTs the next request. The next response
  gets its own clean `:max-tokens` allocation.
* So a long, tool-heavy conversation can produce far more total tokens
  than `:max-tokens` over many turns. The only failure mode that
  `:max-tokens` actually causes is **truncation inside a single
  response** — for example, when you ask the model to write a 6 KB file
  in one shot and `:max-tokens` is set to 4 KB.

==== Stop reasons

When a response completes, Anthropic returns `stop_reason`:

* `:end_turn` — the model is done with this turn. The worker fires
  `:on-end-turn-event` (default `:llm.idle`) and parks in
  `:awaiting-user`. The chart can transition on the event if it cares
  about turn boundaries.
* `:tool_use` — the response contains at least one tool_use block. The
  worker dispatches the tools, appends results, and immediately POSTs
  the next request. Chart-side scripts don't see this.
* `:max_tokens` — the response was truncated at the cap. The worker
  fires `:error.llm.unexpected-stop {:stop-reason :max_tokens}`. The
  chart can either transition to an error path or just let the binding
  die. Treat this as a "bump `:max-tokens` for this state" signal.
* `:stop_sequence`, `:pause_turn`, `:refusal` — same as `:max_tokens`:
  fired as `:error.llm.unexpected-stop` with `:stop-reason` set to the
  specific cause. Charts that opt into `:stop-sequences` (or care about
  refusals) wire a transition on `:error.llm.unexpected-stop` and
  inspect `:_event :data :stop-reason`.

==== Default and recommended values

The wire-layer default is **8192**. That is high enough that most agent
turns (short reasoning + a tool call + a short summary) never truncate,
while staying well below every Claude 4 model's hard output ceiling
(64K+).

When to raise `:max-tokens` per state:

* **Whole-file authoring** — emitting a complete `.cljc` test file,
  a markdown report, or any long-form text. The unit-test demo uses
  8192 for the write/critique/patch states and 16384 for refine.
* **Long markdown analysis** — behavior or coverage reports that may
  span many sections.
* **Extended thinking enabled** — `:max-tokens` must be strictly greater
  than `:thinking`'s `:budget-tokens` (the cap covers BOTH the thinking
  blocks and the visible answer). A working pair is e.g.
  `{:max-tokens 16384 :thinking {:type :enabled :budget-tokens 8192}}`.

When NOT to raise:

* **Routine tool-driven states** — extra budget is just extra room for
  the model to ramble; it doesn't make tool work better.
* **Per-call rate-limit sensitivity** — higher caps don't cost more if
  the model stops earlier (you pay per token actually generated), but
  they DO raise the per-request rate-limit allotment used.

==== Cost note

Anthropic bills per token actually generated, not per `:max-tokens`
ceiling. Raising the cap doesn't cost more on its own — it just gives
the model permission to produce more. Real cost driver is the number of
tokens in the request (your accumulated message history and system
prompt). Use `cache_control` markers on `system` and stable message
prefixes to drive that down; see `escapement.llm.cache` and the
`:system-cache-control` / `:cache-control` keys in the type schemas.

==== If you really want a continuation

The current worker has no automatic continuation for
`stop_reason="max_tokens"`. You can build one chart-side: catch
`:error.llm.unexpected-stop`, inspect `:_event :data :stop-reason`, send a
follow-up via `h/tell-llm` ("continue your previous response"), and let
the model pick up. That's a chart decision, not a library default.

[[web-tools]]
== Web tools: `:web/search` and `:web/fetch`

Two built-in tools give the LLM first-class web access without dragging full
HTML into the context window. `:web/fetch` is always registered in
`default-registry`; `:web/search` is registered **only when `GEMINI_API_KEY`
is set in the environment at namespace-load time**, so a chart running
without a key never advertises a search tool the LLM would only discover by
calling it and failing. Opt in explicitly via `:real-tools [:web/search
:web/fetch]` when you whitelist.

NOTE: The `:web/search` record still defends itself with a
`"GEMINI_API_KEY not set"` error result if someone constructs and registers
it manually after the namespace has loaded — but the recommended path is to
set the env var before the JVM/bb process starts.

=== `:web/search`

Google Search grounding via the Gemini API. Returns up to `max-results`
(default 5, max 10) results as an EDN vector of `{:title :url :snippet}`.

Input schema::
+
[source,clojure]
----
{:query       "string, required"
 :max-results "int 1..10, optional, default 5"}
----

Configuration::
* `GEMINI_API_KEY` — required. Get one at https://aistudio.google.com/apikey.
  If missing, the tool returns `{:is-error true :result "GEMINI_API_KEY not set"}`
  — it never throws.
* `GEMINI_SEARCH_MODEL` — optional model override. Default `gemini-2.5-flash`
  (grounding-eligible, free tier).

Result shape (example)::
+
[source,clojure]
----
[{:title "Clojure Guides"
  :url   "https://clojure.org/guides"
  :snippet "Clojure is great for data."}
 ...]
----

=== `:web/fetch`

HTTP `GET` a URL, streaming the body to a temp file at
`${java.io.tmpdir}/escapement-fetch/<uuid><ext>`. The result is small EDN
metadata plus a short raw preview — the **full body lives on disk**, not in
the LLM's context.

Input schema::
+
[source,clojure]
----
{:url        "string, required"
 :max-bytes  "int 1024..50_000_000, optional, default 5_000_000"
 :timeout-ms "int 100..120_000, optional, default 30_000"}
----

Result map::
+
[source,clojure]
----
{:url          "https://..."
 :final-url    "https://..."         ; after redirects
 :status       200
 :content-type "text/html; charset=utf-8"
 :bytes        412334
 :saved-to     "/tmp/escapement-fetch/abc.html"
 :title        "..."                 ; nil unless HTML
 :preview      "first ~500 chars of body, raw"
 :truncated    false}
----

`:is-error` is true only for network failure, timeout, or non-2xx status. A
body that exceeds `:max-bytes` is **not** an error — it is truncated on
disk and `:truncated true` is set in the result.

=== Recipe: search → fetch → read slices off disk

The intended flow keeps context small:

. `:web/search` returns a few snippets + URLs. Most questions are answered here.
. When a snippet isn't enough, `:web/fetch` saves the chosen URL to disk and
  returns metadata + a tiny preview.
. The LLM then composes existing tools to read only what it needs:
+
[source,clojure]
----
;; grep for the section you care about
{:tool :fs/grep   :pattern "deprecation"   :path "/tmp/escapement-fetch/abc.html"
                  :output-mode "content"   :context 3}

;; read a numbered window of the file
{:tool :fs/read   :path "/tmp/escapement-fetch/abc.html"
                  :offset 1200 :limit 80}

;; convert HTML to clean text via shell if pandoc/html2text is available
{:tool :shell/run :command "pandoc -f html -t plain /tmp/escapement-fetch/abc.html | head -200"}
----

Sandboxing the fetch (Docker, sandbox-exec, firejail) is an operator concern
— the tool itself does no isolation.

[[human-interaction]]
== Human interaction and the TUI

A chart can ask the human for input via the `:human-input` invocation. The
chart-author declares what to ask (free text, single-select pick, etc.); a
pluggable `HumanRenderer` decides how. Production wiring uses the
persistent TUI; tests inject a `StubRenderer` that returns scripted
answers.

=== The `:human-input` invocation

Defined in `src/escapement/invocation/human_input.clj`. Spawned on state
entry; posts `:human.answer {:answer <value>}` to the parent session when
the user responds, then dies.

Authoring sugar lives in `escapement.chart.helpers`:

[source,clojure]
----
(state {:id :ask-name}
  (h/human-input
    {:id "ask"
     :params-fn (fn [_env _data]
                  {:kind          :text
                   :prompt        "What's your name?"
                   :answer-schema [:string {:min 1}]})})
  (transition {:event :human.answer :target :greet}
              (script {:expr (fn [_ d]
                               [(ops/assign :name
                                            (get-in d [:_event :data :answer]))])})))
----

Supported `:kind` values:

* `:text` — free-text line. Returns a string.
* `:select` — single pick from `:options [{:label … :value …}]`. Returns
  the chosen `:value`.
* `:multi-select` — same shape, returns a vector of `:value`s.
* `:confirm` — y/n with `:default`. Returns boolean.
* `:progress` — non-blocking progress indicator (driven by forwarded
  `:human.progress` events; v1 just no-ops to `:answer :done`).
* `:custom` — call `(:render params)` with `[env data]` and return its value.

Events the chart receives:

* `:human.answer {:answer <value>}` on success.
* `:human.cancelled {}` on user-cancel (Esc on a modal).
* `:error.human.invalid-answer {:errors … :answer …}` when an
  `:answer-schema` rejects the user's input.
* `:error.human.worker-exception {:message …}` on a renderer throwable.

Catch error families with `(transition {:event :error.human.* :target
:recover})`.

=== `with-llm-questions` — LLM-asks-human pattern

For the common case where you want an LLM to be able to consult the human
mid-conversation (e.g. design decisions, free-text clarifications), the
`(h/with-llm-questions {...})` helper produces a compound state bundling:

* an `llm-conversation` invocation on the bubble's parent state (so the
  conversation survives the human-input detour);
* a `:converse` child state where the user's `:exit-transitions` fire;
* two ask states (`:ask-choice`, `:ask-text`) that pop the corresponding
  `human-input` modal;
* automatic `tell-llm` of the human's answer back to the live LLM,
  prefixed with `"User chose: "` or `"User said: "`.

Two event-tools are injected into the LLM's `:allowed-events`:

* `event__question_ask_choice {:question :string :options [...]}` —
  prompts a `:select` modal.
* `event__question_ask_text {:question :string}` — prompts a `:text` modal.

[source,clojure]
----
(state {:id :run :initial :work}
  (h/with-llm-questions
    {:id        :work
     :params-fn (fn [_ _]
                  {:system "..."
                   :real-tools [:fs/read :fs/write]
                   :initial-user-message "go"})
     :exit-transitions
     [(transition {:event :done :target :finished})]})
  (final {:id :finished}))
----

Requires an interactive chart (see <<interactive-marker>>) — without a
`HumanRenderer` the ask states stall.

[[interactive-marker]]
=== Interactive chart marker

Chart authors declare a chart as interactive via Clojure var metadata:

[source,clojure]
----
(def ^{:interactive? true} agent (chart/statechart …))
----

The CLI reads this on `load-chart-with-meta` and:

* Refuses to start an interactive chart without a TTY, unless `--no-tui`
  was passed (in which case the stdin fallback renderer is used).
* Enables the persistent TUI by default when a TTY is available.
* Wires up `escapement.tui/->renderer` as the `HumanRenderer`, so modals
  pop in the TUI's bottom region.

Non-interactive charts still get a stdin renderer for any `:human-input`
states they happen to invoke (fail-soft default), but the TUI itself stays
off unless `--tui` is explicit.

=== The TUI

`src/escapement/tui.clj`. JLine-backed persistent display, on a single
input thread, with a modal-state machine and an in-memory line buffer.
Layout:

----
┌──────────────────────────────────────────────────────────────┐
│ escapement · <chart-sym> · <session-short>                  │
├──────────────────────────────────────────────────────────────┤
│ states: [:run :ask-name]                                     │  ← live config
│ [runner] started …                                           │
│ [llm/req] n-messages=3                                       │
│ [llm/resp] stop=tool_use tokens=in:100/out:17                │
│ [tool] name=event__done input={greeting "Hola!"}             │
│ [chart] event=:done config=[:run :finished]                  │
├──────────────────────────────────────────────────────────────┤
│ ▸ What's your name? alice                                    │  ← modal
└──────────────────────────────────────────────────────────────┘
 Esc=interrupt   Ctrl-C=quit   PgUp/PgDn=scroll
----

Wiring:

* Status line shows the current chart configuration. Driven by
  `:runner/start-config` and `:runner/event-processed` transcript events.
* Scrollback buffer holds the last ~2000 transcript lines (PgUp/PgDn to
  navigate, Home/End to jump). Consecutive duplicate lines collapse into
  `… (xN)`. `:runner/tick`, `:runner/quiescent`, and `:checkpoint/written`
  are suppressed from scrollback (still in JSONL).
* `Esc` (when no modal is open) posts `:ui.interrupt` to the chart's
  session — the chart decides what to do with it (e.g. transition to a
  `:cancelled` state). With a modal open, `Esc` cancels just the modal.
* `Ctrl-C` posts `:ui.quit` and tears down the TUI.

Atomic frames are used when the terminal advertises Mode 2026
(Synchronized Output) — detected at startup via DECRQM. iTerm2 (recent),
kitty, wezterm, foot, ghostty, and contour qualify; Apple Terminal does
not and falls back to per-frame writes (still flicker-light, just not
guaranteed atomic). On exit the alt-screen buffer is left, restoring your
shell scrollback exactly as it was before.

[[multi-agent]]
== Multi-agent / team patterns

Multiple `:llm-conversation` invocations can run concurrently (typically
under parallel regions, or as siblings of one parent state). The library
provides three primitives for routing between them.

=== `:target` routing on `:llm.user-message`

`tell-llm` posts a `:llm.user-message` to the chart's session; with
autoforward enabled, EVERY live `:llm-conversation` invocation's
`forward-event!` receives it. With a `:target <invokeid>` in the event
data, only the matching invocation accepts. Comparison normalizes
keyword and string invokeids transparently via
`escapement.invocation.llm-conversation/->id-str`, so `:id :researcher`
and `:id "researcher"` are interchangeable.

=== `h/tell-other-llm`

Sugar for the targeted case:

[source,clojure]
----
(h/tell-other-llm
  {:target "advisor"                  ; or a fn (fn [env data] invokeid)
   :expr   (fn [env data]
             (str "Lead's plan:\n" (:plan data) "\n\nDoes this hold up?"))})
----

Use this when the chart-author knows statically which conversation
receives the message. Plain `tell-llm` continues to broadcast.

=== `:on-end-turn-event` payload

Every `:end_turn` now fires the configured `:on-end-turn-event` (default
`:llm.idle`) with `{:text "<final assistant text>" :from "<invokeid>"}`
in the data. That's the wire for routing one LLM's output to another:
catch the event, inspect `:from`, format `:text` into a follow-up prompt,
`tell-other-llm` it elsewhere.

=== File-backed artifact helpers

For agent pipelines that produce text artifacts to be embedded in later
prompts, three helpers in `escapement.chart.helpers` write to and read
from `<session-dir>/artifacts/<name>`:

`(h/capture-llm-output)` / `(h/capture-llm-output {:as "x.md"})`::
  Returns a script. Used in a transition reacting to `:llm.idle`. Writes
  `:_event :data :text` to `<session-dir>/artifacts/<name>` atomically
  (temp + rename). Default `:as` is the producing invokeid (`:from`).
  Logs `:artifact/captured {:name N :bytes B}` to the transcript.

`(h/render-template tmpl env)` / `(h/render-template tmpl env extras)`::
  Pure-ish substitution. Mustache-light `{{name}}` tokens are resolved
  against `<session-dir>/artifacts/<name>`. `{{output}}` is reserved for
  in-flight text passed via `extras` (used by `forward-llm-output`).
  **Throws** `ex-info {:reason :missing-artifact ...}` on any unresolved
  token — fail-fast so a typoed prompt doesn't ship malformed text to the
  LLM.

`(h/forward-llm-output {:to :template :as :capture?})`::
  Capture + format + targeted `tell-other-llm` in one step. Writes a file
  (unless `:capture? false`), renders the template with `{{output}}`
  bound to the just-arrived text, then sends a `:llm.user-message`
  targeted at `:to`.

[source,clojure]
----
;; Five-state agent pipeline (researcher → writer → editor)
(state {:id :researching}
  (h/llm-conversation
    {:id "researcher"
     :params-fn (fn [_ _] {:initial-user-message "Research X"})})
  (transition {:event :llm.idle :target :writing}
    (h/capture-llm-output)))                ; → artifacts/researcher

(state {:id :writing}
  (h/llm-conversation
    {:id "writer"
     :params-fn (fn [env _]
                  {:initial-user-message
                   (h/render-template
                    "Research:\n\n{{researcher}}\n\nWrite a draft."
                    env)})})
  (transition {:event :llm.idle :target :editing}
    (h/capture-llm-output)))                ; → artifacts/writer

(state {:id :editing}
  (h/llm-conversation
    {:id "editor"
     :params-fn (fn [env _]
                  {:initial-user-message
                   (h/render-template
                    "Draft:\n\n{{writer}}\n\nPolish for clarity."
                    env)})})
  (transition {:event :llm.idle :target :done}
    (h/capture-llm-output)))                ; → artifacts/editor
----

Latest write wins. Keep history by picking versioned filenames
(`(str "draft-" iteration ".md")`).

[[backends]]
== LLM backends

The `LLMBackend` protocol is one method, `send-turn`. Defined in
`src/escapement/llm/protocol.clj`. Four implementations ship.

=== `escapement.llm.api` — Anthropic-compatible HTTP

Defined in `src/escapement/llm/api.clj`. Near-passthrough to the Anthropic
Messages API. Works against any service that speaks that wire format.

[source,clojure]
----
(require '[escapement.llm.api :as api])

;; Anthropic
(api/new-backend {:base-url      "https://api.anthropic.com"
                  :api-key       (System/getenv "ANTHROPIC_API_KEY")
                  :default-model "claude-sonnet-4-5"})

;; z.ai (Anthropic-compatible endpoint, cheap dev option)
(api/new-backend {:base-url      "https://api.z.ai/api/anthropic"
                  :api-key       (System/getenv "ZAI_API_KEY")
                  :default-model "glm-4.6"})
----

The auth mode is auto-sniffed from the base URL: `z.ai` → `Authorization:
Bearer <key>`; anything else → `x-api-key: <key>` plus `anthropic-version:
2023-06-01`. Override with `:auth-mode :bearer` or `:auth-mode :x-api-key`.

`cache_control` markers are passed through verbatim — both Anthropic and
z.ai consume them natively.

NOTE: z.ai does not currently return `cache_creation_input_tokens` and does
not require the `anthropic-version` header. Both differences are tolerated
silently by the request builder and the usage parser.

z.ai's published GLM family (current as of authoring) is tracked in
`escapement.llm.models`: `glm-5.1`, `glm-5`, `glm-5-turbo`, `glm-4.7`,
`glm-4.7-flashx`, `glm-4.7-flash`, `glm-4.6` (200K context), and the
`glm-4.5*` and `glm-4-32b-0414-128k` family (128K). Pass any of them as
`:default-model` or per-state `:model`.

=== `escapement.llm.openai` — OpenAI Chat Completions / OpenRouter

Defined in `src/escapement/llm/openai.clj`. Sibling of the Anthropic
backend. Accepts the same internal `Request` map and translates to the
OpenAI Chat Completions wire format. Works against any OpenAI-compatible
endpoint: OpenAI itself, OpenRouter (multi-provider broker), local
llama.cpp / vLLM servers, Codex-style coding models served via OpenAI
shape, etc.

[source,clojure]
----
(require '[escapement.llm.openai :as openai])

;; OpenAI
(openai/new-backend {:base-url      "https://api.openai.com/v1"
                     :api-key       (System/getenv "OPENAI_API_KEY")
                     :default-model "gpt-4o-mini"})

;; OpenRouter (set Referer/Title headers when publishing usage)
(openai/new-backend {:base-url      "https://openrouter.ai/api/v1"
                     :api-key       (System/getenv "OPENROUTER_API_KEY")
                     :default-model "openai/gpt-4o-mini"
                     :extra-headers {"HTTP-Referer" "https://example.com"
                                     "X-Title"      "my-app"}})
----

Translation rules:

* Our `:system` becomes the leading `role: "system"` message.
* Assistant `:tool_use` blocks fold into `tool_calls`; assistant text and
  tool-calls live on a single OpenAI message.
* Each `:tool_result` user-block fans out into its own
  `role: "tool"` message (OpenAI does not batch tool results like Anthropic
  does). `:is-error` is surfaced inline as a `[error]` prefix (OpenAI has no
  native flag for it).
* `:thinking`, `:redacted_thinking`, and all `cache_control` markers are
  silently dropped (OpenAI's prefix cache is implicit and not addressable).
* `:max-tokens` flips to `max_completion_tokens` for newer models
  (`gpt-5*`, `gpt-4.1*`, `o*`) and stays as `max_tokens` for legacy
  (`gpt-3.5*`, `gpt-4-*`, `gpt-4o*`).
* OpenAI's `usage.prompt_tokens_details.cached_tokens` is surfaced as
  `:cache-read-input-tokens` for transcript parity with the Anthropic
  backend.

CLI auto-detect: `OPENAI_API_KEY` routes to the OpenAI base URL,
`OPENROUTER_API_KEY` routes through the OpenAI backend at OpenRouter's
endpoint. `OPENAI_MODEL` / `OPENROUTER_MODEL` env vars override the default
model strings.

=== `escapement.llm.openai-codex` — ChatGPT subscription via OAuth

Defined in `src/escapement/llm/openai_codex.clj` (entry point) and the
`openai_codex/` sub-package. Routes to
`https://chatgpt.com/backend-api/codex/responses` using an OAuth 2.0 +
PKCE token bound to a ChatGPT Plus, Pro, Business, or Enterprise account.
No OpenAI API key is required; billing is against your subscription's
per-tier message limits.

==== Constructor

[source,clojure]
----
(require '[escapement.llm.openai-codex :as codex])
(codex/new-backend {:default-model "gpt-5.1-codex"})
----

==== Authentication

[source,bash]
----
escapement login codex   # one-time, opens browser for ChatGPT OAuth
escapement logout codex  # remove cached credentials
----

Credentials are saved to `~/.escapement/openai-auth.json` (mode 0600).
The backend refreshes the token automatically when it is within 60 seconds
of expiry.

==== Available models

* `gpt-5.2-codex` — latest flagship Codex model (supports `xhigh` reasoning)
* `gpt-5.2` — GPT-5.2 general purpose
* `gpt-5.1-codex` — standard Codex model *(default)*
* `gpt-5.1-codex-max` — extended context Codex variant
* `gpt-5.1-codex-mini` — lighter Codex variant (lower quota cost)
* `codex-mini-latest` — legacy mini alias
* `gpt-5.1` — GPT-5.1 general purpose

Anthropic-style model names (`claude-opus-4-7`, `claude-sonnet-4-6`) are
silently mapped to `gpt-5.2-codex`; `claude-haiku-4-5` maps to
`gpt-5.1-codex-mini`.

==== Reasoning effort

Pass a `:reasoning` key in the params map (value overrides the default):

[source,clojure]
----
{:reasoning {:effort "high" :summary "auto"}}
----

Valid effort values: `none` (gpt-5.1/gpt-5.2 general only), `low`,
`medium` (default), `high`, `xhigh` (gpt-5.2/codex-max only).

==== Subscription billing

IMPORTANT: This backend authenticates against `chatgpt.com/backend-api`
using an OAuth token bound to your ChatGPT Plus, Pro, Business, or
Enterprise subscription. Usage counts against your subscription's per-tier
message limits (Plus is approximately 30-150 messages per 5-hour window as
of May 2026; see your ChatGPT plan for current quotas). It does NOT bill
the OpenAI API meter.

**This path is for personal development use with your own subscription.**
It is not sanctioned by OpenAI for redistribution or multi-user services.
If you need multi-user or production deployment, use a pay-per-token
backend (the `api` backend above for Anthropic, or a future OpenAI
Platform API backend).

==== Limitations vs `api` backend

* `:max-tokens` is silently ignored (not accepted by the ChatGPT backend).
* `:temperature`, `:top-p`, `:top-k`, `:stop-sequences`, `:tool-choice`
  are silently ignored (reasoning models do not accept them).
* Extended-thinking is replaced by the reasoning effort knob (`:reasoning`
  key described above).
* `cache_control` markers are no-ops; a debug log line is emitted when
  they are present.
* Only GPT-5.x reasoning models are available; there is no cheap
  Haiku-equivalent.
* Stateless: `store: false`. The full conversation is re-sent on every
  turn (no server-side caching across turns beyond reasoning summaries).

=== `escapement.llm.multi` — multi-backend dispatcher

Routes each request to a sub-backend based on the requested `:model`. A
chart that asks for `claude-sonnet-4-6` in one state and `gpt-5.2-codex`
in the next will reach Anthropic and the codex subscription endpoint
respectively, with no caller changes.

[source,clojure]
----
(require '[escapement.llm.api          :as anthropic]
         '[escapement.llm.openai-codex :as codex]
         '[escapement.llm.multi        :as multi])

(def backend
  (multi/new-backend
    {:routes          [[#"^claude-" (anthropic/new-backend {...})]
                       [#"^gpt-5"   (codex/new-backend {})]]
     :default-backend (anthropic/new-backend {...})}))
----

Matchers may be a regex, a set of exact-match strings, or a predicate
`(fn [model-string] boolean)`. Routes are tried in order; first match
wins. If no route matches, `:default-backend` handles the request, or an
`ex-info` is thrown when no default is configured.

The CLI assembles this dispatcher automatically when more than one
credential is available — see <<cli>> for the default route table.

=== `escapement.llm.cache` — content-addressed disk cache

Defined in `src/escapement/llm/cache.clj`. Wraps any `LLMBackend` and
caches by SHA-256 over `(model, system, messages, tools)`. Opt-in via
`ESCAPEMENT_LLM_CACHE=1` or by explicit construction. Useful for
deterministic dev runs against expensive backends.

[[tools]]
== Tools

The `Tool` protocol (`src/escapement/tools/protocol.clj:18`):

[source,clojure]
----
(defprotocol Tool
  (tool-name    [t])  ; keyword, e.g. :fs/read
  (description  [t])  ; short string for the LLM
  (input-schema [t])  ; Malli schema
  (invoke       [t input]))  ; returns {:result <string> :is-error <bool>}
----

A registry is just an atom of `{tool-name → tool}`. Construct with
`tp/new-registry` or seed all five builtins with
`builtin/new-builtin-registry`. `tp/dispatch` validates the input against
the tool's schema before invoking; validation failures are returned as
`{:result <pretty error> :is-error true}` so the LLM gets a corrective
`tool_result` rather than a thrown exception.

`tp/tool->anthropic-tool-def` produces the JSON Schema that the LLM sees,
using `malli.json-schema/transform`. Qualified keywords are flattened
(`:fs/read` → `"fs_read"`).

=== Built-in tools

Defined in `src/escapement/tools/builtin.clj`. All eight are available
from both bb and JVM. The filesystem and search tools are designed to
sit at Claude-Code-parity ergonomics for the LLM.

`:fs/read`::
  Read a UTF-8 text file. Input: `{:path :string
  :offset (? pos-int?) :limit (? pos-int?)}`. Output is `cat -n` style:
  6-digit right-padded 1-based line numbers, a tab, then content. Default
  read window is 2000 lines from the top; `offset`/`limit` page through
  larger files. When more lines remain past the window the result ends
  with a `... [N more lines; read with :offset M]` notice telling the
  model exactly how to fetch the next chunk. Files larger than 200 KiB
  are byte-truncated up front before line-numbering.

`:fs/write`::
  Atomic UTF-8 write. Input: `{:path :string :content :string}`. Writes
  via temp-file + `ATOMIC_MOVE`. Creates parent directories.

`:fs/edit`::
  String-replacement edit. Input: `{:path :string :old-string :string
  :new-string :string :replace-all (? :boolean)}`. By default
  `old-string` must occur exactly once — the LLM is forced to supply
  enough context for an unambiguous edit. Pass `replace-all true` to
  replace every occurrence (the response then reports the count).
  Indentation in `old-string` must match the file byte-for-byte. The
  result reports replacement count; identical `old-string`/`new-string`
  is rejected rather than written as a no-op.

`:fs/multi-edit`::
  Atomic sequence of string-replacement edits to one file. Input:
  `{:path :string :edits [{:old-string :string :new-string :string
  :replace-all (? :boolean)} ...]}`. Edits are applied in order to the
  in-memory content; the file is written only if ALL edits succeed.
  Later edits can operate on the output of earlier ones. On failure
  the response identifies the failing edit index (`edit #N of M`) and
  the file is unchanged.

`:fs/glob`::
  Find files matching a glob pattern (e.g. `**/*.cljc`). Input:
  `{:pattern :string :cwd (? :string) :limit (? pos-int?) :by-mtime?
  (? :boolean)}`. Walks `cwd` (default `.`) recursively using
  `java.nio.file.PathMatcher`. Matches `**/*.foo` against both root and
  nested files (Java's stock `**` only matches nested — we also try the
  suffix without the leading `**/` so behavior matches
  ripgrep/fd/minimatch). Sorted most-recently-modified first by default;
  pass `by-mtime?` false for lexicographic. Capped at `limit` (default
  200) with an overflow notice. Returns absolute paths, one per line.

`:fs/grep`::
  Regex search across files. Input: `{:pattern :string :path (? :string)
  :glob (? :string) :output-mode (? :enum) :ignore-case (? :boolean)
  :context (? :int) :limit (? pos-int?)}`. Prefers `rg` (ripgrep) when
  available on PATH; falls back to `grep -rE`. `output-mode` is one of
  `"files-with-matches"` (default), `"content"` (numbered match lines
  with optional `:context` lines around each hit), or `"count"`. `glob`
  filters file names (`*.clj`). 20-second timeout; non-match returns
  the `[no matches]` sentinel; rg/grep exit 2 surfaces as `is-error`
  with stderr trimmed.

`:shell/run`::
  Run a shell command via `bash -lc`. Input: `{:command :string
  :timeout-ms (? :int)}`. Default timeout 30s. Returns combined
  stdout+stderr and the exit code; `is-error` is true on non-zero exit
  or timeout.

`:repl/eval`::
  Evaluate Clojure code in a fresh sandboxed namespace. Input:
  `{:code :string :timeout-ms (? :int)}`. Default timeout 5s. Returns
  the `pr-str` of the result. Each call creates and removes a one-shot
  `escapement.tools.eval.<nanotime>` namespace; thread-local `*ns*` is
  used (not `in-ns`) so this works from worker threads. This is a
  *sandboxed* evaluator — it does NOT talk to a live project nREPL.
  Use `:shell/run` with `clj-nrepl-eval` for that (see the unit-test
  demo for an example).

[[custom-tool]]
=== Registering a custom tool

There are two registries in play:

`escapement.tools.builtin/default-registry`::
  A `defonce` singleton atom, seeded on namespace load with the eight
  built-ins. The CLI uses this. Top-level `register!` calls in any
  namespace that gets required before `runner/run!` are visible to the
  chart — the standard Clojure side-effect-on-require pattern.

`escapement.tools.builtin/new-builtin-registry`::
  Returns a FRESH atom each call, pre-seeded with the eight built-ins.
  Use this when you want isolation — tests, or a host process driving
  multiple chart runs with disjoint tool sets.

The natural way to expose a custom tool to a CLI-driven chart is to
require its namespace from the chart and let that namespace self-register
at load time:

[source,clojure]
----
(ns my.app.tools
  (:require
   [babashka.http-client :as http]
   [escapement.tools.builtin :as builtin]
   [escapement.tools.protocol :as tp]))

(defrecord HttpGetTool []
  tp/Tool
  (tool-name    [_] :http/get)
  (description  [_] "GET a URL and return the body as a string.")
  (input-schema [_] [:map {:closed true} [:url :string]])
  (invoke [_ {:keys [url]}]
    (let [{:keys [status body]} (http/get url)]
      {:result body :is-error (not (and (>= status 200) (< status 300)))})))

;; Top-level: registers on namespace load. Idempotent because the
;; registry is keyed by tool-name — re-loading the ns just rewrites the
;; entry under :http/get.
(tp/register! builtin/default-registry (->HttpGetTool))
----

Then have your chart namespace require it:

[source,clojure]
----
(ns my.chart
  (:require
   [com.fulcrologic.statecharts.chart :as chart]
   [escapement.chart.helpers :as h]
   [my.app.tools]))   ;; <-- require triggers registration
----

Now the chart's `params-fn` can name the tool in `:real-tools`:

[source,clojure]
----
{:real-tools [:http/get :fs/read]
 :allowed-events [{:event :done :data-schema [:map [:summary :string]]}]
 ...}
----

The CLI just runs:

[source,bash]
----
escapement run my.chart/agent
----

It loads the chart (`runner/load-chart` does `require` on its namespace),
which transitively requires `my.app.tools`, which registers `:http/get`
into the singleton. The CLI then hands that singleton to `runner/run!`.

=== Explicit registration: the `--tools-ns` flag

If you would rather wire tools at the entry point — for example because
the chart cannot transitively require its tools, or you want an explicit
manifest visible at the call site — define a single-arg function and pass
its symbol with `--tools-ns`:

[source,clojure]
----
(defn register-tools!
  "Called by the CLI with the registry atom. Register everything; the
   builtins are already in there."
  [reg]
  (tp/register! reg (->HttpGetTool))
  ;; (other-ns/register! reg) ...
  reg)
----

[source,bash]
----
escapement run my.chart/agent --tools-ns my.app.tools/register-tools!
----

=== Driving the chart yourself

If you are NOT using the CLI — your own bb script or JVM entry point —
choose your registry deliberately:

[source,clojure]
----
(require '[escapement.tools.builtin :as builtin]
         '[escapement.tools.protocol :as tp]
         '[escapement.runner :as runner])

;; Option A: share the global singleton (matches CLI behavior).
(tp/register! builtin/default-registry (->HttpGetTool))

;; Option B: isolated fresh registry (better for tests / parallel runs).
(let [reg (builtin/new-builtin-registry)]
  (tp/register! reg (->HttpGetTool))
  (runner/run! {:chart           (runner/load-chart 'my.chart/agent)
                :tool-registry   reg
                :backend         my-backend
                :session-id      :session/one
                :transcript-path "out/transcript.jsonl"
                :checkpoint-dir  "out/checkpoints"}))
----

[[transcript-runner-cli]]
== Transcript, runner, CLI

=== Transcript event vocabulary

`src/escapement/transcript.clj` is the JSONL sink. Every transcript row
has `:event`, `:ts`, `:seq`, plus event-specific `:data`. The events
emitted across the codebase:

* `:runner/started`, `:runner/start-config`, `:runner/resumed`,
  `:runner/quiescent`, `:runner/tick`, `:runner/done`, `:runner/error`,
  `:runner/aborted`, `:runner/event-processed`
* `:checkpoint/written`
* `:llm/start`, `:llm/request`, `:llm/response`, `:llm/error`,
  `:llm/user-message`, `:llm/worker-exit`, `:llm/context-warning`
* `:human-input/start`, `:human-input/answer`, `:human-input/cancelled`,
  `:human-input/error`, `:human-input/interrupted`,
  `:human-input/validation-failed`
* `:artifact/captured` (with `:name` and `:bytes`)
* `:cli/config-loaded` (`:path`, `:keys`), `:cli/deps-added` (`:coords`) —
  emitted as a prelude before `:runner/started` when an `.escapement.edn`
  is discovered or runtime deps are resolved.
* `:transcript/serialize-error`

The `api` backend emits its own `:llm/request` and `:llm/response` rows
with the full Anthropic body / parsed response (so you can replay the wire
exchange exactly).

=== Inspecting with `jq`

[source,bash]
----
# All LLM responses
jq -c 'select(.event=="llm/response")' .escapement/<sid>/transcript.jsonl

# Histogram of chart events processed
jq -c 'select(.event=="runner/event-processed") | .data["event-name"]' \
   .escapement/<sid>/transcript.jsonl | sort | uniq -c

# All errors
jq -c 'select(.event | endswith("error"))' .escapement/<sid>/transcript.jsonl

# Checkpoint cadence
jq -c 'select(.event=="checkpoint/written") | .seq' \
   .escapement/<sid>/transcript.jsonl | wc -l
----

=== Runner

`src/escapement/runner.clj` exposes `run!`. Required keys:
`:chart`, `:session-id`, `:transcript-path`, `:checkpoint-dir`. Optional:
`:backend`, `:tool-registry`, `:initial-data`, `:resume?`, `:trace?`,
`:max-iterations` (default 100000), `:quiescent-sleep-ms` (default 50).

The pump loop:

1. Drain currently-deliverable events through the processor.
2. After each event, save working memory to the checkpoint store.
3. When the queue is empty, ask each `InvocationProcessor` how many live
   workers it has. If zero, terminate. Otherwise sleep `:quiescent-sleep-ms`
   and try again. This is what lets the chart park while the LLM is
   thinking.

[[cli]]
=== CLI

`src/escapement/cli.clj`. Subcommands:

* `run <chart-sym>` — execute a chart (the everyday command).
* `info` — print environment + the auto-detected LLM backend layout.
* `login codex` / `logout codex` — OAuth flow for the
  `escapement.llm.openai-codex` backend; opens a browser, stores
  credentials in `~/.escapement/openai-auth.json` (mode 0600). One-time;
  the saved token auto-refreshes.

Output paths:

* Default work directory is `.escapement/<session>/`; override with
  `--work-dir`, `--transcript`, or `--checkpoint-dir`. Artifacts produced by
  `capture-llm-output` / `forward-llm-output` land under
  `<session>/artifacts/` (see <<multi-agent>>).
* `--resume` re-opens the latest checkpoint and skips `start!`.

Initial data:

* `--input <edn-file>` reads an EDN map and seeds the chart's data model.
* `--param key=value` is a repeatable one-shot override that's merged on top
  of `--input`. Values are EDN-read with a friendly-to-strings fallback so
  bare words like `--param name=alice` produce strings (not symbols).
  Numbers, keywords, booleans, and collections parse natively.

LLM backend selection:

* `--backend (api|openai|codex)` — explicit single backend.
* Without `--backend`, the CLI scans available credentials and
  auto-assembles a backend:
+
[options="header"]
|===
| Credential               | Sub-backend kind | Default route
| `ANTHROPIC_API_KEY`      | `api` (Anthropic) | `+#"^claude-"+`
| Saved codex OAuth token  | `openai-codex`    | `+#"^gpt-5"+`
| `OPENAI_API_KEY`         | `openai`          | `+#"^gpt-"+`
| `OPENROUTER_API_KEY`     | `openai` (router) | `+#".+/.+"+`
| `ZAI_API_KEY`            | `api` (z.ai)      | `+#"^glm-"+`
|===
+
With a single credential the bare sub-backend is used. With two or more,
a `escapement.llm.multi` dispatcher is built so that a per-state
`:model` keyword in `params-fn` automatically reaches the right
provider. The first available credential (in the table's preference
order) becomes the default backend when no route matches. Run
`escapement info` to see exactly what would be built for the current
environment.
* `--model`, `--api-base-url`, `--api-key-env` override the auto-detected
  values.

Display:

* `--tui` forces the persistent TUI on (requires a TTY).
* `--no-tui` forces it off (useful in CI, or to fall back to stdin prompts
  for `:human-input` invocations).
* `--debug` enables the inspector overlay (press `?` to open) and pauses
  before the first event when `:debug :auto-pause?` is true in
  `.escapement.edn`. Forces the TUI on; cannot combine with `--no-tui`.
* By default the TUI is on for charts marked `^{:interactive? true}` and off
  otherwise. See <<human-interaction>>.

Other:

* `--tools-ns my.ns/register-tools!` invokes a registration fn over the
  builtin registry. Accepts a comma-separated list and can be passed
  multiple times; entries accumulate.
* `--source-paths a:b:c` prepends classpath roots before chart load.
* `--deps '{lib/x {:mvn/version "1.0.0"}}'` resolves additional runtime
  Maven/git coordinates via `babashka.deps/add-deps` before chart load.
* `--trace` emits per-tick transcript events.

[[project-config]]
=== Project configuration (`.escapement.edn`)

A project can pin its layout once in a single `.escapement.edn` file at
its root. Escapement walks up from the current working directory (git
style) looking for the file; the directory containing it becomes the
**config root**, and all relative paths in the file resolve against
that root — so `escapement run …` works the same from any subdirectory.

Schema (validated with Malli on load; unknown keys are rejected):

[source,clojure]
----
{:source-paths  ["ai/agents"]                 ;; classpath roots, prepended
 :deps          {hiccup/hiccup
                 {:mvn/version "2.0.0-RC3"}}  ;; runtime deps via add-deps
 :tools-ns      [my.app/register-tools]       ;; symbol or vector of symbols
 :work-dir      "ai/agents/transcripts"       ;; default --work-dir
 :default-chart my.app.charts.hello/agent}    ;; used when no chart given
----

Startup order (matters because each step may require what the previous
one made visible):

. Discover and validate `.escapement.edn`.
. Layer CLI flags over config over defaults.
. `add-deps` for `:deps` (Maven/git coords).
. `add-classpath` for `:source-paths`.
. `require` every `:tools-ns` and, if the symbol resolves to a function,
  invoke it with the builtin tool registry atom.
. Resolve the chart symbol — CLI argument wins, else `:default-chart`.

Precedence is `CLI flag > .escapement.edn > built-in default`. CLI
`:deps` is merged on top of config `:deps` (CLI wins per coordinate);
CLI `:source-paths` is prepended to config `:source-paths`; CLI
`:tools-ns` entries are appended to config entries. CLI-supplied paths
resolve against `cwd`; config-supplied paths resolve against the config
root. There is no environment-variable layer.

When a config file is found, the transcript opens with a
`:cli/config-loaded` event recording the file path and the keys present.
If runtime deps were resolved, a `:cli/deps-added` event follows.

A missing `.escapement.edn` is silent; defaults apply. A malformed file
fails fast with a humanized Malli error pointing at the offending key.

See also: <<add-chart,Adding a new chart>>.

[[idioms-gotchas]]
== Idioms and gotchas

* **`:type :internal` to keep the LLM alive.** Any transition out of (or
  back into) a bound state kills and re-spawns the worker. If you want
  the conversation to survive a hop, use `:type :internal`. Both
  `scan.clj` and `iterate.clj` lean on this.

* **`h/tell-llm` only works inside the bound state.** Outside, there is
  no live invocation to forward to. The event is silently dropped.

* **Parallel regions get their own workers.** No tool-name collision is
  possible because event-tool names encode the chart event keyword. See
  `parallel_demo.clj`.

* **Top-level `final` empties the configuration.** Wrap finals in a
  compound parent state (every demo chart does this). See
  `SPIKE_FINDINGS.md` item 2.

* **Resume restarts in-flight conversations from scratch.** When the chart
  re-enters a bound state on resume, a fresh worker is spawned with a fresh
  message history; the previous conversation does not survive a process
  restart. This is idempotent for read tools like `:fs/read` but
  **at-most-once cannot be guaranteed for side-effecting tools** like
  `:fs/edit` or `:shell/run`. Charts that need durable side-effect tracking
  must drive it themselves via the data model (e.g. `iterate.clj`
  increments `:iterations` so retries respect the cap).

* **The library passes the triggering event as `:_event`.** Inside a
  transition `script`, `(get-in data [:_event :data ...])` is the standard
  way to read the event payload.

* **Daemon threads only.** All worker threads (`llm-conv-...`) and the
  transcript writer are daemon threads. They do not prevent JVM/bb exit.

[[testing]]
== Testing

Tests run on the JVM via kaocha. The bb runtime is not used because
`com.fulcrologic.statecharts.testing` transitively requires `promesa`,
which crashes under SCI (see `SPIKE_FINDINGS.md`).

The harness is `escapement.engine.testing`. It replaces the library's
testing helpers with a synchronous pump:

[source,clojure]
----
(require '[escapement.engine.testing :as dct])

(def t (-> (dct/new-testing-env {:statechart my-chart
                                 :tool-registry my-registry}
                                my-processor1 my-processor2)
           (dct/start! initial-data)))

(dct/drain! t)             ; pump until quiescent
(dct/configuration t)      ; #{:run :finished}
(dct/in? t :finished)
(dct/data t)               ; current data-model contents
(dct/run-events! t :foo {:name :bar :data {...}})
----

=== Mocking the LLM backend

Implement `LLMBackend` with a script-driven queue of canned responses. The
M7 iterate test
(`test/escapement/charts/iterate_test.clj`) is a complete example:

[source,clojure]
----
(defrecord MockBackend [responses call-log]
  llm/LLMBackend
  (send-turn [_ request]
    (swap! call-log conj request)
    (or (.pollFirst ^LinkedBlockingDeque responses)
        (throw (ex-info "mock out of canned responses" {})))))

(defn- tool-use [tool-uses]
  {:stop-reason :tool_use
   :content     (mapv (fn [{:keys [id name input]}]
                        {:type :tool_use :id id :name name :input input})
                      tool-uses)
   :usage {} :model "mock"})

(defn- end-turn []
  {:stop-reason :end_turn :content [{:type :text :text "ok"}] :usage {} :model "mock"})
----

A test then queues up `(tool-use [...])` and `(end-turn)` responses in the
order the chart should drive them, and asserts the chart reaches
`:finished` with the expected data-model contents.

=== Stubbing a tool

Implement `Tool` with a queue of canned `{:result :is-error}` maps and
register it over the builtin (the iterate test stubs `:shell/run` so tests
do not actually run a shell):

[source,clojure]
----
(defrecord StubShellTool [responses calls]
  tp/Tool
  (tool-name    [_] :shell/run)
  (description  [_] "stub shell")
  (input-schema [_] [:map [:command :string]])
  (invoke [_ input]
    (swap! calls conj input)
    (let [r (.pollFirst ^LinkedBlockingDeque responses)]
      (or r {:result "no canned response" :is-error true}))))

(let [reg (builtin/new-builtin-registry)]
  (tp/register! reg (stub-shell [{:result "ok" :is-error false}]))
  ...)
----

=== Live smoke scripts

The `bb_test/` directory contains scripts that exercise the system against
real backends. `m6_live_smoke.clj` runs `hello`, `scan`, and
`parallel_demo`; `m7_live_iterate.clj` runs the iterate chart against a
tmp directory and reports pass/fail. These are not unit tests — they
require network access and real credentials.

[[project-layout]]
== Project layout

`src/escapement/engine/`::
  Custom engine pieces — `queue` (in-process FIFO event queue), `store`
  (atomic file-backed working-memory checkpoint), `exec` (lambda
  `ExecutionModel`), `env` (assembles the `::sc/env` map), and `testing`
  (JVM synchronous test harness). These replace
  `com.fulcrologic.statecharts.simple`, which crashes under Babashka
  because of a transitive `promesa`/SCI conflict.

`src/escapement/llm/`::
  `protocol` (the one-method `LLMBackend`), `types` (Malli schemas for
  requests/responses/content-blocks/tool-defs), `api` (Anthropic-compatible
  HTTP backend, sniffing z.ai vs Anthropic auth modes), `openai_codex`
  (ChatGPT Plus/Pro subscription backend via OAuth 2.0 + PKCE), and `cache`
  (content-addressed disk cache).

`src/escapement/tools/`::
  `protocol` (`Tool` + registry + `dispatch`) and `builtin` (the eight
  ship tools — `:fs/read`, `:fs/write`, `:fs/edit`, `:fs/multi-edit`,
  `:fs/glob`, `:fs/grep`, `:shell/run`, `:repl/eval`).

`src/escapement/invocation/`::
  `llm_conversation` — the `InvocationProcessor` that binds an LLM
  conversation to a state. The heart of the project. About 450 lines.

`src/escapement/chart/`::
  `helpers` — authoring sugar (`llm-conversation`, `tell-llm`).

`src/escapement/charts/`::
  Demo charts: `hello`, `scan`, `parallel_demo`, `iterate`.

`src/escapement/`::
  `transcript` (single-writer JSONL sink), `runner` (top-level pump loop),
  `cli` (bb/JVM entry), `prompts` (file-based prompt loading with
  `{{VAR}}` substitution).

`demos/`::
  Larger, multi-state worked examples that live outside `src/` because
  they bring their own non-Clojure artifacts (prompt markdown, sample
  input EDN, READMEs). The current resident is `demos/unit_test/` — a
  parallel chart that drives an LLM through behaviors → abstraction →
  (write|gap-analysis) → (critique|patch) → refine to author and seal
  `fulcro-spec` tests for a target function, with a sibling REPL-manager
  region that establishes a project nREPL via shared `:nrepl-port` data
  + a single `:repl/available` event.

`test/`::
  Unit tests (kaocha + fulcro-spec). Run from a JVM REPL.

`bb_test/`::
  Babashka-runnable scripts: sanity checks and live smoke runs.

`spike/`::
  Original spike scripts that proved the patterns under bb. Kept for
  reference; not used at runtime.

[[known-limitations]]
== Known limitations and roadmap

* **OpenAI Codex backend is reverse-engineered against the ChatGPT CLI
  auth flow.** OpenAI may change the protocol or revoke this path without
  notice. Use the `api` backend for production work.

* **Checkpoint-resume restarts in-flight conversations.** Re-entering a
  bound state on resume spawns a fresh worker with an empty message
  history. At-most-once cannot be guaranteed for side-effecting tools.

* **Sandboxing of third-party charts is deferred.** A chart can reference
  arbitrary tools and arbitrary side-effects through `:script` and
  `:on-entry`. There is currently no policy layer.

* **LLM token budgets are per-turn, not per-session.** Long iterative
  runs accumulate context. Use `:max-tokens` in `params-fn`, prompt for
  brevity, and watch the `:context-used-frac` field on
  `:llm/response` transcript events (see <<context-tracking>>).

[[contributing]]
== Contributing and running tests

Tests run via REPL with kaocha. The project's REPL convention (see the
`clojure-repl` skill in the user's global instructions) is to start an
nREPL, connect, and evaluate `(k/run ...)`. The relevant aliases are in
`deps.edn`: `:test` adds `test/`, `bb_test/`, fulcro-spec, kaocha, and the
guardrails JVM properties; `:kaocha` invokes `kaocha.runner`.

[[add-chart]]
=== Adding a new chart

1. Create `src/escapement/charts/my_thing.clj`. Pattern after the demos.
2. Use `h/llm-conversation` for any LLM-bound state; wrap finals in a
   compound parent.
3. Add a unit test under `test/escapement/charts/my_thing_test.clj`
   using a `MockBackend` and (where applicable) stub tools.
4. Run via `escapement run escapement.charts.my-thing/agent`.

For host projects that want to keep charts and chart utility namespaces
outside the Escapement source tree, add an `.escapement.edn` at the
project root with `:source-paths` (and optionally `:default-chart`) —
see <<project-config>>.

=== Adding a new tool

1. `defrecord` implementing `escapement.tools.protocol/Tool`.
2. Provide a Malli `input-schema`; the runtime validates before `invoke`.
3. Return `{:result <string> :is-error <bool>}`. Strings only — the LLM
   sees a string.
4. Register in the chart's tool registry via `tp/register!` (or seed a
   custom registry).
5. Add a unit test under `test/escapement/tools/`.

=== Adding a new backend

1. Implement `escapement.llm.protocol/LLMBackend`.
2. Validate request and response with `escapement.llm.types` so chart
   authors see consistent shapes regardless of backend.
3. Add a `new-backend` constructor.
4. Wire into the CLI's `make-backend` if it should be selectable via
   `--backend`.
